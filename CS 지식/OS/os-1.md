# 📌 Process / Thread / Scheduling

## 1. 프로세스와 스레드

### 1-1. 핵심 개념

- **프로세스(Process)** = 실행 중인 프로그램의 인스턴스  
  → OS가 **독립된 주소 공간(가상 메모리)** 을 부여한다.
- **스레드(Thread)** = 프로세스 내부의 실행 흐름 단위  
  → 같은 프로세스의 스레드들은 **주소 공간을 공유**한다.

```text
프로세스
 ├── 스레드 1 (PC, 레지스터, 스택 독립)
 ├── 스레드 2 (PC, 레지스터, 스택 독립)
 └── 스레드 3 (PC, 레지스터, 스택 독립)

공유 영역
 ├── 코드
 ├── 힙
 ├── 전역 데이터
 └── 파일 디스크립터
```

### 1-2. 무엇을 공유하고 무엇을 독립하는가

| 항목            | 프로세스 간 | 같은 프로세스 스레드 간 |
| --------------- | ----------- | ----------------------- |
| 코드 영역       | ❌          | ✅                      |
| 힙 / 데이터     | ❌          | ✅                      |
| 파일 디스크립터 | ❌          | ✅                      |
| 스택            | ❌          | ❌ (스레드별 독립)      |
| PC              | ❌          | ❌                      |
| 레지스터        | ❌          | ❌                      |
| 페이지 테이블   | ❌          | ✅                      |

### 핵심 인사이트

- 스레드가 가벼운 이유 → **주소 공간 공유**(생성/전환 비용 ↓)
- 하지만 공유 = 위험
  - 힙을 망가뜨리면 전체 프로세스가 위험
  - 그래서 **동기화(락)** 가 필요하다

## 2. 컨텍스트 스위칭(Context Switching)

### 2-1. 정의

CPU가 현재 실행 중인 프로세스/스레드의 상태를 저장하고, 다음 실행할 프로세스/스레드의 상태를 복원하는 과정.

### 2-2. 저장/복원하는 것

- CPU 레지스터(범용 레지스터, PC, 스택 포인터 등)
- 프로세스 상태(Running ↔ Ready)
- 메모리 관리 정보(페이지 테이블 포인터 등)

### 2-3. 왜 비용이 큰가?

#### ① 직접 비용(Direct Cost)

- 레지스터 저장/복원
- 스케줄러 코드 실행
- CPU 파이프라인 플러시(다시 채우는 데 수 사이클)

#### ② 간접 비용(Indirect Cost) — 더 크다

- **TLB miss**: 가상→물리 주소 변환 캐시 미스(수백 사이클 가능)
- **CPU 캐시 cold start**: L1/L2/L3 캐시 미스 연쇄
- **브랜치 프리딕터 cold start**: 분기 예측 정보도 워크로드에 따라 달라짐

> 결론: 컨텍스트 스위칭이 많아지면 실제 일(actual work) 대비 오버헤드가 커지고, p99가 쉽게 튄다.

### 2-4. 스레드 전환 vs 프로세스 전환

- 같은 프로세스 내 스레드 전환은 **페이지 테이블을 바꿀 필요가 없어서**(대체로) TLB flush 부담이 작다  
  → 보통 프로세스 전환보다 가볍다.

## 3. 스레드를 늘리면 왜 오히려 느려질까?

서버 워커를 8 → 16으로 늘렸는데 p99가 악화되면, 보통 아래 중 하나(또는 복합)다.

### 3-1. 컨텍스트 스위칭 과다

- CPU 코어가 4개인데 스레드가 16개면 코어당 4개 스레드 시분할
- 실행-대기-실행 반복 → **캐시 오염 / TLB miss** 증가  
  → 전환 오버헤드가 실제 처리 시간을 잡아먹는다.

### 3-2. 락 경합(Lock Contention)

- 공유 자원(DB 커넥션 풀, 캐시, 로그 버퍼)에 접근 시 락 필요
- 스레드가 많을수록 대기 시간 증가 → 처리량은 늘지 않고 대기만 늘어남

**Amdahl’s Law**

- 직렬 구간(락으로 보호되는 구간)이 아주 조금만 있어도 병렬화 이득은 제한된다.

### 3-3. 캐시 Thrashing + False Sharing

- 각 스레드가 자신의 working set을 캐시에 올리면서 서로 밀어냄
- **false sharing**: 같은 캐시 라인(보통 64B)에 있는 “서로 다른 변수”를 다른 스레드가 수정하면 캐시 무효화가 반복된다.

---

## 4. 최적 스레드 수 경험 법칙

### 4-1. CPU-bound

```text
스레드 수 ≈ CPU 코어 수
```

### 4-2. I/O-bound

```text
스레드 수 ≈ CPU 코어 수 × (1 + I/O 대기 시간 / 연산 시간)
```

---

## 5. CPU-bound vs I/O-bound 모델 선택

| 유형      | 특징                      | 적합 모델                   | 이유                 |
| --------- | ------------------------- | --------------------------- | -------------------- |
| CPU-bound | 연산 중심                 | 코어 수만큼 스레드/프로세스 | CPU를 쉬지 않게      |
| I/O-bound | 네트워크/디스크 대기 중심 | 이벤트 루프 + 비동기 I/O    | 스레드는 대부분 대기 |
| 혼합      | 둘 다 있음                | 이벤트 루프 + 워커 풀       | Node.js 전형         |

## 6. 데드락(Deadlock)

### 6-1. 정의

두 개 이상의 프로세스/스레드가 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태.

### 6-2. 발생 4조건(Coffman)

| 조건      | 설명                          | 방지 전략               |
| --------- | ----------------------------- | ----------------------- |
| 상호 배제 | 한 번에 하나만 사용 가능      | lock-free/불변 데이터   |
| 점유 대기 | 자원 점유한 채 다른 자원 대기 | all-or-nothing          |
| 비선점    | 강제로 빼앗을 수 없음         | 타임아웃/릴리즈         |
| 순환 대기 | 원형으로 대기                 | **락 획득 순서 규칙화** |

**실전에서 가장 실용적인 해법**

- 락을 항상 같은 순서로 획득한다.

## 7. CFS(Completely Fair Scheduler)

Linux에서 널리 쓰인 스케줄러.

### 7-1. 핵심 아이디어

“이상적인 멀티태스킹 CPU”를 흉내 내기 위해 **vruntime(가상 실행 시간)** 개념을 둔다.

- runnable 태스크를 vruntime 기준으로 정렬(레드-블랙 트리)
- **vruntime이 가장 작은 태스크**에 CPU를 먼저 준다
- 실행되면 vruntime이 증가 → 공정하게 분배

### 7-2. nice의 의미

- nice 범위: -20(우선) ~ +19(후순위)
- nice는 weight를 바꾼다  
  → 같은 실제 시간 실행해도 vruntime 증가 속도가 달라져 CPU 점유율이 달라진다.

---

## 8. 스핀락 vs 뮤텍스

| 구분      | 스핀락(Spinlock)       | 뮤텍스(Mutex)    |
| --------- | ---------------------- | ---------------- |
| 대기 방식 | busy-wait              | sleep(대기 큐)   |
| CPU 사용  | 대기 중에도 계속 사용  | 대기 중 CPU 양보 |
| 전환 비용 | 없음                   | 컨텍스트 스위칭  |
| 적합 상황 | 락 점유가 매우 짧을 때 | 락 점유가 길 때  |

판단 기준:

```text
락 점유 시간 < 컨텍스트 스위칭 비용 → 스핀락
락 점유 시간 > 컨텍스트 스위칭 비용 → 뮤텍스
```

# 🔥 WebTest와 연결한 이해

## A. 워커 동시성 8 → 4로 줄였더니 p99 개선

OS 관점에서 해석하면 아래 효과가 같이 난다.

- 컨텍스트 스위칭 감소(코어 4개면 4개 워커가 1:1 매핑)
- 캐시/TLB 오염 감소
- 락 경합 완화(DB/Redis/로그 버퍼 등 공유 자원)
- 메모리 압력 감소(Lighthouse 작업이 무겁다면 스왑/메모리 부족 리스크 감소)

## B. BullMQ 워커 + CPU-bound 작업(Lighthouse)

Node는 싱글 스레드 이벤트 루프라 CPU-bound를 메인에서 돌리면 이벤트 루프가 막힌다.

대안:

- `child_process.fork()`
  - 격리 강함(주소 공간 분리)
  - 생성/전환 비용 큼
- `worker_threads`
  - 생성 비용 낮음
  - 메모리 공유 가능(주의 필요)

## C. 스캔 작업은 왜 “프로세스 격리”가 안전한가

- 프로세스 모델: 주소 공간 독립  
  → 한 스캔이 메모리 누수/크래시를 내도 다른 스캔 영향이 작다.
- 스레드 모델: 힙 공유  
  → 잘못된 접근/오염이 프로세스 전체 장애로 이어질 수 있다.

# 🎯 내가 얻은 결론(운영 관점)

1. 동시성은 “많이 준다”가 정답이 아니다
2. CPU-bound는 코어 수에 맞추는 게 기본이다
3. 공유 자원(락/풀)이 많을수록 스레드 증가는 독이 된다
4. 안정성/격리가 중요하면 프로세스 모델이 유리하다
5. p99가 튀는 원인은 대체로 OS 레벨에서 커진다
