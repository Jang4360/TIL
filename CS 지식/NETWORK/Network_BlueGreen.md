## 오늘의 핵심 요약

단일 EC2 위에 컨테이너를 올리는 것까지는 Day 03에서 다뤘다. 오늘은 한 걸음 더 나아간다. 컨테이너가 늘어나면, 모든 컨테이너를 하나의 네트워크에 몰아넣는 것은 보안과 운영 양쪽에서 문제가 된다. Dev 환경의 컨테이너가 Prod DB에 접근할 수 있어서는 안 되고, 모니터링 시스템은 모든 환경을 관찰할 수 있되 비즈니스 트래픽과는 분리되어야 한다. Docker 네트워크를 **Dev-Net, Prod-Net, Monitoring-Net**으로 나누면 이 문제가 해결된다. 여기에 Host에서 동작하는 Nginx가 외부 진입점 역할을 하고, Blue/Green 전환 패턴까지 더하면 단일 서버에서도 꽤 견고한 운영 구조를 갖출 수 있다.

---

## 왜 이걸 알아야 하는가

Day 03에서 모든 컨테이너를 하나의 사용자 정의 bridge에 넣었다. 동작은 하지만 문제가 있다. 같은 네트워크에 있으면, 네트워크 내의 모든 컨테이너가 서로 이름만으로 자유롭게 통신할 수 있다. 개발 환경의 Spring Boot 앱이 운영 환경의 MySQL에 접속할 수 있다는 뜻이다. 실수로 dev 앱이 prod DB를 바라보고 있었는데, 테스트 데이터를 밀어넣는 상황 — 실제로 일어나는 사고다.

또한 모니터링 도구(Prometheus, Grafana 등)가 비즈니스 서비스와 같은 네트워크에 있으면, 모니터링 시스템의 취약점이 곧바로 서비스 전체의 취약점이 된다. 네트워크를 분리하면 **"이 컨테이너는 저 컨테이너와 절대 직접 통신할 수 없다"**는 강제적 격리를 만들 수 있다.

그리고 배포. 새 버전을 올릴 때 기존 버전을 내리고 새 버전을 올리면, 그 사이에 서비스가 중단된다. 단일 EC2에서도 Blue/Green 패턴을 적용하면 다운타임 없이 전환할 수 있다. 이 모든 것이 Docker 네트워크 분리와 Nginx 설정의 조합으로 가능하다.

## 핵심 개념

### 1. 왜 네트워크를 나누는가 — 격리의 원칙

네트워크 분리의 핵심 원칙은 **"통신이 필요한 컨테이너만 같은 네트워크에 둔다"**는 것이다. 이것은 보안의 최소 권한 원칙(Principle of Least Privilege)을 네트워크 레벨에 적용한 것이다.

Docker에서 네트워크 격리는 간단하다. **서로 다른 Docker 네트워크에 있는 컨테이너는 통신할 수 없다.** 이것이 전부다. 같은 네트워크에 있으면 컨테이너 이름으로 자유롭게 통신하고, 다른 네트워크에 있으면 존재 자체를 모른다. 별도의 방화벽 규칙을 설정할 필요 없이, 네트워크 소속만으로 접근 제어가 이루어진다.

하나의 컨테이너가 여러 네트워크에 동시에 속할 수 있다는 점도 중요하다. 이 특성이 "경계에 있는" 컨테이너, 예를 들어 Reverse Proxy나 모니터링 에이전트를 설계할 때 핵심이 된다.

### 2. 세 개의 네트워크 — Dev-Net, Prod-Net, Monitoring-Net

단일 EC2에서의 전형적인 네트워크 분리 구조를 보자.

| 네트워크 | 소속 컨테이너 | 목적 |
|----------|--------------|------|
| **prod-net** | prod-app, prod-mysql, prod-redis | 운영 서비스 간 통신. 외부 트래픽의 최종 도착지 |
| **dev-net** | dev-app, dev-mysql | 개발/테스트 환경. prod와 완전 격리 |
| **monitoring-net** | prometheus, grafana, node-exporter | 시스템 관찰. 메트릭 수집과 시각화 |

이 구조에서 dev-app은 prod-mysql에 접근할 수 없다. 다른 네트워크에 있으므로 DNS 이름 해석 자체가 안 된다. "연결이 느린 게 아니라 존재를 모른다"는 수준의 격리다.

#### 경계를 넘어야 하는 컨테이너

일부 컨테이너는 여러 네트워크에 동시에 속해야 한다.

| 컨테이너 | 소속 네트워크 | 이유 |
|----------|-------------|------|
| **Nginx (Reverse Proxy)** | prod-net + dev-net | 외부 요청을 prod와 dev로 각각 라우팅해야 하므로 |
| **Prometheus** | monitoring-net + prod-net + dev-net | 모든 환경의 메트릭을 수집해야 하므로 |
| **Grafana** | monitoring-net | Prometheus에서 데이터를 가져오기만 하면 되므로 monitoring-net만으로 충분 |

Nginx가 prod-net과 dev-net에 모두 속한다는 것은, Nginx 컨테이너 안에서 prod-app과 dev-app 둘 다 이름으로 접근 가능하다는 뜻이다. 하지만 prod-app에서 dev-mysql로는 여전히 접근할 수 없다. 경계를 넘는 것은 명시적으로 다중 네트워크에 연결한 컨테이너만 가능하다.

### 3. Host Nginx vs Container Nginx — 어디서 실행할 것인가

Reverse Proxy를 호스트에 직접 설치할 수도 있고, Docker 컨테이너로 실행할 수도 있다. 각각의 트레이드오프가 있다.

| 항목 | Host Nginx | Container Nginx |
|------|------------|-----------------|
| 포트 바인딩 | 직접 80/443 점유. 충돌 위험 없음 | 호스트 포트 매핑 필요 |
| Docker 네트워크 접근 | 컨테이너 내부 IP 또는 호스트 포트 매핑을 통해 접근 | Docker 네트워크에 직접 연결. 컨테이너 이름 사용 가능 |
| 설정 변경 시 | systemctl reload nginx | 컨테이너 재시작 또는 볼륨 마운트 후 reload 시그널 |
| 장애 격리 | Nginx 장애가 호스트 영향 가능 | 컨테이너 내로 격리 |
| 관리 일관성 | OS 패키지 관리로 업데이트 | 다른 서비스와 동일하게 Docker 이미지로 관리 |

**실무에서의 선택 기준:**

**Nginx도 컨테이너로 실행하는 것이 압도적으로 유리하며 실무 표준에 가깝다.**
실무에서 발생하는 대부분의 프록시 장애는 도커 엔진 통째가 죽는 장애보다, 개발자가 Nginx 설정(오타, 라우팅 조건, 인증서 문제 등)을 잘못하여 발생하는 휴먼 에러가 훨씬 잦고 크리티컬하다. 컨테이너화를 통해 dev 환경과 prod 환경의 Nginx 설정을 완벽하게 동일한 형상으로 테스트 및 배포할 수 있으며, 복잡한 포트 바인딩 대신 `proxy_pass http://prod-app-blue;` 처럼 직관적으로 라우팅할 수 있다. 
반면 Host Nginx는 Docker 데몬 전체가 죽어도 사용자에게 "점검 중입니다" 화면을 응답할 수 있다는 장점 외에는 이점이 적다.

**Host Nginx를 사용할 때의 라우팅 방식:**

Host Nginx가 Docker 네트워크 밖에 있으므로, 컨테이너에 접근하려면 포트 매핑이 필요하다. 각 컨테이너를 127.0.0.1의 서로 다른 포트에 매핑하고, Nginx가 이 포트로 프록시한다.

| 호스트 매핑 | 대상 컨테이너 | Nginx 라우팅 기준 |
|-------------|-------------|------------------|
| 127.0.0.1:8080 | prod-app (내부 8080) | api.example.com → 127.0.0.1:8080 |
| 127.0.0.1:8081 | dev-app (내부 8080) | dev-api.example.com → 127.0.0.1:8081 |
| 127.0.0.1:3000 | grafana (내부 3000) | monitor.example.com → 127.0.0.1:3000 |

127.0.0.1로 바인딩하면 외부에서 직접 8080, 8081 등으로 접근할 수 없다. 반드시 Nginx(80/443)를 거쳐야 한다. 이것이 보안 계층을 하나 더 추가하는 효과를 낸다.

### 4. Blue/Green 전환 — 단일 EC2에서의 무중단 배포

Blue/Green 배포는 두 벌의 동일한 환경을 유지하고, 한쪽에서 다른 쪽으로 트래픽을 전환하는 방식이다. "현재 라이브"인 쪽을 Blue, "새로 배포할" 쪽을 Green이라 부른다.

#### 전환의 흐름 (CI/CD 자동화 스크립트 기반)

무중단 배포를 위한 스크립트는 토글(Toggle) 스위치처럼 두 환경(Blue, Green)을 번갈아가며 순환하는 구조로 작성된다.

1. **상태 확인:** 현재 상태에서 Nginx가 가리키고 있는 포트 혹은 컨테이너가 Blue인지 판단한다.
2. **대기 환경 배포:** 라이브 환경이 아닌 대기 환경(Green)에 새 버전 컨테이너를 띄운다.
3. **헬스 체크:** Green 컨테이너가 구동될 때까지 기다린다. /actuator/health 엔드포인트 등의 응답이 정상이 될 때까지 대기한다. (보통 10~30초)
4. **전환 (설정 변경 및 스위치):** 배포 스크립트에서 Nginx의 환경 설정 파일(예: `default.conf`)의 `proxy_pass` 대상을 Green 컨테이너로 변경(문자열 치환)한다. 이후 `docker exec nginx nginx -s reload` 명령어를 보내 Nginx가 변경된 설정을 즉각 반영하도록 한다. 처리 중이던 구버전 요청은 마무리하되, 새로운 요청들은 모두 새 버전(Green)으로 보내져 다운타임이 발생하지 않는다.
5. **검증 및 기존 버전 정리:** 새로 배포된 Green에 에러가 없는지 확인 후, 더 이상 트래픽을 받지 않는 구버전(Blue) 컨테이너는 종료(kill)하여 서버 메모리를 여유롭게 비운다.
6. **롤백:** 문제가 발생하면 Nginx 설정 내용을 바로 전으로 되돌린 후 다시 `reload` 시키면 즉각 복구된다.

#### 단일 EC2에서의 제약

| 항목 | 다중 서버 Blue/Green | 단일 EC2 Blue/Green |
|------|---------------------|---------------------|
| 리소스 | 서버 2대 필요 | 한 서버에 2개 컨테이너 동시 실행. 메모리의 약 2배 소요 |
| 전환 속도 | DNS 또는 LB 레벨. 수초~수분 | Nginx reload. 100ms 이내 |
| 롤백 속도 | 동일 | 동일 |
| 동시 실행 부담 | 별도 서버이므로 없음 | 전환 중 두 컨테이너가 동시 실행되므로 메모리 여유 필요 |

Spring Boot 앱이 각각 512MB~1GB의 힙 메모리를 사용한다면, Blue/Green 전환 중에는 최소 1~2GB의 추가 메모리가 필요하다. t3.small(2GB RAM)에서는 빠듯하고, t3.medium(4GB RAM) 이상이 현실적이다.

#### Blue/Green의 네트워크 구성

Blue와 Green 컨테이너는 같은 prod-net에 속한다. Nginx도 prod-net에 속해 있으므로, 두 컨테이너 모두에 이름으로 접근할 수 있다.

| 컨테이너 이름 | 상태 | Nginx upstream 대상 |
|-------------|------|-------------------|
| prod-app-blue | 현재 라이브 | ✅ 현재 가리키는 중 |
| prod-app-green | 대기 (새 버전) | 전환 시 가리킴 |

전환은 Nginx 설정에서 upstream의 대상을 prod-app-blue에서 prod-app-green으로 바꾸는 것이다. 컨테이너 이름이 곧 주소이므로, IP를 일일이 확인할 필요 없다.

### 5. 전체 구성 조감도

최종적으로 단일 EC2 위의 구성을 정리하면 이렇다.

**외부 진입:** 클라이언트 → EC2 보안그룹(80/443) → Nginx(Host 또는 Container)

**Nginx의 라우팅 분기:**

| 도메인 | 대상 네트워크 | 대상 컨테이너 |
|--------|-------------|-------------|
| api.example.com | prod-net | prod-app-blue 또는 prod-app-green |
| dev-api.example.com | dev-net | dev-app |
| monitor.example.com | monitoring-net | grafana |

**네트워크 간 격리:**

| 출발 | 도착 | 통신 가능 여부 |
|------|------|-------------|
| prod-app → prod-mysql | ✅ 같은 prod-net |
| dev-app → dev-mysql | ✅ 같은 dev-net |
| dev-app → prod-mysql | ❌ 다른 네트워크 |
| prometheus → prod-app | ✅ prometheus가 prod-net에도 소속 |
| grafana → prod-app | ❌ grafana는 monitoring-net에만 소속 |

**네트워크 간 격리 및 연결 원리:**

Docker Bridge 네트워크를 여러 개로 분리하면 다음 요소들이 물리적으로 단절되는 격리 효과를 얻을 수 있다.
1. **IP Subnet 분리:** 각 네트워크는 도커로부터 별개의 대역폭을 할당받는다.
2. **DNS(이름 해석) 공간 분리:** 서로의 네트워크에 있는 DNS 명부를 훔쳐볼 수 없으므로, 서로의 이름을 IP로 변환할 수조차 없다.
3. **방화벽(iptables) 강력 차단:** 리눅스 커널 수준에서 넘어오는 패킷 교류가 엄격히 차단된다.

반대로, Prometheus처럼 두 가지 이상의 환경(monitoring-net, dev-net, prod-net 등)에 모두 접근해야 하는 서비스의 경우, 단순히 `docker-compose.yml` 에서 `networks` 리스트에 여러 네트워크 이름을 등록해 동일 컨테이너 몸체에 여러 개의 랜 카드를 꽂는 식으로 우아하게 문제를 풀 수 있다.

결국 이 구조의 핵심은 **"네트워크 소속이 곧 접근 권한"**이라는 점이다. 복잡한 방화벽 규칙 없이도 네트워크 소속 관계만 설정함으로써 깔끔한 인프라 뼈대를 달성할 수 있다.

## 시나리오

### 시나리오 1: dev 앱이 prod DB에 접속해서 테스트 데이터를 밀어넣었다

**상황:** 팀원이 dev-app의 DB 접속 정보를 설정하다가 실수로 prod-mysql의 주소를 넣었다. 모든 컨테이너가 하나의 Docker 네트워크(app-net)에 있었기 때문에, dev-app에서 prod-mysql로의 접속이 성공했다. 테스트 코드가 돌면서 운영 DB에 더미 데이터 수천 건이 삽입되었다.

**원인 분석:** 네트워크가 분리되어 있지 않았다. 모든 컨테이너가 같은 bridge 네트워크에 속해 있으면, 컨테이너 이름만 알면 누구든 접근할 수 있다. 이것은 "모든 직원이 모든 사무실 열쇠를 가지고 있는" 상태와 같다.

**해결 방안:** 첫째, prod-net과 dev-net을 분리한다. dev-app은 dev-net에만, prod-mysql은 prod-net에만 속하게 한다. 이렇게 하면 dev-app에서 prod-mysql이라는 이름을 사용해도 DNS 해석 자체가 불가능하다. 둘째, 환경 변수로 DB 접속 정보를 주입하되, Docker Compose 파일을 prod용과 dev용으로 분리하여 실수의 여지를 줄인다. 셋째, prod DB에는 접근 가능한 사용자 계정을 별도로 관리하고, dev 계정이 prod DB에 접근할 수 없도록 MySQL 사용자 권한도 분리한다.

### 시나리오 2: Blue/Green 전환 중 메모리 부족으로 Green 컨테이너가 죽는다

**상황:** t3.small(2GB RAM) EC2에서 Blue/Green 전환을 시도했다. Green 컨테이너(Spring Boot, 힙 1GB)를 추가로 띄우자, OS의 OOM Killer가 동작하면서 Green 컨테이너가 강제 종료되었다. 최악의 경우 Blue 컨테이너까지 함께 죽을 수 있다.

**원인 분석:** Blue 컨테이너(1GB) + Green 컨테이너(1GB) + MySQL(약 300~500MB) + OS 자체 사용량(약 300~500MB)을 합치면 2GB를 훌쩍 넘는다. Linux의 OOM Killer는 메모리가 고갈되면 메모리를 가장 많이 쓰는 프로세스를 강제 종료하는데, 어떤 컨테이너가 죽을지는 예측하기 어렵다.

**해결 방안:** 첫째, EC2 인스턴스를 t3.medium(4GB) 이상으로 업그레이드한다. Blue/Green 전환에는 동시 실행 가능한 메모리 여유가 필수다. 둘째, 각 컨테이너에 메모리 제한을 명시적으로 설정한다. Docker의 메모리 제한(예: 768MB)을 걸어두면, 컨테이너가 제한을 초과할 때 해당 컨테이너만 종료되고 다른 컨테이너에 영향을 주지 않는다. 셋째, Spring Boot의 힙 메모리를 컨테이너 제한의 70~80% 수준으로 맞춘다(컨테이너 768MB이면 힙 512MB). 나머지 20~30%는 Metaspace, 스레드 스택, NIO 버퍼 등 비힙 영역이 사용한다.

### 시나리오 3: Prometheus가 prod-app의 메트릭을 수집하지 못한다

**상황:** Prometheus를 monitoring-net에만 연결해두었다. prod-app은 prod-net에만 속해 있다. Prometheus 설정에서 prod-app:8080/actuator/prometheus를 타겟으로 지정했지만, "connection refused" 에러가 발생한다.

**원인 분석:** Prometheus와 prod-app이 서로 다른 Docker 네트워크에 있다. 다른 네트워크에 있는 컨테이너는 이름 해석이 불가능하므로, Prometheus에서 prod-app이라는 호스트를 찾을 수 없다. Docker 네트워크 격리가 정확히 의도한 대로 동작한 것이지만, Prometheus는 예외적으로 여러 네트워크에 접근해야 하는 컨테이너다.

**해결 방안:** Prometheus 컨테이너를 monitoring-net, prod-net, dev-net에 모두 연결한다. 하나의 컨테이너는 여러 Docker 네트워크에 동시에 속할 수 있으므로, Prometheus는 monitoring-net을 통해 Grafana와 통신하고, prod-net을 통해 prod-app의 메트릭을 수집하고, dev-net을 통해 dev-app의 메트릭을 수집한다. 단, Grafana는 monitoring-net에만 두어 불필요한 네트워크 노출을 최소화한다. Grafana는 Prometheus의 데이터를 조회하기만 하면 되므로 비즈니스 네트워크에 직접 접근할 필요가 없다.
