# Day 02. DNS — 도메인이 IP로 바뀌는 과정과 그 사이의 문제들

> 시리즈: 클라우드/네트워크/인프라 실무 지식 · Phase 1 네트워크 기초 & 실무  
> 예상 읽기 시간: 12분

---

## 오늘의 핵심 요약

브라우저에 도메인을 입력하면, 실제 통신이 시작되기 전에 반드시 그 도메인을 IP 주소로 변환하는 과정이 선행된다. 이 변환을 담당하는 시스템이 DNS(Domain Name System)다. DNS는 로컬 캐시 → OS 리졸버 → 재귀 리졸버 → 루트/TLD/권한 네임서버 순서로 질의를 확장해 나가며, 이 과정은 보통 수십 밀리초 안에 끝난다. 하지만 DNS가 실패하거나 느려지면 서비스 전체가 접근 불가 상태에 빠질 수 있다. DNS는 인터넷의 전화번호부이자, 장애 시 가장 먼저 의심해야 할 인프라 계층이다.

---

## 왜 이걸 알아야 하는가

Spring Boot로 API 서버를 개발하고, 배포까지 마쳤다. 그런데 클라이언트에서 "연결이 안 된다"는 보고가 들어온다. 서버는 정상이고, 포트도 열려 있고, 방화벽 규칙도 맞다. 이때 DNS를 모르면 원인 파악의 첫 단추조차 끼울 수 없다.

실무에서 마주치는 DNS 관련 문제는 생각보다 빈번하다. 도메인을 새로 연결했는데 반영이 안 되는 상황, 내부 서비스 간 호출에서 간헐적으로 타임아웃이 나는 상황, 배포 후 일부 사용자만 구버전 서버로 접속하는 상황 — 모두 DNS의 동작 원리를 이해하지 못하면 디버깅이 불가능하다. 특히 클라우드 환경에서는 서버 IP가 수시로 바뀌기 때문에, DNS는 더 이상 "설정하고 잊어버리는 것"이 아니라 "지속적으로 관리해야 하는 인프라"다.

## 핵심 개념

### 1. DNS가 필요한 이유

컴퓨터 간 통신은 IP 주소로 이루어진다. 하지만 사람이 93.184.216.34 같은 숫자를 외워서 쓸 수는 없다. 도메인 이름(example.com)은 사람을 위한 것이고, IP 주소는 기계를 위한 것이다. DNS는 이 둘을 연결하는 분산 데이터베이스 시스템이다.

여기서 "분산"이라는 단어가 핵심이다. DNS는 하나의 거대한 서버가 모든 도메인을 관리하는 구조가 아니다. 전 세계에 계층적으로 분산된 수천 대의 서버가 각자 맡은 영역의 정보를 관리하고, 질의가 들어오면 협력해서 답을 찾는다. 이 설계 덕분에 전 세계 수십억 개의 도메인이 문제 없이 동작할 수 있다.

### 2. DNS 조회의 전체 흐름

사용자가 브라우저에 api.example.com을 입력했을 때, IP를 찾는 과정은 다음 순서로 진행된다.

**1단계: 로컬 캐시 확인**

가장 먼저 자기 자신에게 묻는다. 운영체제는 최근에 조회한 DNS 결과를 캐시에 저장해둔다. 이미 알고 있는 도메인이면 네트워크 요청 없이 즉시 IP를 반환한다. 브라우저도 자체 DNS 캐시를 가지고 있어서, OS 캐시보다 먼저 확인하는 경우가 많다. Chrome의 경우 DNS 캐시 기본 유효 시간은 약 60초다.

**2단계: OS의 hosts 파일 확인**

캐시에 없으면, OS는 로컬에 저장된 hosts 파일을 확인한다. 이 파일에 도메인과 IP의 매핑이 직접 기록되어 있으면 그것을 사용한다. 개발 환경에서 로컬 도메인을 127.0.0.1로 매핑할 때 흔히 쓰는 방법이다. 다만 운영 환경에서 hosts 파일에 의존하면 관리가 어려워지므로 권장되지 않는다.

**3단계: 재귀 리졸버(Recursive Resolver)에게 질의**

로컬에서 답을 못 찾으면, OS에 설정된 DNS 서버(재귀 리졸버)에게 질의를 보낸다. 이 서버는 보통 ISP(인터넷 서비스 제공자)가 제공하거나, 직접 지정한 퍼블릭 DNS(예: Google의 8.8.8.8, Cloudflare의 1.1.1.1)를 사용한다. 재귀 리졸버는 "내가 대신 찾아올게"라고 약속하는 중개자다. 자신의 캐시에 답이 있으면 바로 반환하고, 없으면 다음 단계로 넘어간다.

**4단계: 계층적 질의 — 루트 → TLD → 권한 네임서버**

재귀 리졸버도 답을 모르면, DNS의 계층 구조를 따라 올라간다.

| 계층 | 역할 | 예시 |
|------|------|------|
| **루트 네임서버** | "com은 누가 관리하는지" 알려줌 | 전 세계 13개 루트 서버 클러스터 (a~m.root-servers.net) |
| **TLD 네임서버** | ".com 도메인 중 example.com은 누가 관리하는지" 알려줌 | Verisign이 .com TLD 운영 |
| **권한(Authoritative) 네임서버** | example.com의 실제 IP를 알려줌 | 도메인 소유자가 지정한 네임서버 |

이 과정은 계단식으로 진행된다. 루트 서버에게 "api.example.com 아니?"라고 물으면, 루트는 "모르겠고, .com은 저쪽에 물어봐"라고 TLD 서버 주소를 알려준다. TLD 서버에게 다시 물으면, "example.com은 저쪽 네임서버가 관리해"라고 권한 네임서버 주소를 알려준다. 최종적으로 권한 네임서버가 "api.example.com의 IP는 93.184.216.34야"라고 답한다.

전체 과정은 캐시가 없는 최악의 경우에도 보통 **50~200ms** 안에 완료된다. 캐시가 있으면 **1~5ms** 수준이다.

### 3. DNS 레코드 타입

권한 네임서버가 보관하고 있는 정보는 여러 종류가 있다. 가장 자주 만나는 레코드 타입을 정리하면 다음과 같다.

| 레코드 타입 | 역할 | 예시 |
|-------------|------|------|
| **A** | 도메인 → IPv4 주소 | example.com → 93.184.216.34 |
| **AAAA** | 도메인 → IPv6 주소 | example.com → 2606:2800:220:1:... |
| **CNAME** | 도메인 → 다른 도메인 (별칭) | www.example.com → example.com |
| **MX** | 메일 서버 지정 | example.com → mail.example.com (우선순위 10) |
| **NS** | 해당 도메인의 네임서버 지정 | example.com → ns1.provider.com |
| **TXT** | 임의의 텍스트 정보 | SPF, DKIM 등 메일 인증, 도메인 소유권 확인 |

백엔드 개발자가 가장 자주 다루는 것은 **A 레코드**와 **CNAME 레코드**다. 서버 IP가 고정이면 A 레코드를, 로드밸런서나 CDN처럼 IP가 유동적인 대상을 가리킬 때는 CNAME 레코드를 사용한다. 단, CNAME은 도메인의 루트(apex)에는 설정할 수 없다는 제약이 있다. 즉 example.com 자체에 CNAME을 걸 수 없고, www.example.com 같은 서브도메인에만 가능하다. 이 제약을 우회하기 위해 AWS Route 53의 Alias 레코드, Cloudflare의 CNAME Flattening 같은 벤더 확장 기능이 존재한다.

### 4. TTL — 캐시의 유효 시간

DNS 응답에는 **TTL(Time To Live)** 값이 포함된다. "이 결과를 몇 초 동안 캐시해도 좋다"는 의미다. TTL이 3600이면 1시간 동안은 같은 질의에 대해 캐시된 결과를 사용한다.

TTL 설정은 트레이드오프다.

| TTL | 장점 | 단점 |
|-----|------|------|
| **짧은 TTL** (60~300초) | IP 변경 시 빠르게 반영. 장애 시 신속한 전환 가능 | DNS 질의 빈도 증가, 약간의 지연 추가 |
| **긴 TTL** (3600~86400초) | DNS 질의 부하 감소, 응답 속도 향상 | IP 변경 반영에 최대 TTL만큼의 시간 소요 |

운영 환경에서는 보통 300초(5분) 정도를 기본으로 설정하고, 마이그레이션이나 서버 교체를 앞두고 있다면 미리 60초 이하로 낮춰두는 것이 일반적이다. 중요한 점은, TTL을 낮추더라도 **모든 중간 캐시가 즉시 반영하지는 않는다**는 것이다. ISP의 리졸버가 TTL을 무시하고 자체 최소 캐시 시간(보통 30초~수 분)을 적용하는 경우가 있기 때문이다.

### 5. DNS와 Java/Spring의 관계

Java 애플리케이션에서 DNS는 한 가지 독특한 문제를 만든다. JVM은 기본적으로 DNS 조회 결과를 **영구 캐시**한다(보안 매니저가 활성화된 경우). 이는 JVM이 한번 조회한 도메인의 IP를 프로세스가 죽을 때까지 바꾸지 않는다는 뜻이다. 보안 매니저 없이 실행하면 기본 캐시 시간은 30초다.

이것이 왜 문제인가? 클라우드 환경에서 로드밸런서나 RDS 엔드포인트의 IP는 장애 조치(failover)나 스케일링 시 바뀔 수 있다. JVM이 이전 IP를 캐시하고 있으면, DNS가 이미 새 IP를 가리키고 있어도 애플리케이션은 죽은 서버에 계속 연결을 시도한다. AWS 공식 문서에서도 JVM의 DNS 캐시 TTL을 60초 이하로 설정할 것을 권장한다.

## 시나리오

### 시나리오 1: 도메인을 연결했는데 "사이트에 연결할 수 없음"이 뜬다

**상황:** 새 서비스를 배포하고, DNS 관리 콘솔에서 A 레코드를 등록했다. 그런데 브라우저에서 도메인을 입력하면 "사이트에 연결할 수 없음"이 표시된다. 서버에 IP로 직접 접속하면 잘 된다.

**원인 분석:** DNS 레코드 변경이 전파되는 데는 시간이 걸린다. 새 레코드가 권한 네임서버에 등록되었더라도, 전 세계의 재귀 리졸버와 로컬 캐시에 반영되려면 이전 TTL이 만료되어야 한다. 만약 이전에 같은 도메인으로 다른 레코드가 있었고 TTL이 3600초였다면, 최대 1시간까지 이전 결과가 반환될 수 있다. 또한 NS 레코드를 변경한 경우(네임서버 자체를 옮긴 경우), 전파에 24~48시간이 걸리기도 한다.

**해결 방안:** 첫째, DNS 조회 도구(nslookup, dig 등)로 권한 네임서버에 직접 질의해서 레코드가 제대로 등록되었는지 확인한다. 둘째, 전파 상태를 확인할 수 있는 온라인 도구(whatsmydns.net 등)로 글로벌 전파 현황을 점검한다. 셋째, 급하다면 로컬 hosts 파일에 임시로 매핑을 추가해 테스트를 진행하고, 전파가 완료되면 제거한다. 향후에는 서버 교체 계획이 있을 때 TTL을 미리(최소 기존 TTL 이상의 시간 전에) 60초 이하로 낮춰두는 습관을 들인다.

### 시나리오 2: 마이크로서비스 간 호출에서 간헐적 타임아웃

**상황:** 쿠버네티스 클러스터 안에서 주문 서비스가 결제 서비스를 도메인으로 호출한다. 평소에는 응답 시간이 50ms 이내인데, 간헐적으로 5초 이상 지연되거나 타임아웃(보통 연결 타임아웃 3~5초 설정)이 발생한다.

**원인 분석:** 쿠버네티스 내부 DNS(CoreDNS)에 과부하가 걸린 것이다. 클러스터 내 모든 파드의 DNS 질의가 CoreDNS를 거치는데, 서비스가 늘어나면서 초당 질의 수가 CoreDNS의 처리 용량을 초과했다. CoreDNS 파드의 CPU가 지속적으로 80% 이상이었고, DNS 응답 지연이 서비스 호출 지연으로 이어진 것이다. 또한 Java 애플리케이션이 DNS 결과를 캐시하지 않아 매 요청마다 DNS 조회를 수행하고 있었다.

**해결 방안:** 첫째, CoreDNS의 레플리카 수를 늘린다(기본 2개에서 부하에 맞게 조정). 둘째, 각 노드에 DNS 캐시 레이어(NodeLocal DNSCache)를 배치해 CoreDNS로의 질의를 줄인다. 셋째, JVM의 DNS 캐시 TTL을 적절히 설정해(예: 30~60초) 불필요한 반복 조회를 방지한다. 이 조합으로 DNS 관련 지연은 대부분 해소된다.

### 시나리오 3: 배포 후 일부 사용자가 구버전 서버에 접속한다

**상황:** Blue-Green 배포를 진행했다. DNS의 A 레코드를 기존 서버(Blue) IP에서 신규 서버(Green) IP로 변경했다. 그런데 배포 후 30분이 지났는데도 일부 사용자가 여전히 구버전 서버에 접속하고 있다.

**원인 분석:** A 레코드의 TTL이 1800초(30분)로 설정되어 있었다. 배포 시점에 TTL을 줄이지 않고 바로 IP를 변경했기 때문에, 이미 캐시된 결과를 가진 사용자는 최대 30분간 이전 IP로 접속한다. 일부 ISP의 리졸버는 TTL보다 더 오래 캐시하기도 하므로, 실제 전환 시간은 더 길어질 수 있다.

**해결 방안:** Blue-Green 배포에서 DNS 전환을 사용하려면, 배포 **최소 기존 TTL 이상의 시간 전에** TTL을 60초 이하로 낮춰야 한다. 예를 들어 기존 TTL이 1800초라면, 배포 30분 전에 먼저 TTL만 60초로 변경하고, TTL이 만료된 후(30분 후) IP를 전환한다. 더 나은 방법은 DNS 전환 대신 로드밸런서 레벨에서 트래픽을 전환하는 것이다. ALB/NLB의 타겟 그룹을 교체하면 DNS TTL과 무관하게 즉시 전환된다.
