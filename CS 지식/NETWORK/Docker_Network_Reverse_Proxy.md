# Day 03. Host와 Container의 관계, Docker Network, Reverse Proxy, 그리고 라우팅 전략

> 시리즈: 클라우드/네트워크/인프라 실무 지식 · Phase 1 네트워크 기초 & 실무  
> 예상 읽기 시간: 14분

---

## 오늘의 핵심 요약

EC2 한 대 위에 Docker 컨테이너를 올리는 순간, 네트워크는 한 계층이 더 생긴다. 호스트(EC2)에는 실제 IP가 있고, 컨테이너에는 Docker가 만든 가상 네트워크 안의 내부 IP가 할당된다. 이 둘을 연결하는 것이 Docker Network이고, 외부 트래픽을 적절한 컨테이너로 안내하는 것이 Reverse Proxy의 역할이다. 하나의 EC2에서 Spring Boot 앱, DB, Redis를 컨테이너로 운영하든, dev/prod를 분리하든, 이 구조를 이해해야 "포트가 충돌한다", "컨테이너끼리 통신이 안 된다", "외부에서 접속이 안 된다" 같은 문제를 해결할 수 있다.

---

## 왜 이걸 알아야 하는가

Spring Boot로 개발한 앱을 EC2에 배포한다고 해보자. 로컬에서는 잘 돌았는데, EC2에 Docker로 올리니 문제가 생긴다. 앱 컨테이너에서 같은 EC2의 MySQL 컨테이너에 접속하려는데 "Connection refused"가 뜬다. localhost로 연결했기 때문이다 — 컨테이너 안에서 localhost는 호스트가 아니라 컨테이너 자기 자신을 가리킨다.

혹은 하나의 EC2에 API 서버와 관리자 페이지를 함께 올리고 싶은데, 둘 다 80포트를 써야 한다. 포트 충돌을 어떻게 피할까? 도메인 기반으로 트래픽을 분기하고 싶은데, 컨테이너 앞에 뭘 두어야 할까?

이 모든 질문의 답은 Docker Network와 Reverse Proxy에 있다. 이 개념을 모르면, 단일 EC2 위에서 컨테이너 여러 개를 운영하는 가장 기본적인 구성조차 제대로 할 수 없다.

## 핵심 개념

### 1. Host와 Container — 두 개의 세계

EC2 인스턴스는 하나의 Linux 머신이다. 이 머신에는 AWS가 할당한 프라이빗 IP(예: 10.0.1.15)가 있고, 퍼블릭 IP나 Elastic IP가 연결되어 있을 수 있다. 이것이 **호스트 네트워크**다.

Docker 컨테이너를 실행하면, Docker는 기본적으로 자체 가상 네트워크를 만든다. 컨테이너는 이 가상 네트워크 안에서 172.17.0.x 대역의 IP를 받는다. 핵심을 정리하면 이렇다.

| 구분 | 호스트(EC2) | 컨테이너 |
|------|-------------|----------|
| IP 주소 | AWS가 할당 (10.0.x.x) | Docker가 할당 (172.17.0.x 등) |
| 포트 사용 | 실제 외부와 통신 | 컨테이너 내부에서만 유효 |
| localhost의 의미 | EC2 자기 자신 | 컨테이너 자기 자신 |
| 네트워크 격리 | 없음 (물리 네트워크에 직접 연결) | 기본적으로 격리됨 |

**Low-Level 관점에서의 포트(Port)**
포트는 인터넷 개념이라기보다는 운영체제(OS) 내부에서 "네트워크 트래픽을 특정 프로그램(프로세스)에게 할당하기 위해 뚫어놓은 파이프라인(Socket)"이다. 
컨테이너라는 작은 가상 OS 안에서 Spring Boot가 "나는 8080번 방을 쓸게!" 하고 대기(Listen)하고 있으면, Nginx나 컨테이너 외부에서 목적지 포트를 8080으로 적어 보낸 패킷만이 운영체제를 거쳐 해당 애플리케이션에 도달하게 된다. 하나의 컨테이너 안에는 보통 하나의 핵심 애플리케이션만 실행**(1 Container = 1 Process 권장)**하므로, 포트는 그 애플리케이션으로 들어가는 고유한 진입점이 된다.

비유하자면, EC2는 건물이고 컨테이너는 건물 안의 방이다. 각 방에는 내선 번호(컨테이너 IP)가 있지만, 외부에서 전화를 걸려면 건물의 대표 번호(호스트 IP)를 거쳐야 한다. 내선끼리는 직접 통화할 수 있지만, 외부 전화를 받으려면 교환대(포트 바인딩 또는 Reverse Proxy)가 필요하다.

### 2. Docker Network — 컨테이너 간 통신의 기반

Docker는 여러 종류의 네트워크 드라이버를 제공한다. 단일 EC2 환경에서 알아야 할 핵심은 세 가지다.

| 네트워크 모드 | 동작 방식 | 사용 시점 |
|---------------|-----------|-----------|
| **bridge** (기본) | Docker가 가상 브리지(docker0)를 만들고, 컨테이너에 내부 IP를 할당. 외부 접근은 포트 매핑 필요 | 대부분의 경우. 컨테이너 격리가 필요할 때 |
| **host** | 컨테이너가 호스트의 네트워크를 그대로 사용. 포트 매핑 불필요 | 네트워크 성능이 극도로 중요한 경우 (오버헤드 약 1~3% 감소) |
| **사용자 정의 bridge** | 직접 만든 브리지 네트워크. 같은 네트워크의 컨테이너끼리 이름으로 통신 가능 | 실무에서 가장 권장. 서비스 간 통신에 사용 |

**왜 Host 방식보다 사용자 정의 bridge인가?**
Host 방식을 쓰면 포트 매핑이 생략되어 편해 보이지만, 동일한 애플리케이션(예: 내부 포트가 8080인 Spring Boot)을 여러 개 띄울 때 호스트의 8080 포트를 서로 차지하려다 충돌이 발생한다. 또한 호스트 네트워크 전체에 접근 가능해지므로 보안상 취약해진다. 반면 사용자 정의 bridge를 사용하면 컨테이너별로 독립된 가상 방음벽이 생겨 포트 충돌이 없고 컨테이너 확장에 유리하다.

여기서 **사용자 정의 bridge**가 핵심이다. 기본 bridge 네트워크에서는 컨테이너 간 통신 시 IP를 직접 써야 한다. 문제는 컨테이너를 재시작하면 IP가 바뀔 수 있다는 것이다. 사용자 정의 bridge를 만들고 컨테이너들을 같은 네트워크에 연결하면, **도커 엔진에 내장된 자체 DNS 서버가 해당 컨테이너의 가상 IP(예: 172.20.0.2)와 컨테이너 이름을 자동 매핑**해 준다. 즉, Spring Boot 설정에서 DB 호스트를 172.17.0.3이 아니라 `mysql-container`라고 쓸 수 있다. IP가 바뀌어도 내장 DNS가 즉각 업데이트해주므로 통신이 유지된다.

#### 포트 매핑 — 외부와 내부를 연결하는 문

컨테이너 내부의 포트를 외부에서 접근하려면 **포트 매핑**이 필요하다. "호스트의 8080 포트로 들어오는 트래픽을 컨테이너의 3000 포트로 전달해라"는 식이다.

| 매핑 형태 | 의미 | 보안 관점 |
|-----------|------|-----------|
| 0.0.0.0:8080:3000 | 모든 인터페이스의 8080을 컨테이너 3000으로 | 외부에서 접근 가능 (보안그룹으로 제어) |
| 127.0.0.1:8080:3000 | 로컬호스트의 8080만 컨테이너 3000으로 | 외부 접근 차단. Reverse Proxy를 통해서만 접근 |

**실무 포트 라우팅 표준 (Best Practice):**
최전방의 문지기 역할을 하는 Nginx 컨테이너만 EC2의 기본 웹 포트(80, 443)와 바인딩(`80:80`, `443:443`)하여 외부 트래픽을 받는다. 그 뒷단의 애플리케이션(Spring Boot, DB 등)은 아예 외부로 포트 매핑을 하지 않고, 사용자 정의 bridge 네트워크 내부에서 자신만의 고유한 내부 포트(예: 8080)를 열어둔 채 Nginx를 통해서만 트래픽을 전달받는다. 동일 컴포넌트를 여러 개(예: `react-container-1`, `react-container-2`) 띄우더라도 내부 포트 자체는 3000으로 동일하게 지정하며, Nginx가 이 여러 컨테이너 사이에서 로드 밸런싱을 수행한다.

### 3. Reverse Proxy — 교통 경찰

Reverse Proxy는 클라이언트의 요청을 받아서, 뒤에 있는 적절한 서버(컨테이너)로 전달하는 중간 계층이다. L7(애플리케이션 계층)에서 동작하는 소프트웨어로, 위에서 설명한 Docker 네트워크 모드(L3~L4 수준)와는 계층이 다르며 모든 네트워크 모드 위에서 결합해 사용될 수 있다. "Reverse"라는 이름은 일반 프록시(클라이언트 측)의 반대편, 즉 서버 측에서 동작한다는 뜻이다.

#### Forward Proxy vs Reverse Proxy

| 구분 | Forward Proxy | Reverse Proxy |
|------|---------------|---------------|
| 위치 | 클라이언트 앞 | 서버 앞 |
| 목적 | 클라이언트의 신원을 숨김, 접근 제어 | 서버의 구조를 숨김, 부하 분산, TLS 종료 |
| 누가 존재를 아는가 | 클라이언트가 프록시를 알고 설정 | 클라이언트는 모름. 서버인 줄 앎 |
| 예시 | 회사 방화벽, VPN | Nginx, Traefik, ALB |

단일 EC2에서 Reverse Proxy가 해결하는 문제는 명확하다.

**문제 1 — 포트 충돌 및 라우팅 분기:** 하나의 EC2에서 80포트를 쓸 수 있는 프로세스는 하나뿐이다. API 서버도 80을 쓰고 싶고, 클라이언트 앱도 80을 쓰고 싶다면? Nginx 같은 Reverse Proxy가 80포트를 단독으로 열어두고, HTTP 데이터에 포함된 도메인(Host 헤더)이나 URL 경로를 분석해서 각 요청에 맞는 내부 컨테이너로 알아서 분기해준다.

**문제 2 — TLS 종료:** 각 컨테이너마다 SSL 인증서를 설정하는 것은 관리 부담이다. Reverse Proxy에서 TLS를 한번에 처리하고(TLS Termination), 내부 컨테이너로는 평문 HTTP로 전달하면 인증서 관리가 한 곳으로 집중된다.

**문제 3 — 무중단 전환:** 새 버전을 배포할 때, Reverse Proxy의 설정만 바꿔서 트래픽을 신규 컨테이너로 보내면 된다. 구버전 컨테이너를 즉시 내릴 필요 없이, 요청이 빠진 후 안전하게 제거할 수 있다.

#### Nginx vs Traefik — 대표적인 선택지

| 항목 | Nginx | Traefik |
|------|-------|---------|
| 설정 방식 | 정적 설정 파일 (변경 시 reload 필요) | 동적 설정 (Docker 라벨 기반 자동 감지) |
| TLS 인증서 | 수동 또는 certbot 연동 | Let's Encrypt 자동 갱신 내장 |
| 성능 | 매우 높음. 동시 연결 수만 개 처리 가능 | Nginx 대비 약간 낮지만 실무에서 충분 |
| 학습 곡선 | 설정 문법을 익혀야 함 | Docker 환경에서는 진입 장벽이 낮음 |
| 적합한 상황 | 고성능 필요, 세밀한 제어 | 컨테이너 환경에서 빠른 구성, 자동화 선호 |

단일 EC2에서 컨테이너 몇 개를 운영하는 수준이라면 둘 다 충분하다. Nginx는 동시 접속 10,000개 이상도 문제없이 처리하며, Traefik은 컨테이너가 뜨고 내릴 때 자동으로 라우팅을 업데이트하는 편의성이 강점이다.

### 4. dev/prod 라우팅 전략 — 하나의 EC2에서 환경 분리

예산이 넉넉하지 않은 초기 프로젝트에서는 하나의 EC2에 개발(dev)과 운영(prod) 환경을 함께 올리기도 한다. 이때 라우팅 전략은 크게 세 가지다.

#### 전략 1: 서브도메인 기반 분리

| 요청 도메인 | 라우팅 대상 |
|------------|------------|
| api.example.com | prod Spring Boot 컨테이너 (내부 포트 8080) |
| dev-api.example.com | dev Spring Boot 컨테이너 (내부 포트 8081) |

Reverse Proxy가 Host 헤더를 보고 분기한다. 가장 깔끔한 방식이지만, 도메인 설정과 TLS 인증서 관리가 필요하다. 와일드카드 인증서(*.example.com)를 사용하면 서브도메인 추가 시 인증서를 새로 발급할 필요가 없다.

#### 전략 2: 경로(Path) 기반 분리

| 요청 경로 | 라우팅 대상 |
|----------|------------|
| /api/v1/* | prod 컨테이너 |
| /dev/api/v1/* | dev 컨테이너 |

별도 도메인이 필요 없어 간편하지만, 애플리케이션에서 경로 prefix를 인식해야 하는 번거로움이 있다. Spring Boot의 context-path 설정으로 대응 가능하나, 프론트엔드 연동 시 경로 혼선이 생길 수 있다.

#### 전략 3: 포트 기반 분리

| 호스트 포트 | 라우팅 대상 |
|------------|------------|
| 443 (HTTPS) | prod 컨테이너 |
| 8443 | dev 컨테이너 |

가장 단순하지만, 비표준 포트는 클라이언트가 명시적으로 포트를 붙여야 하므로(https://example.com:8443) 외부 서비스용으로는 적합하지 않다. 내부 개발·테스트 용도로만 사용한다.

#### 어떤 전략을 선택할 것인가

실무에서는 **서브도메인 기반**이 가장 권장된다. 환경 간 완전한 격리가 가능하고, 나중에 dev를 별도 EC2로 분리할 때도 DNS만 변경하면 되기 때문이다. 다만 진짜 중요한 원칙이 있다 — **prod와 dev를 같은 EC2에 두는 것은 어디까지나 비용 절감을 위한 타협이지, 좋은 아키텍처가 아니다.** dev 환경의 버그나 부하가 prod에 영향을 줄 수 있고, 보안 경계도 모호해진다. 가능한 한 빨리 환경을 물리적으로 분리하는 것이 목표여야 한다.

### 5. 전체 구조를 한눈에

단일 EC2 위에서의 전형적인 구성을 정리하면 이렇다.

외부 요청 → EC2 보안그룹(80/443 허용) → **Reverse Proxy 컨테이너**(Nginx/Traefik, 호스트 80/443 바인딩) → 사용자 정의 Docker 브리지 네트워크 → 각 애플리케이션 컨테이너(8080, 8081 등 내부 포트)

여기에 DB나 Redis는 같은 Docker 네트워크에 연결하되, 포트를 외부에 노출하지 않는다. 컨테이너 이름으로 접근하면 되고, 외부에서 직접 접속할 이유가 없기 때문이다.

MySQL 컨테이너의 3306 포트를 호스트에 매핑하는 것은 개발 편의를 위한 것이지, 운영 환경에서는 보안 위험이다. 운영에서는 SSH 터널이나 VPN을 통해서만 DB에 접근해야 한다.

## 시나리오

### 시나리오 1: 컨테이너에서 같은 EC2의 DB에 접속할 수 없다

**상황:** Spring Boot 앱을 Docker 컨테이너로 올리고, 같은 EC2에서 Docker로 실행 중인 MySQL에 접속하려 한다. application.yml에 DB 호스트를 localhost:3306으로 설정했다. 그런데 "Connection refused" 에러가 발생한다.

**원인 분석:** 컨테이너 안에서 localhost는 호스트(EC2)가 아니라 컨테이너 자기 자신이다. Spring Boot 컨테이너의 localhost:3306에는 아무것도 없다. 이것은 Docker 네트워크의 격리 특성 때문이다. 각 컨테이너는 자신만의 네트워크 네임스페이스를 가지며, localhost는 그 네임스페이스 안의 루프백을 가리킨다.

**해결 방안:** 첫째, 두 컨테이너를 같은 사용자 정의 bridge 네트워크에 연결한다. 둘째, DB 호스트를 localhost가 아닌 **MySQL 컨테이너의 이름**(예: mysql-db)으로 변경한다. Docker 내장 DNS가 이름을 해당 컨테이너의 IP로 자동 해석한다. 이렇게 하면 MySQL 컨테이너가 재시작되어 IP가 바뀌더라도 이름 기반 통신은 영향을 받지 않는다.

### 시나리오 2: 두 컨테이너가 같은 포트를 사용해서 하나가 뜨지 않는다

**상황:** API 서버 컨테이너와 관리자 서버 컨테이너를 모두 호스트의 8080 포트에 매핑하려 했다. 첫 번째 컨테이너는 정상 실행되지만, 두 번째 컨테이너를 실행하면 "port is already allocated" 에러가 발생한다.

**원인 분석:** 하나의 호스트 포트에는 하나의 프로세스(또는 컨테이너)만 바인딩할 수 있다. 이건 OS 수준의 제약이다. 컨테이너 내부에서는 각각 독립된 네트워크 네임스페이스를 사용하므로 둘 다 내부적으로 8080을 써도 문제없지만, 호스트 포트에 매핑하는 순간 충돌이 생긴다.

**해결 방안:** 첫째, 각 컨테이너를 다른 호스트 포트에 매핑한다(예: API는 8080, 관리자는 8081). 둘째, 더 나은 방법은 **Reverse Proxy를 도입**하는 것이다. Nginx나 Traefik만 호스트의 80/443에 바인딩하고, 각 컨테이너는 호스트 포트 매핑 없이 Docker 네트워크 안에서만 통신한다. Reverse Proxy가 도메인이나 경로를 보고 적절한 컨테이너로 요청을 전달하면, 포트 충돌 문제 자체가 사라진다.

### 시나리오 3: HTTPS 적용 후 "리다이렉트 루프" 에러

**상황:** Nginx를 Reverse Proxy로 두고, HTTP → HTTPS 리다이렉트를 설정했다. 그런데 브라우저에서 접속하면 "ERR_TOO_MANY_REDIRECTS" 에러가 발생한다.

**원인 분석:** Reverse Proxy 앞에 AWS ALB나 Cloudflare 같은 계층이 하나 더 있는 경우에 자주 발생한다. 흐름을 따라가보면 이렇다: 클라이언트 →(HTTPS)→ ALB →(HTTP)→ Nginx. ALB가 TLS를 종료하고 Nginx에는 HTTP로 전달한다. Nginx는 "HTTP 요청이 들어왔으니 HTTPS로 리다이렉트해야지"라고 판단한다. 클라이언트가 HTTPS로 다시 요청하면, ALB가 또 HTTP로 바꿔서 Nginx에 전달하고, Nginx가 또 리다이렉트하고... 이것이 무한 루프다.

**해결 방안:** Nginx에서 리다이렉트 판단 시 클라이언트의 원래 프로토콜을 기준으로 해야 한다. ALB는 원래 프로토콜을 X-Forwarded-Proto 헤더에 담아 보내므로, Nginx는 이 헤더가 http일 때만 리다이렉트하도록 조건을 수정한다. 또는 TLS 종료를 ALB에서만 수행하고, Nginx에서는 HTTPS 리다이렉트 설정을 제거하는 방법도 있다. 핵심은 **TLS 종료 지점을 하나로 통일**하는 것이다.
