# Day 01. TCP/IP — 데이터는 어떻게 목적지까지 도달하는가  

> **시리즈:** 클라우드/네트워크/인프라 실무 지식 · Phase 1 네트워크 기초 & 실무
> **예상 읽기 시간:** 12분

---

## 오늘의 핵심 요약

**TCP/IP**는 인터넷 통신의 근간이 되는 프로토콜 스택이다. 데이터는 애플리케이션 → 전송 → 인터넷 → 네트워크 접근 계층을 거치며 **캡슐화**되어 전송되고, 수신 측에서 역순으로 **디캡슐화**되어 원본 데이터로 복원된다.

**TCP**는 연결 수립(3-way handshake)을 통해 신뢰성을 보장하고, **IP**는 패킷이 올바른 목적지에 도달하도록 주소 체계와 라우팅을 담당한다. 실무에서는 이 구조를 이해해야 "연결은 되는데 응답이 느린" 상황, "특정 포트만 접근 불가인" 상황의 원인을 계층별로 분리해 진단할 수 있다.

---

## 왜 이걸 알아야 하는가

서버를 운영하다 보면 "서비스가 안 됩니다"라는 보고를 받는다. 이때 가장 먼저 해야 할 일은 **문제가 어느 계층에서 발생했는지 분리하는 것**이다. 네트워크 자체가 끊긴 건지, TCP 연결은 되는데 애플리케이션이 응답을 못 하는 건지, DNS가 잘못 풀리는 건지 — 이 판단의 기반이 되는 것이 TCP/IP 계층 구조다.

이건 단순한 이론이 아니다. 장애 상황에서 "일단 서버 재시작"이 아닌, 근거 있는 진단을 할 수 있느냐의 차이를 만든다.

---

## 핵심 개념

### TCP/IP 4계층 — OSI 7계층의 실무 버전

학교에서 배우는 OSI 7계층은 참조 모델이고, 실제 인터넷은 **TCP/IP 4계층**으로 동작한다. 대응 관계를 잡아두면 이해가 빠르다.



| TCP/IP 계층 | 역할 | OSI 대응 | 대표 프로토콜 |
| :--- | :--- | :--- | :--- |
| **애플리케이션** | 사용자가 접하는 서비스 | 5~7계층 | HTTP, DNS, SSH, FTP |
| **전송(Transport)** | 프로세스 간 통신, 신뢰성 | 4계층 | TCP, UDP |
| **인터넷(Internet)** | 호스트 간 라우팅 | 3계층 | IP, ICMP, ARP |
| **네트워크 접근** | 물리적 전송 | 1~2계층 | Ethernet, Wi-Fi |

핵심은 **각 계층이 자기 역할만 책임진다**는 것이다. TCP는 데이터가 순서대로 빠짐없이 도착하는 것만 신경 쓰고, IP는 패킷이 목적지 주소에 도달하는 것만 신경 쓴다. HTTP는 그 위에서 "이 요청은 GET이고, 응답은 200이다"라는 의미를 부여한다.

### 캡슐화와 디캡슐화 — 택배의 포장과 개봉

데이터가 네트워크를 통해 전달되는 과정은 택배와 비슷하다.

보내는 쪽에서는 각 계층을 지날 때마다 **헤더(header)** 를 하나씩 붙인다. 애플리케이션 데이터에 TCP 헤더가 붙고(세그먼트), 거기에 IP 헤더가 붙고(패킷), 다시 이더넷 헤더가 붙는다(프레임). 이걸 **캡슐화**라고 한다.



받는 쪽에서는 역순으로 헤더를 하나씩 벗겨낸다. 이더넷 헤더를 보고 "이건 내 MAC 주소가 맞다", IP 헤더를 보고 "내 IP가 맞다", TCP 헤더를 보고 "80번 포트로 가는 거구나", 그래서 최종적으로 웹 서버 프로세스에 HTTP 요청 데이터가 도달한다.

이 과정이 왜 중요하냐면, **장애 진단이 결국 "어느 계층의 헤더 처리에서 문제가 생겼는가"를 찾는 일**이기 때문이다.

### TCP 3-way Handshake — 신뢰할 수 있는 연결의 시작

TCP가 UDP와 다른 가장 큰 특징은 데이터를 보내기 전에 먼저 **연결을 수립**한다는 것이다.



1.  **1단계 (SYN):** 클라이언트가 서버에게 "통신하자"라는 신호를 보낸다. 이때 자신의 시퀀스 번호를 함께 전달한다.
2.  **2단계 (SYN-ACK):** 서버가 "좋다, 나도 준비됐다"라고 응답하면서, 클라이언트의 시퀀스 번호를 확인했다는 ACK과 자신의 시퀀스 번호를 함께 보낸다.
3.  **3단계 (ACK):** 클라이언트가 서버의 시퀀스 번호를 확인했다는 ACK을 보낸다. 이 시점부터 양쪽 모두 데이터를 주고받을 수 있다.

이 3단계가 완료되어야 비로소 "연결됐다(ESTABLISHED)"고 말할 수 있다. 여기서 중요한 실무적 포인트가 있다. 만약 **2단계에서 멈춰 있다면**, 서버의 방화벽이 SYN 패킷을 받았지만 응답을 차단하고 있을 가능성이 높다. **1단계에서 아예 반응이 없다면**, 라우팅 자체가 안 되고 있거나 서버가 다운된 상태다.

### 포트 번호 — 같은 IP에서 여러 서비스를 구분하는 방법

IP 주소가 "어느 컴퓨터"를 지정한다면, 포트 번호는 "그 컴퓨터의 어느 프로세스"를 지정한다. 하나의 서버에서 웹 서비스(80), SSH(22), DB(3306)가 동시에 돌아갈 수 있는 이유다.

포트 범위는 세 구간으로 나뉜다.

* **0~1023 (Well-known):** HTTP(80), HTTPS(443), SSH(22) 등 표준 서비스용. 일반 사용자 권한으로 바인딩할 수 없다.
* **1024~49151 (Registered):** MySQL(3306), PostgreSQL(5432), Redis(6379) 등 알려진 애플리케이션용.
* **49152~65535 (Dynamic/Ephemeral):** 클라이언트가 서버에 접속할 때 OS가 자동으로 할당하는 임시 포트.

실무에서 자주 놓치는 부분이 **Ephemeral 포트 고갈** 문제다. 대량의 짧은 연결을 반복하는 서비스에서, 사용 가능한 임시 포트가 바닥나면 새로운 연결이 불가능해진다.

### TCP 연결 종료 — 4-way Handshake와 TIME_WAIT

연결을 맺는 것도 중요하지만, 끊는 과정도 실무에서 매우 중요하다. TCP 연결 종료는 4단계를 거친다.



1.  **1단계 (FIN):** 한쪽이 "나는 더 보낼 데이터가 없다"고 FIN을 보낸다.
2.  **2단계 (ACK):** 상대방이 이를 확인한다.
3.  **3단계 (FIN):** 상대방도 "나도 끝"이라며 FIN을 보낸다.
4.  **4단계 (ACK):** 최초 FIN을 보낸 쪽이 이를 확인한다.

여기서 핵심은 **마지막 ACK을 보낸 쪽이 즉시 연결을 닫지 않는다**는 것이다. **TIME_WAIT** 상태로 일정 시간(보통 60초) 대기한다. 왜냐하면, 마지막 ACK이 네트워크에서 유실되었을 때 상대방이 FIN을 재전송할 수 있고, 이를 처리해야 하기 때문이다.

## 시나리오 1: "서버는 살아있는데, 특정 서비스만 접근이 안 됩니다"

### 상황
운영 중인 서버에 SSH(22번 포트)로는 정상 접속되는데, 웹 서비스(443번 포트)에만 접근이 안 된다는 보고가 들어왔다. 서버 자체는 ping도 되고, 다른 포트의 서비스도 정상이다.

### 원인 분석 — 계층별로 올라가며 진단
* **네트워크/IP 계층은 정상인가?** SSH가 되고 ping이 된다는 건, IP 레벨에서 서버까지의 경로는 살아있다는 뜻이다. 3계층 이하는 문제에서 제외할 수 있다.
* **전송 계층(TCP)은 정상인가?** 443번 포트로 TCP 연결 시도 시 어떤 반응이 오는지가 핵심이다.
    * **아무 응답이 없다(타임아웃):** 방화벽이 해당 포트의 패킷을 DROP하고 있을 가능성이 높다.
    * **즉시 "Connection Refused":** 서버까지 패킷이 도달했지만, 해당 포트에서 리스닝하는 프로세스가 없다는 뜻이다.
* **애플리케이션 계층은 정상인가?** TCP 연결이 되는데 응답이 없다면, 웹 서버의 프로세스 상태, 설정 파일, 인증서(TLS) 문제를 확인해야 한다.

### 해결 방안
가장 흔한 원인은 **방화벽 규칙 누락**이다. 서버 OS의 방화벽이나 클라우드 보안 그룹(Security Group)에서 443 포트가 열려있는지 확인한다.

## 시나리오 2: "갑자기 새로운 연결이 안 맺어집니다"

### 상황
트래픽이 많은 API 서버에서 어느 순간부터 새로운 요청이 처리되지 않는다. 기존에 연결된 세션은 잘 동작하는데, 새 연결만 실패한다.

### 원인 분석
* **TIME_WAIT 소켓 과다 축적:** 짧은 연결을 대량으로 반복할 때, 사용 가능한 임시 포트 범위를 전부 소진하면 새 연결을 맺을 포트가 없다.
* **리슨 큐(Listen Queue) 포화:** 서버 프로세스가 연결을 accept하는 속도보다 요청이 빠르게 들어와 큐(backlog)가 가득 차면 새로운 SYN 패킷을 무시한다.

### 해결 방안
* **TIME_WAIT 문제:** 근본적인 해결은 **커넥션 풀링(Connection Pooling)** 이다. 매번 새 연결을 맺고 끊는 대신 미리 만들어둔 연결을 재사용한다.
* **리슨 큐 포화:** 백로그(backlog) 크기를 늘리거나, 애플리케이션 레벨의 병목을 찾아 해결한다.

---

## 시나리오 3: "연결은 되는데 응답이 너무 느립니다"

### 상황
웹 서비스의 응답 시간이 평소 200ms에서 갑자기 3~5초로 늘어났다. 모든 요청이 느리다.

### 원인 분석
* **네트워크 경로상의 지연:** 패킷이 가는 경로의 라우터/스위치 과부하.
* **TCP 재전송(Retransmission):** 네트워크 품질 저하로 패킷 손실 시, TCP의 **지수 백오프(Exponential Backoff)** 로 인해 지연이 급격히 증가한다.
* **애플리케이션 레벨 병목:** DB 쿼리 지연, 외부 API 호출 타임아웃 대기 등.

### 해결 방안
진단의 첫 단계는 **지연이 네트워크에서 발생하는지, 서버 내부에서 발생하는지 구분**하는 것이다. 네트워크 RTT(Round Trip Time)가 정상이라면 문제는 서버 내부(애플리케이션)에 있다.
