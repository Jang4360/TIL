# 레이턴시가 처리량을 무너뜨리는 이유

## 1. 이 주제가 중요한 이유

백엔드 장애는 항상 에러 로그로 먼저 드러나지 않는다. 실무에서 더 위험한 장애는 “실패”보다 “느림”으로 시작된다. 요청은 실패하지 않고 응답도 오지만, p95와 p99가 길어지면서 스레드, 커넥션, 큐, CPU, DB 세션이 점점 오래 점유된다. 이 상태가 지속되면 시스템은 일을 더 많이 해서 무너지는 것이 아니라, **기다리는 요청이 쌓여서 무너진다.**

레이턴시를 단순히 “응답 시간이 느리다” 정도로 보면 문제를 늦게 본다. 레이턴시는 자원 점유 시간이다. API 하나가 50ms에 끝나면 같은 자원으로 더 많은 요청을 처리할 수 있지만, 500ms를 붙잡으면 같은 트래픽에서도 필요한 동시 처리량이 10배로 늘어난다. 그래서 레이턴시는 사용자 경험 지표이면서 동시에 시스템 용량 지표다.

일반적인 감각을 잡으면 다음과 같다.

| 구간 | 대략적인 지연 감각 |
|---|---:|
| 메모리 접근 | ns 단위 |
| 로컬 디스크/SSD 접근 | μs~ms 단위 |
| DB 단순 쿼리 | 1~10ms |
| 내부 네트워크 왕복 | 1~10ms |
| 외부 API 호출 | 50~300ms 이상 |
| 장애 상황의 외부 API p99 | 1~3초 이상 |

문제는 이 값들이 평균으로 움직이지 않는다는 점이다. 평시 p50은 80ms로 안정적이어도, 피크 시간대 p99가 2초로 튀면 시스템 전체 자원 점유가 급격히 늘어난다. 평균만 보면 “괜찮다”고 판단하지만, 실제 사용자는 일부 요청에서 멈춤을 경험하고, 서버는 tail latency 때문에 큐가 늘어난다.

> 레이턴시는 단순한 시간 지표가 아니라, 시스템이 자원을 얼마나 오래 붙잡는지 보여주는 지표다.

> 💡 **p50은 평시 효율을 보여주고, p99는 장애 가능성을 보여준다.**  
> 백엔드 운영에서는 평균보다 tail latency를 먼저 읽어야 한다.

## 2. 레이턴시는 왜 처리량과 연결되는가

처리량은 단순히 서버 스펙으로 결정되지 않는다. 같은 서버라도 요청 하나가 자원을 얼마나 오래 점유하는지에 따라 처리 가능한 요청 수가 달라진다. 이 관계를 가장 직관적으로 설명하는 법칙이 Little’s Law다.

~~~text
L = λW
~~~

- L: 시스템 안에 동시에 존재하는 요청 수
- λ: 초당 유입 요청 수
- W: 요청 하나가 시스템 안에 머무는 시간

예를 들어 초당 200개의 요청이 들어오고, 요청 하나가 평균 50ms 동안 처리된다면 필요한 동시 처리량은 다음과 같다.

~~~text
L = 200 * 0.05 = 10
~~~

즉, 동시에 약 10개의 요청을 감당하면 된다. 그런데 외부 API 지연, DB lock wait, 커넥션 풀 대기 때문에 요청 시간이 300ms로 늘면 상황이 바뀐다.

~~~text
L = 200 * 0.3 = 60
~~~

트래픽은 그대로인데 필요한 동시 처리량이 6배가 된다. 여기서 스레드 풀, DB 커넥션 풀, HTTP 커넥션 풀, 큐 크기가 충분하지 않으면 요청은 대기열로 밀린다. 그리고 대기열이 생기면 W가 다시 늘어난다. W가 늘면 L이 늘고, L이 늘면 대기가 더 늘어난다. 이 순환이 포화다.

> 💡 트래픽이 늘지 않아도 장애가 날 수 있다.  
> 요청 수가 아니라 **요청 체류 시간**이 늘면 시스템 안의 동시 요청 수가 증가한다.

그래서 실무에서 “요청이 몇 개 들어오느냐”만 보면 부족하다. 반드시 “요청이 얼마나 오래 머무느냐”를 같이 봐야 한다. 서버가 무너지는 시점은 대개 CPU 100%가 아니라, in-flight 요청 수와 pending queue가 계단식으로 증가하는 지점이다.

## 3. 평균 레이턴시가 위험한 이유

평균은 장애를 숨긴다. 예를 들어 100개의 요청 중 95개가 50ms에 끝나고, 5개가 2초 걸린다고 하자. 평균은 비교적 낮게 보일 수 있지만, 실제 운영에서는 2초 걸리는 요청이 더 중요하다. 그 요청들이 스레드와 커넥션을 오래 점유하면서 다음 요청의 대기 시간을 늘리기 때문이다.

그래서 백엔드에서는 보통 다음 지표를 분리해서 본다.

| 지표 | 의미 | 실무 해석 |
|---|---|---|
| p50 | 절반의 요청이 이 시간 안에 끝남 | 평시 효율 |
| p95 | 대부분의 요청 경험 | 일반 사용자 체감 |
| p99 | 최악 구간의 요청 경험 | 포화와 장애 가능성 |
| max | 극단값 | 단독으로 판단하면 노이즈 가능성 있음 |

p50이 안정적인데 p99만 먼저 튀는 경우가 많다. 이때 “아직 평균은 괜찮다”고 판단하면 늦다. p99 악화는 보통 일부 요청이 특정 자원을 오래 붙잡기 시작했다는 신호다. 그 자원이 DB 커넥션이면 풀 대기가 생기고, 외부 API 커넥션이면 HTTP client pool이 막히고, 스레드면 애플리케이션 전체 처리량이 떨어진다.

> 💡 p99가 먼저 무너지고, 그다음 p95가 올라오고, 마지막에 p50이 따라온다.  
> p50까지 나빠졌다면 이미 장애가 상당히 전파된 상태다.

## 4. 레이턴시는 어디서 쌓이는가

실무 API의 레이턴시는 한 지점에서만 생기지 않는다. 요청 하나는 여러 구간을 지나며 시간을 쓴다.

~~~text
Client
  → Gateway / Load Balancer
  → Application Thread
  → Controller
  → Service
  → Transaction
  → DB Connection Acquire
  → Query Execution
  → External API Call
  → Serialization
  → Response
~~~

이 중 실제 계산 시간보다 대기 시간이 더 큰 경우가 많다. 예를 들어 CPU가 열심히 연산해서 느린 것이 아니라, 다음과 같은 대기 때문에 느려진다.

- DB 커넥션을 얻기 위한 대기
- lock이 풀리기를 기다리는 대기
- 외부 API 응답 대기
- HTTP connection pool 대기
- thread pool queue 대기
- GC pause로 인한 정지
- downstream timeout까지 기다리는 대기
- retry backoff 또는 즉시 재시도에 따른 누적 대기

따라서 “API가 느리다”는 말은 정확한 진단이 아니다. 실무에서는 반드시 다음처럼 쪼개야 한다.

~~~text
전체 응답 시간 = 실행 시간 + 대기 시간 + 네트워크 시간 + 큐잉 시간
~~~

좋은 장애 분석은 “어디가 느린가?”가 아니라 “어디서 기다리고 있는가?”를 찾는 것이다.

> 💡 성능 문제의 핵심은 느린 코드가 아닐 수 있다.  
> 대부분의 장애는 **대기 위치를 잘못 설계한 결과**로 커진다.

## 5. DB 커넥션 풀 고갈과 레이턴시 전파

DB 커넥션 풀은 단순히 연결 재사용을 위한 최적화 장치가 아니다. 실무에서는 DB로 들어가는 동시성을 제한하는 보호 장치다. 풀 크기가 30이면 동시에 DB를 사용할 수 있는 요청은 30개다. 나머지는 커넥션을 얻기 위해 기다린다.

문제는 쿼리 시간이 아니라 커넥션 점유 시간이다. 쿼리 자체는 5ms에 끝나도, 트랜잭션 안에서 외부 API를 호출하거나 대용량 응답 변환을 수행하면 커넥션을 300ms, 1초씩 붙잡을 수 있다. DB는 일하지 않는데 커넥션은 반납되지 않는다.

예를 들어 평시에는 다음과 같다고 하자.

~~~text
유입률: 200 rps
커넥션 점유 시간: 50ms
필요 커넥션 수: 200 * 0.05 = 10
~~~

풀 크기가 30이면 여유가 있다. 그런데 트랜잭션 안에서 외부 API 지연이 발생해 점유 시간이 300ms가 되면 다음과 같이 바뀐다.

~~~text
필요 커넥션 수: 200 * 0.3 = 60
~~~

풀 크기 30을 초과한다. 이때부터 요청은 DB 앞에서 줄을 선다. 사용자는 “API가 느리다”고 느끼지만, 실제 쿼리 실행 시간은 여전히 짧을 수 있다. 병목은 query execution이 아니라 connection acquire이다.

> 💡 “DB query는 빠른데 API가 느리다”는 패턴은 커넥션 풀 대기를 의심해야 한다.

실무에서 봐야 할 지표는 다음이다.

| 지표 | 의미 | 위험 신호 |
|---|---|---|
| pool active | 사용 중인 커넥션 수 | max에 붙어서 내려오지 않음 |
| pool idle | 쉬고 있는 커넥션 수 | 0 근처 유지 |
| acquire time | 커넥션 획득 대기 시간 | p95가 두 자릿수 ms 이상으로 상승 |
| pending threads | 커넥션을 기다리는 요청 수 | 계단식 증가 |
| query time | 실제 SQL 실행 시간 | 낮은데 API가 느리면 풀 대기 가능성 |
| transaction duration | 트랜잭션 전체 시간 | query time보다 훨씬 길면 범위 문제 |

여기서 중요한 점은 풀 크기를 바로 늘리는 것이 정답이 아니라는 점이다. 풀을 늘리면 애플리케이션 대기는 줄 수 있지만, DB가 감당하지 못하면 DB 내부 lock wait, IO wait, CPU 사용률이 올라간다. 그러면 tail latency가 다시 튄다.

풀 고갈 대응 순서는 보통 다음과 같다.

~~~text
1. acquire time과 pending threads로 풀 포화 확인
2. 트랜잭션 범위 확인
3. 커넥션 점유 시간이 긴 경로 제거
4. 외부 API 호출을 트랜잭션 밖으로 분리
5. lock wait와 slow query 확인
6. timeout/retry 정책 조정
7. 마지막으로 pool size와 DB capacity 조정
~~~

> 💡 풀 크기 증설은 병목 위치를 확인한 뒤에 해야 한다.  
> 앱 큐를 DB 내부 큐로 옮기는 것뿐이면 장애는 다른 형태로 재발한다.

## 6. 외부 API 지연과 retry storm

외부 API에 의존하는 서비스에서는 장애가 실패보다 느림으로 먼저 시작된다. 외부 API p99가 300ms에서 2초로 튀면, 상류 애플리케이션은 timeout 직전까지 스레드와 커넥션을 붙잡는다. 여기에 retry를 넣으면 한 사용자 요청이 여러 개의 하류 요청으로 증폭된다.

예를 들어 정책이 다음과 같다고 하자.

~~~text
timeout: 800ms
retry: 즉시 2회
~~~

사용자 요청 1건은 최대 3개의 외부 API 호출로 바뀐다.

~~~text
원 요청 1회 + retry 2회 = 최대 3회
~~~

평시에는 성공률을 올리는 것처럼 보일 수 있다. 그러나 하류가 이미 느려진 상태에서는 재시도가 복구가 아니라 부하 증폭이 된다. 하류 입장에서는 처리해야 할 요청이 늘고, 상류 입장에서는 기다리는 요청이 늘어난다. 결국 양쪽 모두 queue가 길어진다.

> 💡 재시도는 신뢰성 도구이지만, 포화 상태에서는 부하 증폭기다.

특히 위험한 것은 즉시 retry다. 여러 인스턴스가 같은 timeout 기준으로 동시에 실패하고, 동시에 재시도하면 트래픽 파동이 생긴다. 이 현상을 retry storm이라고 볼 수 있다.

이를 줄이기 위해 사용하는 기본 조합은 다음이다.

~~~text
제한된 retry 횟수
+ exponential backoff
+ jitter
+ retry budget
+ circuit breaker
~~~

각각의 목적은 다르다.

| 기법 | 목적 | 핵심 |
|---|---|---|
| retry limit | 증폭 상한 제한 | 요청 1건이 몇 배까지 늘어나는지 통제 |
| exponential backoff | 하류 회복 시간 확보 | 즉시 재공격 방지 |
| jitter | 동시 재시도 분산 | 재시도 스파이크 완화 |
| retry budget | 전체 재시도 총량 제한 | 선의의 self-DDoS 방지 |
| circuit breaker | 빠른 실패 전환 | 포화 전이 차단 |

retry budget은 특히 중요하다. 예를 들어 원 요청 대비 retry 요청이 20%를 넘지 않도록 제한하면, 장애 중에도 하류 시스템이 회복할 여지를 가진다. 반대로 retry budget이 없으면 모든 상류 서비스가 “성공률을 높이기 위해” 재시도하면서 하류를 계속 두드린다.

> 💡 retry 성공률만 KPI로 보면 위험하다.  
> retry 후 성공이 늘어도 전체 p99, in-flight, queue depth가 나빠지면 운영 관점에서는 실패다.

## 7. timeout은 짧을수록 좋은가

timeout은 짧다고 좋은 것도 아니고, 길다고 안정적인 것도 아니다. timeout은 실패를 감지하는 장치이면서 동시에 자원 점유 시간을 제한하는 장치다.

너무 짧은 timeout은 정상 요청까지 실패로 만든다. 예를 들어 외부 API p95가 400ms인데 timeout을 300ms로 잡으면 정상적으로 성공할 요청도 실패한다. 이 상태에서 retry가 걸리면 불필요한 재시도량이 늘어난다.

반대로 너무 긴 timeout은 실패 감지를 늦춘다. 외부 API가 사실상 멈춘 상태인데 5초까지 기다리면, 상류 애플리케이션은 그동안 스레드와 커넥션을 붙잡고 있다. 요청이 쌓이면 시스템 전체가 느려진다.

따라서 timeout은 하나의 전역 값으로 두면 안 된다. 호출의 성격에 따라 달라야 한다.

| 호출 유형 | 예시 | timeout 전략 |
|---|---|---|
| 필수 DB 조회 | 로그인, 결제 상태 확인 | 짧고 명확하게 |
| 필수 외부 API | 경로 계산, 인증 검증 | SLA 안에서 제한적으로 |
| 부가 정보 API | 추천, 혼잡도, 배너 | 짧게 실패 후 fallback |
| 비동기 처리 | 알림, 로그, 통계 | 사용자 응답 경로에서 분리 |

중요한 것은 전체 SLA 예산이다. 사용자가 2초 안에 응답을 받아야 한다면, 내부 로직, DB, 외부 API, retry 시간을 모두 합쳐도 2초를 넘으면 안 된다.

~~~text
Client SLA 2s
= Gateway 100ms
+ App Logic 200ms
+ DB 300ms
+ External API 800ms
+ Buffer 600ms
~~~

여기에 retry를 넣으려면 retry까지 포함한 최악 경로가 SLA 안에 들어와야 한다. 그렇지 않으면 사용자는 이미 응답을 포기했는데 서버는 뒤늦게 성공한 응답을 처리하는 상황이 생긴다.

> 💡 timeout은 장애를 없애는 값이 아니라, 장애 전파 범위를 제한하는 값이다.

---

## 8. 트랜잭션 범위가 레이턴시에 미치는 영향

“트랜잭션은 짧게 가져가야 한다”는 말은 단순한 코드 스타일이 아니다. 트랜잭션이 길면 DB 커넥션 점유 시간, lock 보유 시간, rollback 비용, 장애 전파 범위가 모두 커진다.

위험한 구조는 다음과 같다.

~~~text
@Transactional
public void processOrder() {
    주문 조회
    재고 차감
    외부 결제 API 호출
    알림 API 호출
    응답 DTO 변환
}
~~~

이 구조에서는 외부 결제 API가 느려지는 동안 DB 트랜잭션과 커넥션이 계속 유지될 수 있다. 결제 API p99가 2초로 튀면 DB 커넥션도 2초 가까이 붙잡힌다. 이때 다른 요청은 커넥션을 얻지 못해 대기한다.

더 나은 구조는 트랜잭션 안에서 DB 정합성에 필요한 최소 작업만 수행하고, 외부 호출은 트랜잭션 밖으로 분리하는 것이다.

~~~text
1. 트랜잭션 시작
2. 주문 상태 변경
3. outbox 이벤트 저장
4. 트랜잭션 종료
5. 비동기로 외부 결제/알림 처리
~~~

물론 모든 외부 호출을 무조건 분리할 수는 없다. 결제 승인처럼 강한 일관성이 필요한 흐름도 있다. 다만 이 경우에도 트랜잭션 범위, timeout, 보상 트랜잭션, idempotency key, 상태 머신을 함께 설계해야 한다.

> 💡 트랜잭션 안에 느린 I/O를 넣는 것은 DB 커넥션을 외부 시스템 지연에 종속시키는 설계다.

실무에서는 다음 질문으로 트랜잭션 범위를 점검한다.

~~~text
이 작업이 반드시 같은 트랜잭션 안에 있어야 하는가?
외부 API 실패 시 DB 변경도 반드시 취소되어야 하는가?
상태를 PENDING으로 저장하고 비동기 확정할 수 있는가?
중복 요청이 들어오면 같은 결과를 반환할 수 있는가?
커넥션을 잡은 상태로 네트워크 I/O를 기다리고 있지는 않은가?
~~~

## 9. Headroom은 어떻게 판단하는가

headroom은 “서버가 아직 여유 있다”는 감각적인 표현이 아니다. 특정 장애 이벤트가 와도 포화되지 않을 수 있는 수치적 여유다.

예를 들어 다음 이벤트를 가정할 수 있다.

~~~text
외부 API p95: 200ms → 800ms
DB lock wait: 5ms → 100ms
GC pause: 200ms 발생
트래픽: 평시 대비 1.5배
retry rate: 원 요청 대비 20%
~~~

이 상황에서도 다음 지표가 임계치를 넘지 않아야 headroom이 있다고 말할 수 있다.

- p95/p99 latency가 SLA 안에 머무는가
- DB connection acquire time이 급등하지 않는가
- pending threads가 계단식으로 증가하지 않는가
- HTTP client pool이 고갈되지 않는가
- retry rate가 budget 안에 머무는가
- circuit breaker가 과도하게 열리지 않는가
- CPU보다 queue depth가 먼저 증가하지 않는가

headroom은 평균 CPU 사용률 40% 같은 단일 지표로 판단하면 안 된다. CPU가 낮아도 DB 커넥션 풀이 고갈되면 API는 멈춘다. CPU가 낮아도 외부 API 응답을 기다리는 스레드가 가득 차면 처리량은 떨어진다.

> 💡 CPU 여유가 곧 시스템 여유는 아니다.  
> I/O 기반 백엔드에서는 pool, queue, timeout, in-flight가 더 먼저 무너질 수 있다.

## 10. 관측은 어떻게 설계해야 하는가

레이턴시를 제대로 보려면 전체 응답 시간만 보면 부족하다. 요청 경로를 구간별로 나눠야 한다.

최소한 다음 지표를 수집해야 한다.

~~~text
HTTP server latency: endpoint별 p50/p95/p99
DB query latency: SQL 또는 repository 단위
DB connection acquire time
Transaction duration
External API latency: provider별 p50/p95/p99
Retry count / retry rate
Circuit breaker state
Thread pool active / queue size
Connection pool active / idle / pending
In-flight requests
Error rate by cause: timeout, connection refused, 5xx, pool exhausted
~~~

중요한 것은 같은 타임라인에 겹쳐 보는 것이다. p99가 오른 시점에 acquire time이 먼저 올랐는지, 외부 API p99가 먼저 올랐는지, retry rate가 먼저 올랐는지 순서를 봐야 한다.

예를 들어 다음 순서라면 외부 API 지연이 장애 시작점일 가능성이 높다.

~~~text
External API p99 상승
→ app in-flight 증가
→ thread pool active 증가
→ timeout 증가
→ retry rate 증가
→ downstream p99 추가 악화
~~~

반대로 다음 순서라면 DB 풀 포화 가능성이 높다.

~~~text
DB acquire time 상승
→ pending threads 증가
→ endpoint p99 상승
→ timeout 증가
→ retry rate 증가
→ 전체 API 지연
~~~

> 💡 장애 분석은 지표의 “값”보다 “순서”가 중요하다.  
> 무엇이 먼저 올랐는지 알아야 원인과 결과를 구분할 수 있다.

## 11. 실무 대응 순서

레이턴시 장애가 발생했을 때 무작정 서버를 늘리거나 timeout을 늘리면 원인을 가릴 수 있다. 실무에서는 보통 다음 순서로 접근한다.

### 1단계. 포화 지점을 확인한다

먼저 어느 큐가 길어졌는지 본다.

~~~text
DB connection pool인가?
HTTP client pool인가?
Thread pool인가?
Message queue인가?
Load balancer 앞단인가?
Downstream API인가?
~~~

이때 endpoint p99, in-flight, pool pending, acquire time을 같이 본다.

### 2단계. 증폭 경로를 차단한다

장애 중에는 성공률을 높이는 것보다 시스템 생존이 우선이다. retry가 증폭을 만들고 있다면 즉시 제한한다.

~~~text
retry 횟수 축소
즉시 retry 제거
backoff + jitter 적용
retry budget 적용
circuit breaker threshold 조정
부가 기능 fallback 처리
~~~

### 3단계. 점유 시간을 줄인다

Little’s Law 기준으로 W를 낮추는 작업이다.

~~~text
트랜잭션 범위 단축
외부 API를 트랜잭션 밖으로 분리
불필요한 직렬화 제거
N+1 쿼리 제거
COUNT 쿼리 제거
캐시 적용
읽기 모델 분리
비동기 처리 전환
~~~

### 4단계. 병목 자원을 조정한다

점유 시간을 줄였는데도 부족하면 자원 크기를 조정한다.

~~~text
DB pool size 조정
HTTP client pool size 조정
thread pool size 조정
DB read replica 검토
캐시 계층 확장
서버 scale-out
~~~

단, 풀 크기를 늘릴 때는 하류가 감당 가능한지 반드시 확인해야 한다. 풀은 대기 위치를 옮길 뿐, 병목 자체를 없애지 못한다.

### 5단계. 회복 기준을 검증한다

조치 후에는 평균 응답 시간이 아니라 회복 곡선을 본다.

~~~text
p99가 안정화되는가?
pending queue가 줄어드는가?
retry rate가 budget 안으로 들어오는가?
in-flight 요청 수가 정상 범위로 내려오는가?
connection acquire time이 낮아지는가?
downstream 에러율이 줄어드는가?
~~~

> 💡 장애 대응의 목적은 순간 성공률 회복이 아니라 포화 전이 차단과 회복 곡선 확보다.

## 12. 면접 대비

> 💡 서술형 문제  
>
> 트래픽은 평소와 비슷한데 특정 시간대부터 API p99가 300ms에서 2초로 증가했다. 평균 DB query time은 크게 변하지 않았고, 외부 API timeout과 retry도 일부 증가했다. 이 상황에서 어떤 가설을 세우고, 어떤 지표를 어떤 순서로 확인하며, 어떻게 완화할지 설명하라.

### 모범 답안

저는 먼저 평균 응답 시간이 아니라 tail latency와 대기열 지표를 기준으로 보겠습니다. 트래픽이 늘지 않았는데 p99가 증가했다면 요청 수 증가보다 요청 체류 시간 증가가 원인일 가능성이 큽니다. Little’s Law 기준으로 유입률 λ가 같아도 요청 체류 시간 W가 증가하면 시스템 안의 동시 요청 수 L이 늘고, 이로 인해 pool과 queue가 포화될 수 있습니다.

먼저 endpoint별 p50/p95/p99를 확인해 p99만 먼저 악화됐는지 봅니다. 그다음 같은 타임라인에서 DB connection acquire time, pool active/idle/pending, transaction duration, external API p95/p99, retry rate, in-flight 요청 수를 겹쳐 봅니다. 평균 DB query time이 유지되는데 acquire time과 pending threads가 증가했다면 쿼리 실행보다 커넥션 풀 포화가 원인일 수 있습니다. 반대로 외부 API p99가 먼저 증가하고 retry rate가 뒤따라 증가했다면 downstream 지연과 retry storm을 의심합니다.

완화는 먼저 증폭을 줄이는 방향으로 하겠습니다. 즉시 retry가 있다면 retry 횟수를 줄이고, exponential backoff와 jitter를 적용해 재시도 파동을 분산합니다. 동시에 retry budget을 둬 원 요청 대비 재시도 비율을 제한하고, circuit breaker로 비정상 downstream에 대해 fail-fast를 적용합니다. 그다음 트랜잭션 범위를 확인해 외부 API 호출이나 느린 I/O가 DB 커넥션을 잡은 상태에서 수행되는지 제거합니다. 필요하다면 부가 정보 조회는 fallback 처리하고, 필수 요청과 비필수 요청의 timeout을 분리합니다.

마지막으로 pool size나 서버 증설을 검토하되, 이것은 병목 위치를 확인한 뒤 적용해야 합니다. 풀을 늘리면 앱 대기는 줄 수 있지만 DB 내부 lock wait나 IO wait가 증가하면 장애가 다른 위치로 이동할 수 있기 때문입니다. 검증은 평균 latency가 아니라 p99, acquire time, pending threads, retry rate, in-flight 요청 수가 정상 범위로 돌아오는지로 판단하겠습니다.

핵심은 “느린 요청 하나”가 아니라 “느린 요청이 만든 대기열과 증폭 경로”를 찾는 것입니다.

## 13. 요약 정리

> 💡 레이턴시는 사용자 경험 지표이면서 자원 점유 시간 지표다.

트래픽이 늘지 않아도 요청 체류 시간 W가 늘면 Little’s Law에 따라 시스템 안의 동시 요청 수 L이 증가한다.

p50은 평시 효율, p95는 대부분 사용자 경험, p99는 장애 가능성을 보여준다.

DB 장애는 query time보다 connection acquire time과 transaction duration에서 먼저 드러날 수 있다.

외부 API 지연 상황에서 무분별한 retry는 복구가 아니라 부하 증폭이 될 수 있다.

timeout은 짧을수록 좋은 값이 아니라, SLA 예산 안에서 자원 점유와 실패 감지를 조절하는 값이다.

실무 대응 순서는 포화 지점 확인 → 증폭 경로 차단 → 점유 시간 단축 → 병목 자원 조정 → 회복 지표 검증이다.

결국 레이턴시 감각이란 “몇 ms가 빠른가”를 아는 것이 아니라, **어떤 대기가 어떤 큐를 만들고, 그 큐가 어떤 자원을 고갈시키는지 읽는 능력**이다.
