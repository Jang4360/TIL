# 트랜잭션을 썼는데도 왜 동시성 버그가 생길까

주문 수량을 차감하는 로직에 트랜잭션을 걸었다.

결제 승인, 재고 차감, 주문 상태 변경이 하나의 트랜잭션 안에서 실행된다. 그런데 운영 중에는 재고가 음수가 되거나, 같은 쿠폰이 두 번 사용되거나, 관리 화면에서 방금 생성된 주문이 보였다가 사라지는 것처럼 보이는 일이 생긴다.

처음에는 이렇게 생각한다.

> 트랜잭션을 썼는데 왜 이런 일이 생기지?

ACID를 배우고 나면 트랜잭션이 원자성, 일관성, 격리성, 지속성을 보장하므로 동시성 문제도 자동으로 막아줄 것처럼 느껴진다.

하지만 트랜잭션은 내 코드 블록을 완전한 안전 구역으로 만들어주는 기능이 아니다.

트랜잭션은 작업 묶음의 성공과 실패를 관리한다. 동시에 실행되는 트랜잭션 사이에서 무엇을 얼마나 격리할지는 isolation level, lock, MVCC, 인덱스, 쿼리 패턴이 함께 결정한다.

핵심 질문은 이것이다.

> 트랜잭션을 썼는데도 왜 이상한 읽기와 동시성 버그가 발생할 수 있는가?

답은 단순하다.

트랜잭션은 작업을 묶어주지만, 비즈니스 불변식을 자동으로 이해하지 않는다.

"재고는 0 미만이면 안 된다", "사용자는 쿠폰을 한 번만 받을 수 있다", "전체 발급 수는 10,000개를 넘으면 안 된다" 같은 규칙은 DB가 직접 강제할 수 있는 row, unique key, counter, slot, constraint로 표현해야 한다.

---

## 먼저 구조를 잡자

트랜잭션을 이해할 때 먼저 버려야 할 오해가 있다.

트랜잭션은 "이 코드 블록 안에서는 동시성 문제가 사라진다"는 뜻이 아니다.

더 정확히는 DB가 여러 읽기와 쓰기를 하나의 논리적 단위로 묶고, 실패 시 되돌리며, 동시에 실행되는 다른 작업과의 충돌을 일정 규칙에 따라 조정하는 장치다.

ACID는 네 가지 성질을 말한다.

```text
Atomicity
  전부 성공하거나 전부 실패한다.

Consistency
  DB 제약과 애플리케이션 규칙이 깨지지 않아야 한다.

Isolation
  동시에 실행되는 트랜잭션이 서로 어떻게 보이는지 정한다.

Durability
  커밋된 결과가 장애 이후에도 남는다.
```

여기서 동시성 버그의 대부분은 Isolation을 과대평가해서 생긴다.

트랜잭션 안에 넣었다고 해서 모든 읽기가 최신이고, 모든 쓰기가 자동으로 직렬화되며, 모든 조건 검사가 안전해지는 것은 아니다.

재고 차감 흐름을 보자.

```text
1. 사용자가 상품 A를 주문한다.
2. 애플리케이션이 현재 재고를 조회한다.
3. 재고가 충분하면 주문을 생성한다.
4. 상품 재고를 차감한다.
5. 트랜잭션을 커밋한다.
```

겉으로 보면 문제없어 보인다.

```sql
BEGIN;

SELECT stock
FROM product
WHERE id = 10;

-- stock > 0 이면
INSERT INTO orders(product_id, quantity)
VALUES (10, 1);

UPDATE product
SET stock = stock - 1
WHERE id = 10;

COMMIT;
```

하지만 동시에 두 요청이 들어오면 이야기가 달라진다.

두 트랜잭션이 같은 시점의 재고를 읽을 수 있다. 조건 판단은 애플리케이션 메모리에서 이루어질 수 있다. 실제 update 시점의 lock 획득 순서에 따라 대기, 충돌, deadlock, lost update가 발생할 수 있다.

DB 내부에서는 다음 요소들이 함께 움직인다.

```text
1. 트랜잭션은 시작 시점과 커밋 시점을 가진다.
2. 쓰기 작업은 보통 row 단위 write lock을 잡는다.
3. 읽기 작업은 DB와 isolation level에 따라 lock을 잡거나 MVCC snapshot을 읽는다.
4. MVCC는 과거 버전을 보여줘 읽기와 쓰기의 충돌을 줄인다.
5. 충돌이 심하면 대기, timeout, deadlock, serialization failure가 발생한다.
```

중요한 점은 이것이다.

트랜잭션은 단일 기능이 아니라 commit, rollback, lock, version, isolation policy가 결합된 실행 모델이다.

그래서 "트랜잭션을 썼다"는 말만으로는 안전성을 판단할 수 없다.

어떤 isolation level인지, 어떤 row를 어떤 순서로 읽고 쓰는지, 조건 검사가 DB 안에서 원자적으로 수행되는지까지 봐야 한다.

---

## 내부에서는 무슨 일이 일어나는가

### ACID의 I는 항상 완전한 격리를 뜻하지 않는다

문제는 Isolation이라는 이름이 주는 착각에서 시작된다.

많은 개발자는 트랜잭션을 열면 다른 트랜잭션의 중간 상태가 보이지 않고, 따라서 동시성 문제가 사라질 것이라고 생각한다.

하지만 DB는 성능과 동시성을 위해 isolation level을 여러 단계로 나눈다.

SQL 표준의 대표적인 격리 수준은 다음과 같다.

| 격리 수준 | 대략적인 의미 | 주의할 점 |
| --- | --- | --- |
| READ UNCOMMITTED | 커밋되지 않은 변경도 보일 수 있음 | 대부분의 주요 DB에서는 거의 쓰지 않음 |
| READ COMMITTED | 커밋된 데이터만 읽음 | 같은 트랜잭션 안에서도 다시 읽으면 결과가 달라질 수 있음 |
| REPEATABLE READ | 반복 읽기에서 같은 snapshot을 보는 방향 | DB 구현에 따라 phantom/write skew 처리 차이가 있음 |
| SERIALIZABLE | 동시에 실행해도 직렬 실행과 같은 결과를 보장하는 가장 강한 수준 | 충돌 실패와 retry, 처리량 저하를 감수해야 함 |

PostgreSQL 문서는 Serializable을 여러 트랜잭션을 어떤 순서로 하나씩 실행한 것과 같은 효과를 보장하는 수준으로 설명한다. MySQL InnoDB는 기본 isolation level이 `REPEATABLE READ`이고, PostgreSQL은 기본이 `READ COMMITTED`다.

여기서 중요한 것은 DB마다 구현이 다르다는 점이다.

PostgreSQL의 `REPEATABLE READ`는 snapshot isolation에 가깝게 동작해서 SQL 표준의 repeatable read보다 강하게 phantom을 막는 면이 있다. 반면 MySQL InnoDB의 `REPEATABLE READ`에서는 consistent read, locking read, next-key lock 동작을 구분해서 봐야 한다.

그래서 "REPEATABLE READ면 안전하다" 또는 "READ COMMITTED면 위험하다"처럼 외우면 안 된다.

보호하려는 불변식이 무엇인지 먼저 봐야 한다.

### write lock은 쓰기를 보호하지만 읽은 판단까지 보호하지는 않는다

트랜잭션 안에서 `UPDATE`를 실행하면 DB는 보통 해당 row에 write lock을 건다.

그래서 같은 row를 동시에 수정하려는 다른 트랜잭션은 기다리거나 실패한다.

이 때문에 이렇게 생각하기 쉽다.

> 어차피 update할 때 lock이 걸리니 괜찮지 않을까?

하지만 문제는 update 이전의 판단이다.

많은 코드는 먼저 읽고, 애플리케이션에서 조건을 검사한 뒤, 나중에 쓴다.

```java
Product product = productRepository.findById(productId);

if (product.stock() <= 0) {
    throw new SoldOutException();
}

product.decreaseStock(1);
```

ORM을 쓰면 이 흐름이 더 자연스러워 보인다.

객체를 읽고, 메서드로 상태를 바꾸고, 트랜잭션 종료 시점에 flush된다.

하지만 내부적으로는 읽기와 쓰기 사이에 시간이 생긴다. 그 사이 다른 트랜잭션이 같은 row를 바꾸면 처음 읽은 값에 기반한 판단이 낡은 판단이 될 수 있다.

lost update는 이 지점에서 자주 나온다.

두 트랜잭션이 같은 값을 읽고 각각 계산한 뒤 덮어쓰면 한쪽 변경이 사라진다.

```sql
-- T1, T2가 모두 stock = 10을 읽음

-- T1
UPDATE product
SET stock = 9
WHERE id = 10;

-- T2
UPDATE product
SET stock = 9
WHERE id = 10;
```

최종 stock은 8이 아니라 9가 된다.

물론 실제 DB와 ORM 설정에 따라 update 시점에 lock 대기나 충돌 감지가 일어날 수 있다. 그러나 "읽은 값 기반으로 새 값을 계산해 저장하는 방식"은 언제나 lost update 위험을 가진다.

이를 줄이려면 조건과 변경을 DB의 단일 문장으로 밀어 넣는 편이 안전하다.

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 10
  AND stock >= 1;
```

이 방식은 읽기, 조건 검사, 쓰기가 하나의 update 안에서 처리된다.

영향받은 row 수가 1이면 성공이고, 0이면 재고 부족 또는 충돌로 볼 수 있다.

트랜잭션 안에 있다는 사실보다 조건 검사와 상태 변경이 같은 원자적 경계 안에 있는지가 더 중요하다.

### MVCC는 읽기를 빠르게 하지만 최신 상태를 보장하지 않는다

MVCC는 Multi-Version Concurrency Control의 약자다.

이름보다 중요한 것은 동작 방식이다.

DB가 row의 여러 버전을 유지하고, 각 트랜잭션은 자신의 시점에 보이는 버전을 읽는다. 덕분에 읽기 작업이 쓰기 작업을 매번 기다리지 않아도 된다.

이 구조는 성능에 유리하다.

관리 화면에서 주문 목록을 조회하는 동안 결제 트랜잭션이 주문 상태를 업데이트해도, 조회는 특정 snapshot을 기준으로 빠르게 진행될 수 있다.

읽기와 쓰기가 서로 block하지 않으니 처리량도 좋아진다.

하지만 MVCC의 장점은 동시에 오해의 원인이 된다.

snapshot을 읽는다는 말은 항상 최신을 읽는다는 뜻이 아니다.

PostgreSQL의 `READ COMMITTED`에서는 각 statement가 시작될 때의 snapshot을 읽는다. 같은 트랜잭션 안에서 같은 `SELECT`를 두 번 실행해도 두 번째 statement는 그 사이 커밋된 변경을 볼 수 있다.

반면 `REPEATABLE READ`에서는 트랜잭션의 snapshot을 기준으로 반복 조회가 유지된다.

MySQL InnoDB에서도 consistent nonlocking read와 locking read의 동작을 구분해야 한다. 일반 `SELECT`는 snapshot을 읽고, `SELECT ... FOR UPDATE`는 최신 사용 가능한 데이터를 읽으며 읽은 row에 exclusive lock을 건다.

즉 MVCC는 읽기 성능을 위해 과거 버전을 보여주는 구조이지, 비즈니스적으로 가장 맞는 최신 상태를 보장하는 구조가 아니다.

최신성이 중요한 판단에는 snapshot read만 믿지 말고 locking read, conditional update, version check를 검토해야 한다.

### 오래 열린 트랜잭션은 과거 버전을 붙잡는다

MVCC는 과거 버전을 유지한다.

그런데 트랜잭션이 오래 열려 있으면 DB는 그 트랜잭션이 볼 수 있어야 하는 과거 버전을 쉽게 정리하지 못한다.

예를 들어 배치 작업이 오래 열린 트랜잭션 안에서 미처리 주문을 조회한다고 하자.

```sql
BEGIN;

SELECT *
FROM orders
WHERE status = 'READY';

-- 오래 걸리는 외부 처리 또는 대량 계산

SELECT *
FROM orders
WHERE status = 'READY';

COMMIT;
```

그 사이 다른 트랜잭션이 READY 주문을 추가하거나 상태를 바꿔도, 현재 트랜잭션의 snapshot에서는 보이지 않을 수 있다.

동시에 오래 열린 snapshot 때문에 PostgreSQL에서는 vacuum 지연과 bloat가 생길 수 있고, MySQL InnoDB에서는 undo log가 길어질 수 있다.

단순 조회 트랜잭션 하나도 오래 열려 있으면 쓰기 성능과 저장 공간에 영향을 줄 수 있다.

그래서 조회 트랜잭션도 짧게 유지해야 한다.

### phantom read는 row가 아니라 범위가 변할 때 생긴다

동시성 버그는 항상 같은 row를 두 명이 수정할 때만 생기지 않는다.

더 까다로운 문제는 조건에 맞는 row 집합이 바뀌는 경우다.

이것이 phantom read의 핵심이다.

예를 들어 좌석 예약 시스템에서 특정 공연의 남은 좌석 수를 계산하고, 여유가 있으면 예약 row를 추가한다고 하자.

```sql
BEGIN;

SELECT COUNT(*)
FROM reservations
WHERE show_id = 7
  AND status = 'CONFIRMED';

-- 정원보다 작으면
INSERT INTO reservations(show_id, user_id, status)
VALUES (7, 101, 'CONFIRMED');

COMMIT;
```

여기서 보호해야 하는 것은 특정 reservation row 하나가 아니다.

아직 존재하지 않는 미래의 row까지 포함한 범위다.

두 트랜잭션이 동시에 count를 읽고 insert하면 각자 문제없어 보인다. 하지만 전체 정원 제한은 깨질 수 있다.

DB가 이 문제를 막으려면 단순 row lock으로는 부족하다.

인덱스 범위에 대한 lock, gap lock, predicate lock, serializable isolation, exclusion constraint, unique constraint 같은 더 강한 장치가 필요하다.

특히 쿼리가 적절한 인덱스를 타지 못하면 DB가 보호해야 할 범위를 명확히 잡기 어렵거나 과도하게 넓은 lock을 잡을 수 있다.

phantom read를 "같은 select를 두 번 했는데 행이 추가됐다" 정도로만 외우면 부족하다.

진짜 문제는 없는 row의 부재를 근거로 의사결정하는 코드다.

```text
이미 발급된 쿠폰이 없으면 발급
오늘 정산 row가 없으면 생성
활성 세션이 N개 미만이면 추가
겹치는 예약이 없으면 예약 생성
```

이런 로직은 select 결과만으로 안전해지지 않는다.

### deadlock은 DB가 망가진 것이 아니라 순서가 충돌했다는 신호다

deadlock은 두 트랜잭션이 서로의 lock을 기다리면서 더 이상 진행할 수 없는 상태다.

흔한 예시는 계좌 이체다.

```text
1. T1은 A 계좌를 잠그고 B 계좌를 수정하려 한다.
2. T2는 B 계좌를 잠그고 A 계좌를 수정하려 한다.
3. T1은 B lock을 기다린다.
4. T2는 A lock을 기다린다.
5. DB는 하나를 victim으로 골라 rollback한다.
```

트랜잭션을 썼기 때문에 deadlock이 생긴다기보다는, 여러 트랜잭션이 여러 자원을 다른 순서로 잡기 때문에 생긴다.

DB는 deadlock을 감지하면 보통 한쪽 트랜잭션을 실패시켜 전체 시스템이 멈추지 않게 한다.

애플리케이션 입장에서는 갑자기 SQL exception이 발생한 것처럼 보인다.

deadlock은 가끔 나는 DB 오류가 아니다.

반복된다면 lock 획득 순서, 트랜잭션 길이, 인덱스, update 범위가 잘못되었다는 신호다.

일시적 deadlock은 retry 대상이지만, 반복적 deadlock은 구조를 봐야 한다.

## 언제 문제가 되는가

### 쿠폰 선착순 발급

대표 시나리오는 쿠폰 선착순 발급이다.

요구사항은 단순하다.

```text
1. 쿠폰은 1인 1회만 발급된다.
2. 전체 발급 수량은 10,000장을 넘으면 안 된다.
```

개발자는 트랜잭션 안에서 기존 발급 여부를 확인하고, 전체 발급 수를 확인한 뒤, 발급 row를 insert한다.

```sql
BEGIN;

SELECT COUNT(*)
FROM coupon_issues
WHERE coupon_id = 1
  AND user_id = 100;

SELECT COUNT(*)
FROM coupon_issues
WHERE coupon_id = 1;

INSERT INTO coupon_issues(coupon_id, user_id)
VALUES (1, 100);

COMMIT;
```

테스트에서는 잘 동작한다.

하지만 이벤트 오픈 시점에 수백 개 요청이 동시에 들어오면 문제가 드러난다.

첫 번째 문제는 중복 발급이다.

같은 사용자의 두 요청이 거의 동시에 들어오면 둘 다 "아직 발급 이력 없음"을 볼 수 있다. 그 뒤 둘 다 insert하면 중복 row가 생긴다.

트랜잭션은 각각 정상적으로 커밋되었지만, 1인 1회 규칙은 깨졌다.

이 문제는 `(coupon_id, user_id)` unique constraint 없이 애플리케이션 select만으로 막기 어렵다.

```sql
ALTER TABLE coupon_issues
ADD CONSTRAINT uk_coupon_issues_coupon_user
UNIQUE (coupon_id, user_id);
```

두 번째 문제는 총량 초과다.

전체 발급 수 count가 9,999일 때 여러 트랜잭션이 동시에 count를 읽으면 각자 발급 가능하다고 판단한다.

결과적으로 10,000장을 초과할 수 있다.

이건 단일 사용자 중복보다 더 어렵다. unique constraint 하나로 "최대 N개" 규칙을 직접 표현하기 어렵기 때문이다.

이럴 때는 "전체 발급 수"를 명시적 자원으로 모델링해야 한다.

예를 들어 `coupon` row에 `issued_count`를 둔다.

```sql
UPDATE coupon
SET issued_count = issued_count + 1
WHERE id = 1
  AND issued_count < total_quantity;
```

영향받은 row 수가 1이면 발급 가능하다.

0이면 이미 소진된 것이다.

이 방식은 count 조회를 단일 row 조건부 update로 바꾼다.

### 회의실 예약 범위 겹침

다른 예시는 회의실 예약이다.

요구사항은 다음이다.

```text
같은 회의실의 예약 시간은 서로 겹치면 안 된다.
```

나쁜 방식은 보통 이렇다.

```sql
BEGIN;

SELECT *
FROM reservation
WHERE room_id = 1
  AND start_time < :new_end
  AND end_time > :new_start;

-- 겹치는 예약이 없으면
INSERT INTO reservation(room_id, start_time, end_time)
VALUES (1, :new_start, :new_end);

COMMIT;
```

동시에 두 트랜잭션이 같은 범위를 검사하면 둘 다 "겹치는 예약 없음"을 볼 수 있다.

이건 단일 row unique constraint로 막기 어렵다. 범위 조건이기 때문이다.

해결 방법은 여러 가지다.

첫 번째는 slot으로 쪼개는 것이다.

30분 단위 예약만 허용한다면 `reservation_slot` 테이블을 둔다.

```sql
CREATE TABLE reservation_slot (
    room_id BIGINT NOT NULL,
    slot_start TIMESTAMP NOT NULL,
    reservation_id BIGINT NOT NULL,
    PRIMARY KEY (room_id, slot_start)
);
```

10:00~11:00 예약이면 두 개 slot을 insert한다.

```text
(room_id=1, slot_start=10:00)
(room_id=1, slot_start=10:30)
```

동시에 누군가 10:30~11:30을 예약하려고 하면 10:30 slot에서 unique 충돌이 난다.

두 번째는 부모 row를 잠그는 것이다.

```sql
BEGIN;

SELECT *
FROM room
WHERE id = 1
FOR UPDATE;

SELECT *
FROM reservation
WHERE room_id = 1
  AND start_time < :new_end
  AND end_time > :new_start;

INSERT INTO reservation(room_id, start_time, end_time)
VALUES (1, :new_start, :new_end);

COMMIT;
```

같은 `room_id`에 대한 예약 생성은 room row lock 때문에 순차 처리된다.

세 번째는 PostgreSQL exclusion constraint를 쓰는 것이다.

PostgreSQL은 range type과 exclusion constraint로 "같은 room_id에서 period가 겹치면 안 된다"를 DB 제약으로 표현할 수 있다.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservation (
  id BIGINT PRIMARY KEY,
  room_id BIGINT NOT NULL,
  period TSTZRANGE NOT NULL,
  EXCLUDE USING gist (
    room_id WITH =,
    period WITH &&
  )
);
```

PostgreSQL 문서는 range type에 대해서는 scalar 값의 unique보다 exclusion constraint가 적합한 경우가 많다고 설명한다.

이 방식은 DB 종속적이지만, 범위 겹침이라는 불변식을 스키마에 직접 넣을 수 있다는 장점이 있다.

### 상태 기반 배치와 사용자 요청 충돌

배치도 자주 문제가 된다.

예를 들어 만료 주문 배치가 있다.

```sql
UPDATE orders
SET status = 'EXPIRED'
WHERE status = 'PENDING'
  AND expires_at < NOW();
```

동시에 사용자는 결제를 완료한다.

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_no = ?
  AND status = 'PENDING';
```

둘 다 `PENDING`을 보고 상태를 바꾼다.

여기서 중요한 것은 상태 전이를 조건부 update로 표현하는 것이다.

배치든 사용자 요청이든 "현재 상태가 내가 기대한 상태일 때만 바꾼다"는 조건이 있어야 한다.

또 배치가 넓은 범위를 한 번에 update하면 lock wait이 커질 수 있다.

작은 chunk로 나누고, 인덱스를 맞추고, 필요하면 `SKIP LOCKED` 같은 큐성 처리 방식을 검토해야 한다.

## 해결 패턴

### 1. 불변식을 문장으로 먼저 정의한다

동시성 문제를 해결하려면 먼저 깨지면 안 되는 규칙을 문장으로 써야 한다.

```text
재고는 0 미만이면 안 된다.
사용자는 같은 쿠폰을 한 번만 받을 수 있다.
전체 쿠폰 발급 수는 10,000개를 넘으면 안 된다.
같은 회의실의 예약 시간은 겹치면 안 된다.
주문은 CREATED -> PAID -> SHIPPED 순서로만 이동한다.
```

그 다음 이 불변식이 어디에서 보호되는지 본다.

```text
애플리케이션 if 문인가?
DB unique constraint인가?
조건부 update인가?
row lock인가?
serializable isolation인가?
exclusion constraint인가?
메시지 consumer의 멱등 처리인가?
```

애플리케이션 if 문만으로 보호되는 불변식은 동시성에 약하다.

핵심 불변식은 가능하면 DB가 원자적으로 판단할 수 있는 형태로 내려야 한다.

### 2. 단일 row 숫자는 조건부 update로 처리한다

재고 차감처럼 단일 row의 숫자를 줄이는 문제는 조건부 update가 잘 맞는다.

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :product_id
  AND stock >= :quantity;
```

영향받은 row 수로 성공 여부를 판단한다.

```text
affected rows = 1
  -> 차감 성공

affected rows = 0
  -> 재고 부족 또는 상태 변경
```

이 방식은 읽기, 비교, 변경을 하나의 update 문 안으로 넣는다.

읽고 판단한 뒤 나중에 update하는 구조보다 안전하다.

### 3. 하나만 가능하면 unique constraint로 표현한다

사용자별 쿠폰 1회 발급은 unique constraint로 표현한다.

```sql
ALTER TABLE coupon_issues
ADD CONSTRAINT uk_coupon_user UNIQUE (coupon_id, user_id);
```

동시에 같은 사용자의 요청이 여러 개 들어와도 DB는 하나만 성공시킨다.

나머지는 duplicate key 오류가 난다.

이 오류를 단순 500으로 반환하면 안 된다.

같은 요청의 재시도라면 기존 발급 결과를 반환하고, 다른 요청이라면 409 Conflict처럼 의미 있는 응답으로 바꿔야 한다.

unique constraint는 동시성 제어이면서 도메인 규칙이다.

### 4. 최대 N개 규칙은 counter row나 slot으로 바꾼다

`SELECT COUNT(*)` 후 insert는 위험하다.

count 결과가 lock으로 보호되지 않으면 여러 트랜잭션이 같은 결론을 낼 수 있다.

쿠폰 총량 제한은 counter row로 바꿀 수 있다.

```sql
BEGIN;

UPDATE coupon
SET issued_count = issued_count + 1
WHERE id = :coupon_id
  AND issued_count < total_quantity;

-- affected rows = 1인 경우에만
INSERT INTO coupon_issues(coupon_id, user_id)
VALUES (:coupon_id, :user_id);

COMMIT;
```

전체 수량 보호는 `coupon.issued_count`가 담당한다.

사용자 중복 발급 보호는 `coupon_issues(coupon_id, user_id)` unique constraint가 담당한다.

이 방식의 장점은 쿼리가 단순하고 lock 범위가 명확하다는 점이다.

단점은 `coupon` row 하나가 hot row가 된다는 점이다.

트래픽이 매우 크면 이 row에 lock 대기가 집중될 수 있다.

다른 방식은 slot을 미리 만드는 것이다.

```sql
CREATE TABLE coupon_slot (
    id BIGINT PRIMARY KEY,
    coupon_id BIGINT NOT NULL,
    slot_no INT NOT NULL,
    issued_user_id BIGINT,
    issued_at TIMESTAMP,
    CONSTRAINT uk_coupon_slot UNIQUE (coupon_id, slot_no)
);
```

발급 가능한 10,000개 slot을 미리 만들어둔다.

발급할 때는 아직 점유되지 않은 slot 하나를 가져간다.

```sql
SELECT id
FROM coupon_slot
WHERE coupon_id = :coupon_id
  AND issued_user_id IS NULL
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

그 다음 해당 slot을 점유한다.

```sql
UPDATE coupon_slot
SET issued_user_id = :user_id,
    issued_at = NOW()
WHERE id = :slot_id;
```

PostgreSQL 문서는 `SKIP LOCKED`가 잠긴 row를 기다리지 않고 건너뛰므로 큐성 테이블에서 여러 worker가 경합을 줄이는 데 사용할 수 있다고 설명한다.

단, `SKIP LOCKED`는 일관된 전체 조회가 아니라 잠긴 row를 건너뛰는 방식이다. 일반 조회에는 맞지 않고, queue-like 작업에 맞다.

### 5. 범위 겹침은 모델링을 바꾼다

회의실 예약처럼 범위가 겹치면 안 되는 문제는 선택지가 여러 개다.

slot 방식은 범위를 discrete한 row로 바꾼다.

```text
10:00~11:00 예약
  -> 10:00 slot
  -> 10:30 slot
```

장점은 unique constraint로 충돌이 명확해진다는 점이다.

단점은 slot granularity를 정해야 하고, 긴 예약은 여러 row를 insert해야 한다는 점이다.

부모 row lock 방식은 같은 자원에 대한 작업을 순차 처리한다.

```sql
SELECT *
FROM room
WHERE id = :room_id
FOR UPDATE;
```

장점은 구현이 단순하고 복잡한 범위에도 적용 가능하다는 점이다.

단점은 같은 room에 대한 예약이 모두 직렬화되어 병렬성이 줄어든다는 점이다.

PostgreSQL exclusion constraint는 범위 겹침 규칙을 DB 제약으로 직접 표현한다.

장점은 불변식이 스키마에 박힌다는 점이다.

단점은 DB 종속적이고 팀이 해당 기능에 익숙해야 한다는 점이다.

SERIALIZABLE은 일반적인 해결책이 될 수 있다.

하지만 충돌이 많은 경로에서는 serialization failure가 늘 수 있고, 결국 retry 설계가 필요하다.

가능하면 불변식을 unique key, counter, slot, exclusion constraint처럼 더 명시적인 구조로 표현할 수 있는지 먼저 본다.

### 6. 낙관적 락은 버전으로 충돌을 감지한다

낙관적 락은 먼저 잠그지 않는다.

대신 내가 읽은 뒤 누가 바꿨는지 update 시점에 확인한다.

보통 version 컬럼을 둔다.

```sql
SELECT stock, version
FROM product
WHERE id = 1;
```

결과가 다음과 같다고 하자.

```text
stock = 10
version = 3
```

수정할 때는 version을 조건에 넣는다.

```sql
UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
  AND version = 3;
```

그 사이 다른 트랜잭션이 먼저 수정해서 version이 4가 됐다면 이 update는 영향을 주는 row가 0개다.

낙관적 락은 충돌이 적은 환경에서 좋다.

lock을 오래 보유하지 않아도 되고, 읽기와 계산을 자유롭게 할 수 있다.

하지만 같은 row에 쓰기가 많이 몰리면 계속 실패한다. 이때 retry가 폭증하면 오히려 부하가 커진다.

낙관적 락은 "락을 안 쓰는 방법"이 아니다.

충돌 감지 시점을 뒤로 미루는 방법이다.

### 7. 비관적 락은 먼저 잠그고 판단한다

비관적 락은 먼저 잠그고 진행한다.

```sql
BEGIN;

SELECT *
FROM product
WHERE id = 10
FOR UPDATE;

-- 현재 값을 보고 판단

UPDATE product
SET stock = stock - 1
WHERE id = 10;

COMMIT;
```

MySQL InnoDB 문서는 `SELECT ... FOR UPDATE`가 읽은 row에 exclusive lock을 걸며, 해당 row를 update/delete하거나 locking read하려는 다른 트랜잭션은 기다린다고 설명한다.

PostgreSQL 문서도 `FOR UPDATE` row lock은 같은 row를 update/delete/select for update하려는 트랜잭션을 막고, row lock은 트랜잭션 종료 시 해제된다고 설명한다.

비관적 락은 같은 row에 대한 판단과 변경 사이의 안정성을 준다.

하지만 대기와 deadlock이 생긴다.

여러 row를 잠글 때는 항상 같은 순서로 잠근다.

```text
계좌 이체
  account_id 작은 계좌부터 lock
  account_id 큰 계좌 lock
  이체 수행
```

트랜잭션 안에서 외부 API를 호출하면 안 된다.

lock을 잡은 채 결제사, 메시지 브로커, 파일 업로드를 기다리면 lock 보유 시간이 길어지고 p99가 튄다.

### 8. 트랜잭션을 짧게 나누고 상태를 명시한다

모든 것을 하나의 긴 트랜잭션으로 감싸고 싶어진다.

하지만 외부 API 호출, 메시지 발행, 긴 계산이 트랜잭션 안에 들어가면 lock 보유 시간이 길어진다.

예를 들어 다음 흐름은 위험하다.

```text
1. BEGIN
2. 주문 row lock
3. 외부 결제 승인 호출
4. 재고 차감
5. 메시지 발행
6. COMMIT
```

외부 결제 API가 2초 지연되면 주문 row lock도 2초 동안 유지된다.

대신 상태를 나눌 수 있다.

```text
1. BEGIN
2. payment_attempt = PENDING 저장
3. order = PAYMENT_PENDING 전이
4. COMMIT

5. 외부 결제 API 호출

6. BEGIN
7. payment_attempt = SUCCEEDED
8. order = PAID
9. outbox 이벤트 저장
10. COMMIT
```

이 방식은 상태 모델이 복잡해진다.

하지만 lock 보유 시간이 줄고, 장애가 난 지점을 복구하기 쉬워진다.

### 9. retry는 멱등성과 함께 넣는다

deadlock victim, lock wait timeout, serialization failure는 retry로 성공할 수 있다.

하지만 retry는 같은 요청이 여러 번 실행된다는 뜻이다.

첫 번째 요청이 실제로는 성공했는데 응답만 실패했을 수 있다.

쿠폰 발급 API를 보자.

```text
1. 서버가 쿠폰 발급 성공
2. DB commit 완료
3. 응답을 보내는 중 네트워크 timeout
4. 클라이언트는 실패로 판단
5. 같은 요청 retry
```

멱등성이 없으면 같은 사용자에게 쿠폰이 두 번 발급될 수 있다.

결제라면 두 번 결제될 수 있다.

그래서 retry 가능한 작업에는 같은 요청을 여러 번 보내도 결과가 한 번만 반영되는 구조가 필요하다.

쿠폰 발급에서는 unique constraint가 멱등성의 하한선이 된다.

```sql
UNIQUE(coupon_id, user_id)
```

결제나 주문 생성 API라면 idempotency key를 둘 수 있다.

```text
idempotency_request
  - key
  - user_id
  - request_hash
  - response_body
  - status
```

retry는 정합성 설계가 아니다.

retry는 이미 충돌을 감지한 뒤 다시 시도하는 실행 정책이다. 충돌이 왜 발생하는지 줄이지 않고 retry만 늘리면 DB 부하와 tail latency가 같이 증가한다.

## 트레이드오프

동시성 처리는 하나의 정답이 아니라 선택의 연속이다.

### isolation level을 올리는 선택

`REPEATABLE READ`나 `SERIALIZABLE`을 쓰면 이상한 읽기와 동시성 충돌을 줄일 수 있다.

얻는 것은 강한 일관성과 단순한 사고 모델이다.

잃는 것은 처리량, 대기 시간, 실패율이다.

특히 `SERIALIZABLE`에서는 충돌을 막는 대신 일부 트랜잭션을 실패시켜 retry하도록 만들 수 있다.

트랜잭션이 길고, 외부 API 호출이 포함되어 있고, 사용자 요청이 특정 row나 범위에 몰리는 상황에서 무작정 isolation level을 올리면 p99가 크게 튈 수 있다.

강한 격리는 짧고 예측 가능한 트랜잭션에서 효과가 크다.

### 명시적 lock을 거는 선택

```sql
SELECT *
FROM product
WHERE id = 10
FOR UPDATE;
```

얻는 것은 판단과 변경 사이의 안정성이다.

특정 row를 잠근 뒤 읽고 수정하므로 같은 row에 대한 동시 변경을 직렬화할 수 있다.

잃는 것은 lock 대기와 deadlock 가능성이다.

여러 row를 다른 순서로 잠그거나, 인덱스가 부정확해서 예상보다 많은 row를 잠그면 지연이 커진다.

단순 조회에 locking read를 남발하면 MVCC가 주는 장점을 버리고 읽기까지 쓰기 경합에 끌어들인다.

### 원자적 update와 DB 제약을 쓰는 선택

`UPDATE ... WHERE stock >= 1`이나 unique constraint는 애플리케이션 race condition을 DB의 원자적 판단으로 줄인다.

얻는 것은 명확한 성공/실패 기준이다.

잃는 것은 도메인 규칙을 DB 스키마와 쿼리로 표현해야 하는 설계 비용이다.

그래도 핵심 불변식은 가능하면 DB 제약으로 내려야 한다.

애플리케이션 코드만으로 동시성 불변식을 지키는 것은 트래픽이 늘수록 깨지기 쉽다.

### counter row를 쓰는 선택

쿠폰 총량처럼 최대 N개 규칙을 하나의 counter row로 표현하면 조건부 update가 가능해진다.

얻는 것은 명확한 lock 대상과 빠른 판단이다.

잃는 것은 hot row다.

모든 발급 요청이 같은 `coupon` row를 update하므로 트래픽이 몰리면 대기열이 생긴다.

트래픽이 크면 slot 모델, sharded counter, queue 기반 직렬화 같은 대안을 검토해야 한다.

### slot 모델을 쓰는 선택

slot 모델은 발급 가능한 자리나 예약 가능한 구간을 미리 row로 만든다.

얻는 것은 명확한 점유 모델이다.

10,000개 쿠폰이면 10,000개 slot만 존재하므로 초과 발급이 어렵다. 서로 다른 slot을 가져가면 병렬 처리도 가능하다.

잃는 것은 모델 복잡도다.

slot을 미리 만들고, 수량 변경과 회수, 만료, 부분 취소를 처리해야 한다. 시간 예약에서는 slot granularity가 요구사항과 맞아야 한다.

### 낙관적 락을 쓰는 선택

낙관적 락은 lock 보유 시간을 줄이고, 충돌이 적은 환경에서 높은 처리량을 얻을 수 있다.

잃는 것은 충돌 시 재시도 로직과 사용자 경험 처리다.

같은 row에 쓰기가 매우 몰리는 핫스팟에서는 계속 실패하고 retry 폭풍을 만들 수 있다.

충돌이 드문 설정 변경, 사용자 프로필 수정, 관리 화면 수정에는 잘 맞는다.

재고 차감, 선착순 쿠폰처럼 충돌이 핵심인 경로에서는 조건부 update나 비관적 직렬화가 더 단순할 수 있다.

### 트랜잭션을 짧게 나누는 선택

트랜잭션을 짧게 나누면 lock 보유 시간과 장애 전파 범위가 줄어든다.

잃는 것은 상태 전이가 복잡해진다는 점이다.

`PENDING_PAYMENT`, `PAID`, `STOCK_RESERVED`, `CONFIRMED`, `FAILED` 같은 중간 상태를 다뤄야 한다.

재처리와 보상 로직도 필요하다.

하지만 외부 API 호출까지 긴 트랜잭션으로 묶는 방식보다 복구 가능성이 높다.

## 어떻게 분석할까

트랜잭션 관련 문제는 "느리다"와 "데이터가 이상하다"가 같이 나타나는 경우가 많다.

그래서 먼저 증상을 나눠야 한다.

```text
정합성 깨짐인가?
lock wait인가?
deadlock인가?
serialization failure인가?
retry 폭증인가?
중복 요청인가?
```

### 1. 깨진 불변식을 문장으로 쓴다

가장 먼저 해야 할 일은 깨진 규칙을 문장으로 쓰는 것이다.

```text
재고는 0 미만이면 안 된다.
사용자는 같은 쿠폰을 한 번만 가져야 한다.
활성 주문은 사용자당 10개 이하여야 한다.
같은 회의실의 예약은 겹치면 안 된다.
```

그 다음 이 불변식이 실제로 어디에서 보호되는지 확인한다.

DB 제약이 있는지, 조건부 update가 있는지, 단순 select 후 if 문인지, isolation level에 기대고 있는지 봐야 한다.

### 2. 예외 타입을 구분한다

다음 예외들은 의미가 다르다.

```text
duplicate key
  unique constraint가 충돌을 막은 것일 수 있음

deadlock
  lock 획득 순서가 충돌했을 수 있음

lock wait timeout
  누군가 lock을 오래 잡고 있을 수 있음

serialization failure
  SERIALIZABLE 또는 snapshot 기반 충돌 감지가 동작한 것일 수 있음

optimistic lock failure
  내가 읽은 version이 더 이상 최신이 아님
```

duplicate key는 반드시 나쁜 신호가 아니다.

중복 요청을 DB가 막아낸 정상적인 방어 신호일 수 있다.

반대로 lost update는 예외 없이 조용히 발생할 수 있다. 결과 데이터로 추적해야 한다.

### 3. 트랜잭션 전체 시간을 본다

SQL 하나가 20ms인데 트랜잭션 전체가 2초일 수 있다.

이 경우 DB 자체보다 트랜잭션 안의 애플리케이션 처리, 외부 API, 메시지 발행, 파일 처리 등이 lock 보유 시간을 늘렸을 가능성이 있다.

트랜잭션은 SQL 실행 시간만큼만 위험한 것이 아니다.

lock을 잡은 뒤 commit하기까지의 전체 시간만큼 위험하다.

trace에서 다음을 봐야 한다.

- transaction begin
- 첫 write 또는 locking read
- 외부 API 호출
- DB update
- message publish
- commit
- response

### 4. lock holder와 waiter를 같이 본다

대기 중인 SQL만 보면 부족하다.

누가 lock을 잡고 있는지 봐야 한다.

PostgreSQL에서는 `pg_stat_activity`, `pg_locks`를 본다.

MySQL에서는 `SHOW ENGINE INNODB STATUS`, performance_schema, `information_schema.innodb_trx` 계열을 본다.

중요한 것은 lock holder의 SQL과 트랜잭션 시작 시각이다.

오래 열린 트랜잭션 하나가 많은 요청을 줄 세울 수 있다.

### 5. 실행 계획과 인덱스를 본다

`UPDATE`나 `SELECT ... FOR UPDATE`가 인덱스를 타지 못하면 예상보다 많은 row를 스캔하면서 lock을 잡을 수 있다.

MySQL InnoDB 문서는 locking read, update, delete가 일반적으로 statement 처리 중 스캔한 index record에 lock을 건다고 설명한다.

즉 "결과적으로 한 row만 바꿨다"보다 "그 row를 찾기 위해 어떤 index range를 스캔했는가"가 중요하다.

확인할 것은 다음이다.

- WHERE 조건에 맞는 인덱스가 있는가
- 범위 조건이 너무 넓지 않은가
- 낮은 selectivity 컬럼만 타고 있지는 않은가
- ORDER BY/LIMIT이 lock 순서를 예측 가능하게 만드는가
- 같은 테이블을 다른 코드 경로가 다른 순서로 잠그지는 않는가

### 6. retry rate와 timeout budget을 본다

retry가 정상 요청의 1~2% 수준인지, 장애 시각에 30~50%까지 치솟았는지에 따라 해석이 다르다.

전자는 일시적 충돌 흡수일 수 있다.

후자는 시스템이 스스로 부하를 증폭시키는 상태다.

특히 클라이언트 retry, 서버 retry, 메시지 큐 redelivery가 겹치면 실제 DB 요청 수는 원래 트래픽보다 훨씬 커진다.

timeout도 함께 봐야 한다.

DB lock wait timeout이 애플리케이션 timeout보다 길면, 애플리케이션은 이미 실패했는데 DB는 계속 대기할 수 있다.

반대로 너무 짧으면 정상적인 순간 경합도 과도하게 실패한다.

## 해결 전략

가장 먼저 할 일은 트랜잭션을 더 크게 만드는 것이 아니다.

핵심 불변식을 DB가 직접 지키게 만드는 것이다.

순서는 다음처럼 잡는 것이 안전하다.

```text
1. 깨진 불변식을 문장으로 정의한다.
2. DB constraint나 원자적 update로 표현 가능한지 본다.
3. lock이 필요하면 대상 row와 획득 순서를 줄인다.
4. 트랜잭션 안의 외부 작업을 제거한다.
5. isolation level은 필요한 트랜잭션에만 올린다.
6. retry는 멱등성과 backoff를 갖춘 뒤 넣는다.
7. p95, p99, lock wait, retry rate로 효과를 검증한다.
```

### 1. 애플리케이션 if를 DB 불변식으로 바꾼다

위험한 코드는 보통 이렇게 생겼다.

```java
if (!couponIssueRepository.exists(couponId, userId)) {
    couponIssueRepository.save(new CouponIssue(couponId, userId));
}
```

이 코드는 단일 요청에서는 맞다.

하지만 동시에 실행되면 둘 다 `exists = false`를 볼 수 있다.

DB 제약으로 바꾼다.

```sql
ALTER TABLE coupon_issues
ADD CONSTRAINT uk_coupon_user UNIQUE (coupon_id, user_id);
```

그리고 insert 충돌을 비즈니스 응답으로 처리한다.

```text
insert 성공
  -> 발급 성공

duplicate key
  -> 이미 발급됨. 기존 발급 결과 반환 또는 409
```

### 2. read-modify-write를 조건부 update로 바꾼다

위험한 흐름은 다음이다.

```text
1. 현재 값을 읽는다.
2. 애플리케이션에서 조건을 판단한다.
3. 새 값을 계산한다.
4. update한다.
```

가능하면 다음으로 바꾼다.

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :product_id
  AND stock >= :quantity;
```

영향받은 row 수가 곧 결과다.

이 방식은 DB가 현재 값을 기준으로 조건을 판단하고 변경한다.

### 3. count 기반 의사결정을 counter나 slot으로 바꾼다

`SELECT COUNT(*)`는 의사결정에는 편하다.

하지만 그 count 결과가 lock으로 보호되지 않으면 동시에 들어온 트랜잭션들이 같은 결론을 낼 수 있다.

쿠폰 총량은 counter row로 바꾼다.

```sql
UPDATE coupon
SET issued_count = issued_count + 1
WHERE id = :coupon_id
  AND issued_count < total_quantity;
```

또는 slot 모델로 바꾼다.

```text
발급 가능한 10,000개 slot 생성
각 요청은 slot 하나를 점유
점유할 slot이 없으면 소진
```

어떤 방식이든 핵심은 같다.

범위나 count 조건을 DB가 원자적으로 보호할 수 있는 명시적 자원으로 바꾼다.

### 4. locking read는 필요한 곳에만 쓴다

`SELECT ... FOR UPDATE`는 판단과 변경 사이에 row를 보호해야 할 때 쓴다.

하지만 모든 select에 붙이면 안 된다.

단순 조회 화면에 locking read를 쓰면 읽기까지 쓰기 경합에 끌어들인다.

사용할 때는 다음을 확인한다.

- 트랜잭션이 짧은가
- 잠글 row가 명확한가
- WHERE 조건이 적절한 인덱스를 타는가
- 여러 row를 잠글 때 순서가 고정되어 있는가
- lock을 잡은 뒤 외부 API를 호출하지 않는가

### 5. isolation level은 필요한 트랜잭션에만 올린다

`SERIALIZABLE`은 강력하다.

하지만 모든 문제의 기본값으로 두면 처리량이 줄고 serialization failure가 늘 수 있다.

단일 row의 재고 차감은 조건부 update로 충분할 수 있다.

사용자별 1회 쿠폰은 unique constraint가 더 명확하다.

범위 겹침은 PostgreSQL exclusion constraint나 slot 모델이 더 직접적일 수 있다.

isolation level은 불변식을 표현할 수 있는 구조를 검토한 뒤, 필요한 경로에 제한적으로 올리는 편이 좋다.

### 6. retry는 작게, 멱등하게, 지터와 함께 넣는다

재시도 가능한 오류를 분류한다.

```text
deadlock victim
serialization failure
일부 lock wait timeout
transient network error
```

retry는 작게 둔다.

```text
retry count: 1~3회
backoff: 50ms -> 100ms -> 200ms
jitter: 랜덤 지연
deadline: 전체 timeout 예산 안에서만
```

그리고 멱등성이 있어야 한다.

결제 승인, 쿠폰 발급, 포인트 적립, 메시지 발송처럼 외부 부작용이 있는 작업은 idempotency key, unique constraint, outbox, 상태 테이블 없이 retry하면 안 된다.

### 7. 긴 작업은 outbox와 상태 전이로 분리한다

트랜잭션 안에서 메시지를 발행하거나 외부 API를 호출하지 않는다.

DB 변경과 발행할 이벤트 기록은 같은 트랜잭션으로 묶는다.

```sql
BEGIN;

UPDATE orders
SET status = 'PAID'
WHERE order_no = :order_no
  AND status = 'PAYMENT_PENDING';

INSERT INTO outbox_events(event_id, aggregate_id, type, payload, status)
VALUES (:event_id, :order_no, 'OrderPaid', :payload, 'READY');

COMMIT;
```

실제 메시지 발행은 relay가 처리한다.

이 방식은 상태 모델과 relay 운영이 추가된다.

대신 DB lock을 잡은 채 메시지 브로커를 기다리지 않아도 된다.

## 면접에서는 이렇게 답한다

질문은 이렇게 나올 수 있다.

> 트랜잭션을 사용했는데도 재고가 음수가 되거나 중복 쿠폰이 발급될 수 있나요? 가능하다면 왜 그런가요?

1분 답변은 이렇게 말할 수 있다.

가능합니다.

트랜잭션은 commit과 rollback을 보장하지만, 동시에 실행되는 트랜잭션 사이의 모든 논리적 충돌을 자동으로 막아주지는 않습니다. 특히 isolation level에 따라 같은 트랜잭션 안에서도 읽기 결과가 달라질 수 있고, MVCC를 쓰는 DB에서는 읽기가 최신값이 아니라 snapshot을 볼 수 있습니다.

재고 차감처럼 단일 row의 값 변경은 `UPDATE ... WHERE stock >= quantity`처럼 조건 검사와 변경을 하나의 원자적 update로 묶는 방식이 안전합니다.

쿠폰 중복 발급처럼 "이미 없으면 insert"하는 로직은 select 후 insert만으로 race condition이 생길 수 있으므로 `(coupon_id, user_id)` unique constraint로 불변식을 DB에 표현해야 합니다.

전체 수량 제한처럼 count나 범위 기반 규칙은 row lock만으로 부족할 수 있습니다. 이 경우 counter row를 조건부 update하거나, 발급 slot을 미리 만들거나, PostgreSQL exclusion constraint 또는 SERIALIZABLE isolation을 검토할 수 있습니다.

또한 deadlock이나 serialization failure는 트랜잭션 설계에서 발생할 수 있는 정상적인 충돌 신호입니다. 이때는 lock 획득 순서, 트랜잭션 길이, 인덱스, retry의 멱등성을 함께 봐야 합니다. 단순히 retry만 늘리면 부하가 증폭될 수 있으므로, 먼저 충돌 구조를 줄이고 재시도는 제한적으로 적용해야 합니다.

핵심 채점 포인트는 다음이다.

- 트랜잭션과 isolation level을 구분하는가
- MVCC가 최신 읽기를 보장하지 않는다는 점을 아는가
- read-modify-write의 race window를 설명하는가
- 조건부 update와 unique constraint를 해결책으로 제시하는가
- count/range 기반 규칙은 별도 모델링이 필요하다는 점을 아는가
- retry에는 멱등성이 필요하다는 점을 말하는가

꼬리 질문은 이렇게 이어질 수 있다.

### READ COMMITTED와 REPEATABLE READ에서 같은 select를 두 번 실행하면 어떤 차이가 생길 수 있나요?

`READ COMMITTED`에서는 각 statement가 시작될 때 커밋된 데이터를 기준으로 읽는다.

따라서 같은 트랜잭션 안에서도 두 번째 select는 그 사이 다른 트랜잭션이 커밋한 변경을 볼 수 있다.

`REPEATABLE READ`에서는 같은 트랜잭션 안에서 같은 snapshot을 유지하는 방향으로 동작한다. 그래서 첫 번째 읽기 이후 커밋된 변경이 보이지 않을 수 있다.

단, DB별 구현 차이가 있다. PostgreSQL의 repeatable read와 MySQL InnoDB의 repeatable read는 세부 동작이 다르므로 사용하는 DB 기준으로 확인해야 한다.

### lost update를 optimistic lock과 conditional update로 각각 어떻게 막을 수 있나요?

optimistic lock은 version 컬럼을 둔다.

읽을 때 version을 가져오고, update할 때 `WHERE version = old_version` 조건을 넣는다.

그 사이 누가 먼저 수정했다면 affected rows가 0이 되어 충돌을 감지한다.

conditional update는 조건 검사와 변경을 하나의 SQL로 합친다.

예를 들어 `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock >= 1`처럼 작성한다.

DB가 현재 값을 기준으로 조건을 검사하고 변경하므로 애플리케이션의 낡은 판단을 줄일 수 있다.

### 범위 조회 후 insert는 SERIALIZABLE 말고 어떻게 막을 수 있나요?

불변식을 DB가 직접 강제할 수 있는 형태로 바꾼다.

회의실 예약처럼 범위 겹침을 막아야 한다면 시간 slot으로 쪼개고 `(room_id, slot_start)` unique constraint를 둘 수 있다.

또는 같은 room row를 `FOR UPDATE`로 잠그고 해당 room의 예약 생성을 순차 처리할 수 있다.

PostgreSQL이라면 range type과 exclusion constraint로 "같은 room_id에서 period가 겹치면 안 된다"를 표현할 수도 있다.

쿠폰 총량처럼 최대 N개 규칙은 counter row를 조건부 update하거나 발급 slot을 미리 만들어 점유하는 방식으로 바꿀 수 있다.

## 요약

트랜잭션을 썼다는 사실만으로 동시성 안전성이 보장되지는 않는다.

무엇을 읽고, 무엇을 잠그고, 어떤 snapshot을 보고, 어떤 조건을 원자적으로 검사하는지가 더 중요하다.

ACID의 Isolation은 하나의 고정된 보장이 아니라 isolation level과 DB 구현에 따라 달라지는 정책이다. `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`은 성능과 정합성 사이의 선택지를 만든다.

write lock은 쓰기 충돌을 조정하지만, 애플리케이션이 이전에 읽은 값으로 내린 판단까지 자동으로 보호하지 않는다. lost update를 피하려면 조건 검사와 변경을 DB의 원자적 연산으로 묶거나 version check를 사용해야 한다.

MVCC는 읽기와 쓰기의 충돌을 줄이지만 최신 상태를 항상 보여주지는 않는다. 오래 열린 트랜잭션은 과거 버전을 붙잡아 정리 지연과 성능 저하를 만들 수 있다.

phantom read와 count 기반 의사결정은 특히 위험하다. 없는 row나 범위 조건을 근거로 insert하는 로직은 unique constraint, counter row, slot 모델, locking strategy, serializable isolation 중 적절한 보호 장치가 필요하다.

deadlock은 단순 DB 오류가 아니라 lock 획득 순서와 트랜잭션 경계가 충돌했다는 신호다. 일시적 충돌은 retry할 수 있지만, 반복되는 deadlock은 구조를 고쳐야 한다.

가장 중요한 질문은 이것이다.

> 이 비즈니스 불변식은 DB가 원자적으로 지킬 수 있는 형태로 표현되어 있는가?

이 질문에 답할 수 있을 때 트랜잭션은 단순한 `@Transactional`이 아니라, 동시 요청 속에서도 결과를 하나로 수렴시키는 설계 도구가 된다.
