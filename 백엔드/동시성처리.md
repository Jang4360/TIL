# 같은 주문이 두 번 처리되는 Race Condition은 어떻게 막는가

주문 API는 성공을 한 번만 반환했다.

그런데 결제 승인 내역은 두 건이 생겼다. 사용자는 버튼을 한 번 눌렀다고 말하고, 프론트 로그에도 클릭 이벤트는 한 번만 남아 있다. 그런데 서버 로그를 보면 같은 주문 생성 요청이 거의 같은 시각에 두 번 들어와 있다.

처음에는 이상하게 느껴진다.

코드에서는 이미 주문 상태를 확인한다. 주문이 없으면 만들고, 결제가 안 됐으면 승인하고, 처리 완료 상태로 바꾼다. 단일 요청만 보면 틀린 곳이 없어 보인다.

하지만 문제는 이 코드가 동시에 실행될 때도 맞는지다.

단일 요청 기준으로 맞는 코드와, 동시에 여러 번 실행되어도 결과가 하나로 수렴하는 코드는 다르다.

> 같은 비즈니스 행위를 한 번만 처리하려면 애플리케이션의 `if` 체크가 아니라, idempotency key, unique constraint, transaction boundary, lock, outbox를 조합해 중복 실행되어도 결과가 하나로 수렴하는 구조를 만들어야 한다.

---

## 먼저 구조를 잡자

주문 중복 처리는 보통 다음 흐름에서 터진다.

```text
1. 클라이언트가 주문 생성 또는 결제 요청을 보낸다.
2. 서버가 주문 또는 결제 이력을 조회한다.
3. 아직 처리되지 않았다고 판단한다.
4. 결제 승인, 재고 차감, 쿠폰 사용 같은 부작용을 실행한다.
5. DB에 처리 완료 상태를 저장한다.
6. 이벤트를 발행해 배송, 알림, 정산 시스템으로 넘긴다.
```

단일 요청만 보면 자연스러운 순서다.

하지만 두 요청이 거의 동시에 들어오면 2번과 5번 사이가 열린 창이 된다. 첫 번째 요청이 아직 커밋하기 전에 두 번째 요청도 "아직 처리되지 않았다"고 판단할 수 있다.

간단히 보면 이런 코드가 위험하다.

```java
Order order = orderRepository.findByOrderNo(orderNo);

if (order == null) {
    orderRepository.save(new Order(orderNo, userId, amount));
    paymentClient.approve(orderNo, amount);
}
```

문제는 `findByOrderNo`와 `save` 사이에 다른 요청이 끼어들 수 있다는 점이다.

"조회 후 없으면 생성"은 읽기 쉬운 코드지만, 동시성 관점에서는 원자적이지 않다.

이 문제를 풀려면 책임을 나눠 봐야 한다.

- 요청 식별: 이 요청이 이전 요청과 같은 비즈니스 행위인지 구분한다.
- 상태 보호: 같은 주문 또는 결제 건을 두 요청이 동시에 바꾸지 못하게 한다.
- 부작용 제어: 외부 결제, 메시지 발행, 재고 차감이 중복 실행되지 않게 한다.
- 실패 복구: 중간에 죽어도 나중에 같은 결과로 수렴하게 한다.

여기서 idempotency key는 "같은 요청인지"를 식별한다.

unique constraint는 "DB에 같은 결과가 두 개 생기지 않게" 막는다.

transaction boundary는 "어디까지를 하나의 원자적 변경으로 볼지"를 정한다.

distributed lock은 "여러 서버 인스턴스 사이에서 동시에 같은 키를 처리하지 않게" 한다.

outbox는 "DB 변경과 이벤트 발행 사이의 불일치"를 줄인다.

중요한 점은 하나의 기술이 모든 문제를 해결하지 않는다는 것이다.

unique constraint는 중복 row를 막지만 외부 결제 API 중복 호출을 막지는 못한다.

distributed lock은 동시 실행을 줄이지만 락 만료, 네트워크 지연, 프로세스 중단 같은 실패 모드를 새로 만든다.

outbox는 이벤트 유실을 줄이지만 소비자 멱등성까지 자동으로 보장하지는 않는다.

## 내부에서는 무슨 일이 일어나는가

### 조회 후 생성은 원자적이지 않다

문제는 "이미 주문이 있는지 확인했는데도 두 개가 생긴다"는 현상이다.

원인은 조회와 생성이 하나의 원자적 연산이 아니기 때문이다.

두 요청 A, B가 같은 주문 번호 `ORD-1`을 처리한다고 해보자.

```text
1. A가 SELECT * FROM orders WHERE order_no = 'ORD-1'을 실행한다.
2. 결과가 없다.
3. B도 같은 SELECT를 실행한다.
4. 결과가 없다.
5. A가 INSERT한다.
6. B도 INSERT한다.
```

애플리케이션 입장에서는 둘 다 "없는 것을 확인하고 만들었다."

하지만 DB 입장에서는 두 트랜잭션이 서로의 미커밋 변경을 보지 못했거나, 애초에 중복을 막는 제약이 없었기 때문에 둘 다 성공할 수 있다.

이때 가장 기본적인 방어선은 unique constraint다.

```sql
ALTER TABLE orders
ADD CONSTRAINT uk_orders_order_no UNIQUE (order_no);
```

이 제약이 있으면 두 요청이 동시에 insert하더라도 최종적으로 하나만 성공한다. 나머지 하나는 duplicate key 오류를 받는다.

여기서 끝나면 부족하다.

duplicate key를 그대로 500으로 반환하면 사용자는 실패로 느낀다. 같은 idempotency key의 재시도라면 기존 결과를 조회해 같은 응답을 돌려주는 것이 더 맞다.

즉 unique constraint는 데이터가 깨지는 것을 막는 하한선이고, idempotency 처리는 API 의미와 사용자 경험을 보존하는 상위 설계다.

### Idempotency key는 요청이 아니라 의도를 식별한다

문제는 네트워크 재시도, 브라우저 새로고침, 앱 중복 탭, 게이트웨이 retry 때문에 같은 요청이 여러 번 들어올 수 있다는 점이다.

서버는 이 요청들이 같은 비즈니스 행위인지 알아야 한다.

idempotency key는 "이 요청을 한 번만 처리해 달라"는 클라이언트와 서버 사이의 식별자다.

예를 들어 결제 요청에 다음 헤더를 붙인다.

```http
POST /payments
Idempotency-Key: pay-20260620-user1-cart5
```

서버는 이 키로 처리 이력을 저장한다.

```sql
CREATE TABLE idempotency_keys (
    idempotency_key VARCHAR(128) PRIMARY KEY,
    request_hash VARCHAR(128) NOT NULL,
    status VARCHAR(20) NOT NULL,
    response_code INTEGER,
    response_body JSON,
    resource_type VARCHAR(50),
    resource_id VARCHAR(128),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    expires_at TIMESTAMP NOT NULL
);
```

처리 흐름은 다음에 가깝다.

```text
1. idempotency key를 먼저 insert한다.
2. 이미 존재하면 기존 처리 상태를 확인한다.
3. 완료 상태면 저장된 응답을 반환한다.
4. 진행 중이면 409 Conflict 또는 202 Accepted를 반환한다.
5. 신규 키면 실제 비즈니스 처리를 진행한다.
6. 성공하면 응답 또는 결과 리소스 참조를 저장한다.
```

Stripe 문서도 idempotency key를 사용해 같은 요청의 재시도를 안전하게 처리하고, 같은 key로 다시 들어온 요청에는 첫 요청의 결과를 반환하는 모델을 설명한다. AWS Builders Library도 retry를 안전하게 만들기 위한 API 계약으로 idempotency token을 다룬다.

핵심은 idempotency key가 "요청을 한 번만 받겠다"는 뜻이 아니라는 점이다.

서버는 같은 요청을 여러 번 받을 수 있다. 대신 결과가 한 번 처리된 것처럼 수렴해야 한다.

### request_hash는 key 재사용 버그를 막는다

idempotency key만 보면 위험하다.

같은 key로 완전히 다른 요청이 들어올 수 있기 때문이다.

첫 번째 요청이 이렇게 들어왔다고 해보자.

```http
POST /payments
Idempotency-Key: abc-123
```

```json
{
  "orderId": "order-1",
  "amount": 10000,
  "items": ["A"]
}
```

서버는 결제를 성공시키고 다음 정보를 저장한다.

```text
key: abc-123
request_hash: hash(orderId=order-1, amount=10000, items=A)
status: SUCCESS
response: { paymentId: "pay-1", status: "paid" }
```

네트워크가 끊겨 클라이언트가 응답을 못 받았다.

그래서 같은 요청을 다시 보낸다.

```json
{
  "orderId": "order-1",
  "amount": 10000,
  "items": ["A"]
}
```

이 경우 `request_hash`가 같다.

서버는 같은 요청의 재시도라고 판단하고 기존 응답을 반환하면 된다.

문제는 두 번째 요청이 이렇게 들어오는 경우다.

```http
POST /payments
Idempotency-Key: abc-123
```

```json
{
  "orderId": "order-2",
  "amount": 500000,
  "items": ["MacBook"]
}
```

idempotency key는 같다.

하지만 요청의 의미는 완전히 다르다.

서버가 key만 보고 기존 응답을 반환하면, 500,000원 결제 요청에 대해 10,000원 결제 성공 응답을 붙여주는 꼴이 된다.

그래서 같은 key로 다른 `request_hash`가 들어오면 보통 거부해야 한다.

```http
409 Conflict
```

```json
{
  "error": "IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST",
  "message": "Same idempotency key was used with a different request body."
}
```

request_hash에는 비즈니스 결과를 바꾸는 필드를 넣는다.

결제라면 다음 필드가 중요하다.

- `orderId`
- `amount`
- `currency`
- `merchantId`
- `items`
- `customerId`
- `paymentMethodId`

반대로 매번 달라질 수 있지만 결과에 영향이 없는 값은 빼는 경우가 많다.

- `clientTimestamp`
- `traceId`
- `deviceInfo`
- `userAgent`

주의할 점은 JSON 문자열 그대로 해시하면 안 된다는 것이다.

아래 두 요청은 의미상 같지만 문자열은 다르다.

```json
{
  "amount": 10000,
  "orderId": "order-1"
}
```

```json
{
  "orderId": "order-1",
  "amount": 10000
}
```

필드 순서와 공백 차이 때문에 다른 해시가 나오면 정상 재시도를 거부할 수 있다.

그래서 canonical JSON처럼 정규화하거나, 중요한 필드만 뽑아 안정적인 순서로 직렬화한 뒤 해시하는 편이 좋다.

### Idempotency record는 마지막이 아니라 시작할 때 잡아야 한다

idempotency 기록을 마지막에만 남기면 중복 실행을 막기 어렵다.

```text
1. 실제 작업 성공
2. idempotency record 저장 전에 서버 장애
3. 클라이언트 재시도
4. 서버는 처음 보는 요청으로 판단
5. 중복 결제, 중복 주문, 중복 발행 발생
```

마지막 기록 방식은 처리 결과 로그에 가깝다.

진짜 guard로 쓰려면 요청 시작 시점에 key를 선점해야 한다.

```text
1. idempotency_key insert
   - status = PROCESSING
   - request_hash = ...
2. insert에 성공한 요청만 실제 작업 수행
3. 작업 성공 시 SUCCESS와 response 저장
4. 작업 실패 시 FAILED 또는 재시도 가능 상태로 변경
```

여기서도 DB unique constraint가 필요하다.

```sql
ALTER TABLE idempotency_keys
ADD CONSTRAINT uk_idempotency_key UNIQUE (idempotency_key);
```

동시에 같은 key 요청이 두 개 들어오면 둘 중 하나만 insert에 성공해야 한다. 나머지는 unique violation을 보고 기존 레코드를 조회해야 한다.

상태는 보통 다음처럼 둔다.

| 상태 | 의미 | 재요청 처리 |
| --- | --- | --- |
| `PROCESSING` | 누군가 처리 중 | 409, 202, 짧은 대기 후 조회 |
| `SUCCESS` | 완료됨 | 저장된 응답 또는 결과 리소스 반환 |
| `FAILED_RETRYABLE` | 일시 실패 | 재시도 가능 |
| `FAILED_FINAL` | 최종 실패 | 저장된 실패 응답 반환 |
| `EXPIRED` | 보관 기간 만료 | 정책에 따라 신규 요청 또는 거부 |

중요한 점은 `PROCESSING`이 영원히 남을 수 있다는 것이다.

서버가 작업 중 죽으면 key는 잡혔지만 결과가 저장되지 않는다. 이 상태를 복구하려면 timeout과 reconciliation 경로가 필요하다.

### Transaction boundary는 보호 범위를 결정한다

트랜잭션을 걸었는데도 중복 부작용이 발생할 수 있다.

원인은 DB transaction이 보호하는 범위와 실제 부작용의 범위가 다르기 때문이다.

DB transaction은 DB 안의 변경을 원자적으로 묶는다.

하지만 외부 결제 API 호출, 메시지 브로커 publish, 이메일 발송은 DB transaction 안에 자연스럽게 포함되지 않는다.

이런 코드가 대표적으로 위험하다.

```java
@Transactional
public void pay(String orderNo) {
    Order order = orderRepository.findByOrderNo(orderNo);
    paymentClient.approve(orderNo); // 외부 부작용
    order.markPaid();
}
```

겉으로는 transaction 안에 있으니 안전해 보인다.

하지만 `paymentClient.approve`가 성공한 뒤 DB 커밋 전에 서버가 죽으면 결제는 됐는데 주문 상태는 미결제로 남을 수 있다.

반대로 DB 상태를 먼저 바꾸고 메시지 발행에 실패하면 주문은 완료됐는데 배송 시스템은 모를 수 있다.

transaction boundary를 정할 때는 DB 정합성과 외부 부작용 정합성을 분리해야 한다.

DB 안에서만 끝나는 중복 생성은 unique constraint와 transaction으로 강하게 막을 수 있다.

외부 시스템이 끼는 순간에는 멱등 API, outbox, 재처리 작업, 상태 머신이 함께 필요하다.

### 조건부 update는 확인과 변경을 하나로 합친다

재고 차감 예시를 보자.

재고 1개 남은 상품에 대해 두 주문이 동시에 들어오면 둘 다 `stock > 0`을 보고 차감할 수 있다.

위험한 흐름은 다음과 같다.

```text
1. SELECT stock FROM products WHERE product_id = 10;
2. stock이 1보다 크면
3. UPDATE products SET stock = stock - 1;
```

확인과 변경 사이에 다른 요청이 끼어들 수 있다.

이럴 때는 조건부 update가 더 낫다.

```sql
UPDATE products
SET stock = stock - 1
WHERE product_id = 10
  AND stock > 0;
```

영향받은 row 수가 1이면 성공이다.

0이면 이미 다른 요청이 차감했거나 재고가 부족한 것이다.

쿠폰 사용도 비슷하다.

```sql
UPDATE coupons
SET used = TRUE,
    used_at = NOW()
WHERE coupon_id = ?
  AND used = FALSE;
```

영향받은 row 수가 1인 요청만 쿠폰 사용에 성공한다.

이 방식은 "조회 후 변경"을 하나의 DB 연산으로 합친다.

다만 조건부 update만으로 외부 API 중복 호출까지 막을 수는 없다. 외부 호출 전후의 상태 전이와 idempotency key가 함께 필요하다.

### Distributed lock은 실행을 줄이지만 정답은 아니다

서버가 여러 대일 때 JVM 내부 `synchronized`나 local lock은 충분하지 않다.

같은 주문 요청이 서로 다른 인스턴스로 라우팅되면 각 인스턴스는 자신만의 메모리 락만 보고 동시에 실행할 수 있다.

그래서 Redis, ZooKeeper, DB advisory lock 같은 distributed lock을 고려한다.

예를 들어 `lock:order:ORD-1` 키를 잡은 요청만 주문 처리를 진행하게 만든다.

Redis라면 보통 다음 형태다.

```text
SET lock:order:ORD-1 {token} NX PX 3000
```

Redis 공식 문서도 `NX`, `PX`와 고유한 random value를 이용한 락 패턴을 설명한다. 여기서 token은 락 해제 시 자신이 잡은 락인지 확인하기 위해 필요하다.

하지만 distributed lock은 "한 번에 하나만 실행될 가능성"을 높여줄 뿐, 정합성의 최종 방어선으로 두기에는 불안하다.

- TTL이 너무 짧으면 작업 중 락이 만료된다.
- TTL이 너무 길면 프로세스 장애 후 처리가 오래 막힌다.
- 네트워크 지연이나 GC pause로 락 보유 시간이 흔들릴 수 있다.
- Redis failover 상황에서 락 소유 판단이 복잡해질 수 있다.
- 락 획득 후 DB 저장 전에 죽으면 결과는 여전히 불완전하다.

distributed lock은 충돌 빈도를 낮추는 장치다.

데이터의 최종 정합성은 unique constraint, 조건부 update, 상태 전이 검증, idempotency record 같은 저장소 수준의 불변조건으로 지켜야 한다.

락을 넣었다고 unique constraint를 제거하면 위험하다.

락은 실행 순서를 조절하는 장치이고, unique constraint는 잘못된 결과가 저장되지 않게 막는 장치다. 둘은 대체 관계가 아니라 보완 관계다.

### Outbox는 DB는 성공했는데 이벤트는 실패한 상황을 다룬다

주문은 정상 생성됐는데 배송, 알림, 정산 시스템이 이벤트를 받지 못할 수 있다.

반대로 이벤트는 발행됐는데 DB transaction이 rollback되면 존재하지 않는 주문을 후속 시스템이 처리할 수도 있다.

outbox 패턴은 비즈니스 테이블 변경과 이벤트 기록을 같은 DB transaction에 저장한다.

```sql
BEGIN;

INSERT INTO orders(order_no, status)
VALUES ('ORD-1', 'PAID');

INSERT INTO outbox_events(event_id, aggregate_id, type, payload, status)
VALUES ('EVT-1', 'ORD-1', 'OrderPaid', '{...}', 'READY');

COMMIT;
```

이후 별도 relay가 outbox table을 읽어 메시지 브로커로 발행한다.

```text
1. outbox_events에서 READY 이벤트 조회
2. 메시지 브로커로 발행
3. 성공하면 SENT 또는 published_at 기록
4. 실패하면 남겨두고 재시도
```

핵심은 이벤트 발행 자체를 DB transaction 안에서 바로 하지 않는다는 점이다.

대신 "나중에 반드시 발행해야 할 이벤트"를 DB에 먼저 안전하게 기록한다. 서버가 중간에 죽어도 outbox 테이블에 남아 있는 이벤트를 보고 다시 발행할 수 있다.

Microservices.io의 transactional outbox 패턴도 메시지 relay가 같은 메시지를 두 번 발행할 수 있으므로 소비자가 멱등적이어야 한다고 설명한다.

outbox는 이벤트 유실을 줄인다.

하지만 중복 발행을 완전히 없애지는 않는다.

relay가 브로커에 publish한 직후 outbox 상태를 `SENT`로 바꾸기 전에 죽으면 같은 이벤트를 다시 발행할 수 있다.

그래서 소비자도 `event_id` 기준으로 멱등 처리해야 한다.

### Inbox 또는 processed_messages는 소비자 중복 처리를 막는다

메시지 시스템은 중복 전달될 수 있다.

AWS SQS Standard Queue 문서도 at-least-once delivery를 제공하며, 분산 구조상 메시지 사본이 한 번 이상 전달될 수 있음을 설명한다. Kafka도 at-least-once 설정에서는 producer가 응답을 받지 못하면 resend할 수 있고, 이 과정에서 중복이 생길 수 있다.

그래서 소비자는 같은 메시지를 여러 번 받아도 결과가 하나로 수렴해야 한다.

가장 단순한 방식은 처리한 이벤트 ID를 저장하는 것이다.

```sql
CREATE TABLE processed_messages (
    consumer_name VARCHAR(100) NOT NULL,
    message_id VARCHAR(128) NOT NULL,
    processed_at TIMESTAMP NOT NULL,
    PRIMARY KEY (consumer_name, message_id)
);
```

소비 흐름은 다음처럼 잡을 수 있다.

```text
1. 메시지를 받는다.
2. processed_messages에 message_id를 insert한다.
3. 이미 있으면 중복 메시지로 보고 skip한다.
4. insert에 성공한 경우에만 비즈니스 로직을 수행한다.
5. 같은 transaction 안에서 결과 변경을 commit한다.
```

이 구조도 트레이드오프가 있다.

processed_messages가 계속 늘어난다. 보관 기간과 purge 정책이 필요하다.

또 메시지 처리 중 외부 API를 호출한다면 그 외부 부작용까지 자동으로 멱등해지지는 않는다. 소비자 안에서도 idempotency key나 외부 요청 고유 ID를 사용해야 한다.

## 언제 문제가 되는가

Race Condition은 테스트 환경에서 잘 안 보인다.

요청이 적고, 네트워크가 안정적이고, gateway retry나 queue redelivery가 잘 발생하지 않기 때문이다.

하지만 운영 중인 시스템에서는 같은 요청이 한 번만 온다는 가정이 쉽게 깨진다.

### 결제 승인

사용자가 주문 버튼을 눌렀다.

응답이 늦어지자 앱은 timeout으로 재시도한다. API Gateway도 5xx 또는 timeout에 대해 retry를 한 번 수행한다. 사용자는 같은 주문 의도를 한 번 표현했지만, 서버에는 같은 주문 번호 또는 같은 장바구니에 대한 요청이 두세 개 들어온다.

가장 위험한 흐름은 다음과 같다.

```text
1. 첫 번째 요청이 주문 row를 조회한다.
2. 아직 결제 완료 이력이 없다.
3. 외부 PG에 승인 요청을 보낸다.
4. PG 승인은 성공한다.
5. 서버가 DB에 완료 상태를 저장하기 전에 timeout 또는 프로세스 종료가 발생한다.
6. 두 번째 요청이 다시 들어온다.
7. DB에는 아직 결제 완료 상태가 없다.
8. 두 번째 요청도 PG 승인 요청을 보낸다.
```

DB만 보면 "미결제였으니 결제했다"는 코드가 정상처럼 보인다.

하지만 외부 결제 시스템에서는 같은 의도가 두 번 승인될 수 있다.

특히 PG idempotency key를 넘기지 않았거나, 내부 payment attempt와 PG transaction id를 제대로 매핑하지 않으면 복구가 어렵다.

Stripe PaymentIntent 문서는 같은 구매에 대해 중복 PaymentIntent 생성을 막기 위해 idempotency key를 제공하라고 안내한다. 또한 네트워크 오류처럼 성공 여부를 알 수 없는 경우에는 객체 상태를 조회하거나 webhook을 통해 결과를 확인하는 방식이 필요하다.

### 재고 차감

재고 1개 남은 상품에 대해 두 주문이 동시에 들어온다.

둘 다 `stock > 0`을 조회하고 차감하면 재고가 음수가 되거나 두 주문이 모두 성공할 수 있다.

이 경우 핵심은 확인과 변경을 분리하지 않는 것이다.

```sql
UPDATE products
SET stock = stock - 1
WHERE product_id = 10
  AND stock > 0;
```

영향받은 row 수가 1이면 성공, 0이면 실패로 처리한다.

인기 상품처럼 같은 row에 쓰기가 몰리는 경우에는 조건부 update만으로도 lock wait이 커질 수 있다. 이때는 재고 예약 테이블, 큐 기반 직렬화, 샤딩된 재고 버킷 같은 구조를 검토할 수 있다.

### 쿠폰 사용

쿠폰도 비슷하다.

```text
1. coupon.used = false 조회
2. 아직 안 썼다고 판단
3. 할인 적용
4. coupon.used = true 저장
```

동시에 두 요청이 들어오면 둘 다 2번을 통과할 수 있다.

해결은 조건부 update 또는 사용 이력 unique constraint다.

```sql
UPDATE coupons
SET used = TRUE,
    used_at = NOW()
WHERE coupon_id = ?
  AND used = FALSE;
```

또는 사용 이력을 별도 테이블에 둔다.

```sql
CREATE TABLE coupon_usages (
    coupon_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    used_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_coupon_usage_coupon UNIQUE (coupon_id)
);
```

어떤 기준이 유일해야 하는지 먼저 정해야 한다.

쿠폰이 사용자당 한 번인지, 쿠폰 자체가 한 번인지, 주문당 한 번인지에 따라 unique constraint가 달라진다.

### 메시지 중복 소비

주문 생성 이벤트가 두 번 소비될 수 있다.

브로커가 적어도 한 번 전달을 보장하거나, consumer가 ack 전에 죽거나, relay가 같은 outbox 이벤트를 다시 발행하면 같은 이벤트가 다시 들어온다.

이때 소비자가 단순히 "이벤트가 왔으니 포인트 지급"을 실행하면 포인트가 중복 지급될 수 있다.

해결은 이벤트 ID 또는 비즈니스 key 기준 멱등 처리다.

```sql
INSERT INTO processed_messages(consumer_name, message_id, processed_at)
VALUES ('point-consumer', 'EVT-1', NOW());
```

insert가 성공한 경우에만 포인트를 지급한다.

이미 존재하면 같은 이벤트를 처리한 적이 있으므로 skip한다.

### timeout budget이 어긋난 경우

클라이언트 timeout이 2초, API Gateway timeout이 3초, 서버 내부 PG 호출 timeout이 5초라고 하자.

바깥쪽이 먼저 끊고 재시도할 수 있다.

서버는 아직 처리 중인데 클라이언트와 gateway는 실패로 판단한다. 그래서 같은 요청이 다시 들어온다.

timeout은 계층별로 맞춰야 한다.

```text
client timeout > gateway timeout > server timeout > downstream timeout
```

항상 이 공식이 그대로 맞는 것은 아니지만, 중요한 원칙은 바깥 계층이 내부 작업의 결과를 기다릴 수 있는 예산을 가져야 한다는 점이다.

내부 호출이 더 오래 걸리면 바깥쪽은 실패로 판단하고 재시도하는데, 내부 작업은 계속 진행되는 모순이 생긴다.

## 트레이드오프

동시성 처리에는 하나의 정답이 없다.

각 장치는 얻는 것이 있고 잃는 것이 있다.

### unique constraint

unique constraint는 가장 강한 최종 방어선이다.

얻는 것은 DB 수준의 불변조건이다. 애플리케이션 버그가 있거나 요청이 동시에 들어와도 같은 `order_no`, `payment_attempt_id`, `coupon_id`가 중복 저장되지 않는다.

잃는 것은 충돌을 비즈니스 응답으로 해석해야 하는 복잡도다.

duplicate key 오류를 그대로 500으로 내보내면 안 된다. 같은 idempotency key의 재시도라면 기존 결과를 반환하고, 다른 요청이라면 409 Conflict처럼 의미 있는 응답으로 바꿔야 한다.

주의할 점은 중복 기준이 명확하지 않은 상태에서 제약부터 걸면 정상 요청까지 막을 수 있다는 것이다.

예를 들어 `order_id` 하나에 결제 시도가 여러 번 있을 수 있다면 `payments(order_id)` unique는 너무 강하다. 카드 A 실패 후 카드 B 재결제가 막힐 수 있다. 이 경우에는 `payment_attempt_id`나 `(order_id, attempt_no)`가 더 적절할 수 있다.

### idempotency key

idempotency key는 재시도를 안전하게 만든다.

얻는 것은 같은 요청이 여러 번 들어와도 같은 결과를 반환할 수 있는 API 의미다.

잃는 것은 key 저장소, request_hash 검증, TTL, 진행 중 상태 처리, 응답 캐싱 같은 관리 비용이다.

클라이언트가 매 요청마다 새로운 key를 만들면 멱등성이 동작하지 않는다.

반대로 같은 key를 서로 다른 요청에 재사용하면 conflict가 늘어난다. 그래서 request_hash 검증이 필요하다.

TTL도 트레이드오프다.

- TTL이 너무 짧으면 늦은 재시도를 막지 못한다.
- TTL이 너무 길면 저장소가 커진다.
- 결제나 송금처럼 고객 문의와 재처리 기간이 긴 도메인은 더 오래 보관해야 할 수 있다.

Stripe 문서는 idempotency key를 일정 시간이 지나면 제거할 수 있고, 제거 후 재사용된 key는 새 요청으로 처리될 수 있다고 설명한다. 그래서 각 시스템은 "얼마나 늦게 같은 요청이 다시 올 수 있는가"를 기준으로 TTL을 정해야 한다.

### request_hash

request_hash는 같은 key로 다른 payload가 들어오는 문제를 막는다.

얻는 것은 안전한 응답 재사용이다.

잃는 것은 canonicalization 복잡도다.

JSON 필드 순서, 공백, 기본값, 숫자 표현, null 처리 때문에 의미상 같은 요청이 다른 hash를 만들 수 있다. 반대로 중요한 필드를 빼면 서로 다른 요청이 같은 hash로 보일 수 있다.

그래서 "모든 문자열을 그대로 해시"보다 "결과를 바꾸는 필드만 정규화해서 해시"하는 편이 좋다.

### 짧은 transaction

transaction을 짧게 나누면 lock 보유 시간과 DB connection 점유가 줄어든다.

얻는 것은 처리량과 장애 격리다.

잃는 것은 상태 모델이 복잡해진다는 점이다.

`CREATED`, `PAYMENT_PENDING`, `PAID`, `PAYMENT_FAILED`, `CANCEL_REQUESTED` 같은 중간 상태를 제대로 다뤄야 한다. 실패 보정 작업도 필요하다.

긴 transaction 하나로 모든 일을 감싸면 코드는 단순해 보일 수 있다. 하지만 외부 API 호출과 메시지 발행이 섞이는 순간 DB transaction만으로 전체 정합성을 보장할 수 없다.

### 조건부 update

조건부 update는 확인과 변경을 하나의 DB 연산으로 합친다.

얻는 것은 race window 축소다.

잃는 것은 상태 전이를 명확히 설계해야 하는 부담이다.

```sql
UPDATE orders
SET status = 'PAYMENT_PENDING'
WHERE order_no = ?
  AND status = 'CREATED';
```

영향받은 row 수가 0이면 이미 상태가 바뀐 것이다.

이걸 오류로 볼지, 기존 결과를 반환할지, 현재 상태를 조회해 분기할지 정책이 필요하다.

### distributed lock

distributed lock은 같은 key에 대한 동시 실행을 줄인다.

얻는 것은 외부 API 중복 호출 감소와 hot key 충돌 완화다.

잃는 것은 락 TTL, owner token, failover, lease 만료, lock holder 장애라는 새로운 실패 모드다.

쓰면 안 되는 방식은 락만으로 정합성을 보장하는 것이다.

락이 풀리거나 중복 획득되는 순간 데이터가 깨진다면 설계가 취약하다.

distributed lock은 앞단의 충돌 완화 장치로 쓰고, 뒤에는 unique constraint와 조건부 update를 둬야 한다.

### outbox

outbox는 DB 변경과 이벤트 발행 사이의 유실을 줄인다.

얻는 것은 커밋된 비즈니스 변경을 나중에라도 발행할 수 있는 복구 가능성이다.

잃는 것은 relay, outbox table 증가, 중복 발행, consumer deduplication 관리다.

outbox는 exactly-once를 보장하지 않는다.

message relay가 같은 이벤트를 두 번 발행할 수 있고, 브로커도 중복 전달할 수 있다. 그래서 소비자는 event_id 기준으로 멱등해야 한다.

### retry

retry는 일시적 충돌과 네트워크 오류를 흡수한다.

얻는 것은 순간적인 timeout, deadlock victim, duplicate conflict 이후의 회복력이다.

잃는 것은 부하 증폭과 부작용 중복 위험이다.

AWS Builders Library의 retry/backoff 글도 side effect가 있는 API는 idempotency 없이는 안전하게 retry하기 어렵다고 설명한다.

retry는 실패를 감추는 장치가 아니다.

재실행해도 안전한 작업에만 붙일 수 있는 장치다.

## 어떻게 분석할까

중복 처리를 분석할 때는 먼저 중복의 기준을 확정해야 한다.

"주문 row가 두 개 생겼다"와 "결제 승인이 두 번 됐다"와 "이벤트가 두 번 소비됐다"는 서로 다른 문제다.

같은 사용자의 같은 장바구니인지, 같은 `order_no`인지, 같은 idempotency key인지, 같은 `payment_attempt_id`인지 기준을 분리해야 한다.

### 1. 중복 결과의 key를 찾는다

먼저 실제로 중복된 결과를 기준으로 잡는다.

```text
orders.order_no
payments.payment_attempt_id
payments.pg_transaction_id
coupon_usages.coupon_id
outbox_events.event_id
processed_messages.message_id
```

중복된 결과의 key가 없으면 분석이 어려워진다.

그래서 애초에 로그와 테이블에 추적 가능한 key를 남겨야 한다.

### 2. 요청 로그를 시간순으로 모은다

같은 key에 대한 요청 로그를 시간순으로 모은다.

봐야 할 값은 다음이다.

- idempotency key
- request_hash
- order_no
- payment_attempt_id
- external transaction id
- trace_id
- request start time
- downstream call time
- DB commit time
- response time
- retry count

단순히 API가 두 번 호출됐다는 것보다 첫 요청이 어디까지 성공했는지가 중요하다.

### 3. retry가 어디서 발생했는지 나눈다

retry는 여러 곳에서 발생한다.

```text
client retry
API Gateway retry
server internal retry
message broker redelivery
worker retry
operator manual retry
batch re-run
```

같은 중복 요청이라도 원인이 다르다.

클라이언트 timeout 때문에 생긴 중복과, consumer ack 실패 때문에 생긴 중복은 대응이 다르다.

### 4. DB 제약과 충돌을 확인한다

DB에서는 unique constraint가 실제로 있는지 확인한다.

PostgreSQL이라면 `ON CONFLICT`, MySQL이라면 `INSERT ... ON DUPLICATE KEY UPDATE` 같은 구문을 사용할 수 있다. 두 방식 모두 unique index 또는 primary key 같은 충돌 기준이 있어야 의미가 있다.

봐야 할 것은 다음이다.

- 중복을 막아야 하는 컬럼에 unique constraint가 있는가
- 제약 기준이 비즈니스 중복 기준과 맞는가
- duplicate key 오류가 발생하고 있는가
- 발생한 duplicate key를 애플리케이션이 500으로 반환하고 있지는 않은가
- upsert가 의도치 않게 기존 데이터를 덮어쓰고 있지는 않은가

duplicate key 오류가 증가했다면 방어선이 작동하고 있다는 뜻일 수 있다.

반대로 duplicate key 오류가 전혀 없는데 중복 데이터가 생긴다면 제약이 없거나 기준이 잘못됐을 가능성이 크다.

### 5. timeout budget을 확인한다

timeout이 중복 요청을 만든다.

다음 값을 나란히 봐야 한다.

- client timeout
- API Gateway timeout
- server request timeout
- DB timeout
- external payment API timeout
- message visibility timeout
- worker processing timeout

바깥쪽 timeout이 안쪽 timeout보다 짧으면 바깥쪽은 실패로 판단하고 재시도하지만, 안쪽 작업은 계속 진행될 수 있다.

이 상태에서 idempotency key가 없으면 중복 실행이 발생한다.

### 6. outbox와 consumer 상태를 본다

outbox row가 `READY`에 오래 머무르면 relay가 막힌 것이다.

`SENT`인데 consumer 처리가 안 됐다면 브로커 또는 소비자 문제일 수 있다.

같은 `event_id`가 여러 번 소비됐다면 중복 전달 자체는 정상일 수 있다. 문제는 consumer deduplication이 없는 것이다.

봐야 할 지표는 다음이다.

- outbox READY count
- relay publish failure count
- event publish latency
- consumer duplicate skip count
- consumer retry count
- dead letter queue count
- message age

### 7. metric을 같이 본다

동시성 문제는 하나의 지표로 보이지 않는다.

다음 지표를 시간순으로 겹쳐 봐야 한다.

- API p95, p99 latency
- timeout count
- retry rate
- duplicate conflict count
- idempotency conflict count
- lock wait time
- DB connection pool active count
- queue depth
- external API latency
- pending payment_attempt count
- stuck PROCESSING idempotency key count

timeout이 먼저 늘고 retry rate가 뒤따라 증가했다면 느려진 요청이 중복 요청을 만들었을 가능성이 있다.

queue depth가 증가한 뒤 consumer 중복 처리 로그가 늘었다면 메시지 재전달이나 ack 지연을 의심해야 한다.

## 해결 전략

가장 먼저 해야 할 일은 중복을 막는 불변조건을 DB에 두는 것이다.

그 다음 idempotency key로 API 의미를 보존하고, 조건부 update로 상태 전이를 보호하고, outbox/inbox로 메시지 경계를 안전하게 만든다.

distributed lock과 retry는 보조 수단이다.

### 1. 중복 기준을 DB 제약으로 고정한다

주문 번호가 비즈니스적으로 유일하다면 `orders(order_no)`에 unique constraint를 둔다.

```sql
ALTER TABLE orders
ADD CONSTRAINT uk_orders_order_no UNIQUE (order_no);
```

결제 시도 단위가 유일해야 한다면 `payments(payment_attempt_id)`에 둔다.

```sql
ALTER TABLE payments
ADD CONSTRAINT uk_payments_attempt UNIQUE (payment_attempt_id);
```

외부 결제 거래 ID도 중복되면 안 된다.

```sql
ALTER TABLE payments
ADD CONSTRAINT uk_payments_pg_tx UNIQUE (pg_transaction_id);
```

쿠폰 사용은 정책에 따라 달라진다.

```sql
ALTER TABLE coupon_usages
ADD CONSTRAINT uk_coupon_usage_coupon UNIQUE (coupon_id);
```

또는 사용자별 1회라면 다음이 더 맞다.

```sql
ALTER TABLE coupon_usages
ADD CONSTRAINT uk_coupon_usage_user UNIQUE (coupon_id, user_id);
```

중복 기준을 먼저 정해야 한다.

DB 제약은 기술 설정이 아니라 비즈니스 불변조건을 표현하는 장치다.

### 2. duplicate key를 비즈니스 응답으로 바꾼다

unique constraint를 걸면 충돌이 오류로 드러난다.

그 오류를 그대로 500으로 던지면 안 된다.

같은 idempotency key와 같은 request_hash라면 기존 결과를 반환한다.

다른 요청이라면 409 Conflict로 반환한다.

```text
duplicate key 발생
  -> 같은 idempotency key인가?
      yes -> request_hash 비교
          same -> 기존 결과 반환
          different -> 409 Conflict
      no -> 비즈니스 key 기준 기존 리소스 조회 후 409 또는 기존 결과 반환
```

이렇게 해야 DB 방어선이 사용자에게 불필요한 실패로 보이지 않는다.

### 3. idempotency record를 먼저 선점한다

요청이 들어오면 비즈니스 처리보다 먼저 idempotency record를 insert한다.

```sql
INSERT INTO idempotency_keys (
    idempotency_key,
    request_hash,
    status,
    created_at,
    updated_at,
    expires_at
) VALUES (
    :key,
    :request_hash,
    'PROCESSING',
    NOW(),
    NOW(),
    NOW() + INTERVAL '48 hours'
);
```

PostgreSQL이라면 `ON CONFLICT DO NOTHING`으로 선점 여부를 판단할 수 있다.

```sql
INSERT INTO idempotency_keys (...)
VALUES (...)
ON CONFLICT (idempotency_key) DO NOTHING;
```

insert row count가 1이면 내가 처리권을 얻은 것이다.

0이면 기존 record를 조회한다.

MySQL이라면 unique key와 duplicate key 예외, 또는 `INSERT ... ON DUPLICATE KEY UPDATE`를 사용할 수 있다. 단, upsert가 기존 request_hash나 status를 의도치 않게 덮어쓰지 않도록 조심해야 한다.

### 4. 같은 key의 상태별 응답을 정한다

idempotency record 상태별 정책을 명확히 둔다.

```text
SUCCESS
  -> 저장된 response_code, response_body 반환

PROCESSING
  -> 202 Accepted 또는 409 Conflict
  -> 짧게 대기 후 재조회하는 것도 가능

FAILED_RETRYABLE
  -> 같은 key로 재시도 허용 또는 복구 흐름 진입

FAILED_FINAL
  -> 저장된 실패 응답 반환

EXPIRED
  -> 정책에 따라 409 또는 신규 처리
```

`PROCESSING`에 대해 무조건 새 처리를 시작하면 안 된다.

누군가 이미 처리 중이라는 뜻이기 때문이다.

다만 오래된 `PROCESSING`은 복구 대상이다.

```sql
SELECT *
FROM idempotency_keys
WHERE status = 'PROCESSING'
  AND updated_at < NOW() - INTERVAL '10 minutes';
```

이런 record는 외부 상태 조회, 내부 리소스 조회, 보정 작업으로 복구해야 한다.

### 5. 상태 전이를 조건부 update로 만든다

상태 전이는 "현재 상태가 예상한 상태일 때만" 성공해야 한다.

```sql
UPDATE orders
SET status = 'PAYMENT_PENDING',
    updated_at = NOW()
WHERE order_no = :order_no
  AND status = 'CREATED';
```

영향받은 row 수가 1이면 이 요청이 전이에 성공한 것이다.

0이면 이미 다른 요청이 먼저 처리했거나, 전이할 수 없는 상태가 된 것이다.

그다음 현재 상태를 조회해 분기한다.

```text
PAID
  -> 이미 처리 완료. 기존 결과 반환

PAYMENT_PENDING
  -> 처리 중. 202 또는 재조회 안내

CANCELLED
  -> 결제 불가. 409

PAYMENT_FAILED
  -> 재시도 가능 여부 판단
```

상태 머신을 명확히 두면 "조회 후 if"보다 안전해진다.

### 6. 외부 결제 호출 전에 payment_attempt를 만든다

외부 결제 API가 포함되면 더 조심해야 한다.

안전한 흐름은 보통 다음에 가깝다.

```text
1. idempotency key 선점
2. payment_attempt 생성
   - status = PENDING
   - payment_attempt_id = ...
   - order_id = ...
   - request_hash = ...
3. DB commit
4. 외부 PG 호출
   - PG idempotency key 또는 merchant_order_id 전달
5. PG 성공 응답 수신
6. payment_attempt를 SUCCEEDED로 update
7. idempotency record에 SUCCESS와 응답 저장
```

왜 외부 호출 전에 `PENDING`을 commit할까?

외부 호출 후 DB 저장 전에 죽는 경우를 복구하기 위해서다.

`PENDING` record가 있으면 나중에 같은 idempotency key 재요청, webhook, reconciliation job이 이 시도를 찾아 상태를 보정할 수 있다.

PG 호출에는 내부 `payment_attempt_id`나 `merchant_order_id`를 넘긴다.

그래야 서버가 죽은 뒤에도 외부 결제 시스템에 "이 거래가 성공했는지" 조회할 수 있다.

### 7. PG 성공 후 DB 반영 전에 죽는 상황을 복구한다

가장 까다로운 실패 모드는 이것이다.

```text
1. payment_attempt = PENDING 저장
2. PG 승인 성공
3. DB에 SUCCEEDED 저장 전에 서버 장애
```

이 상태에서 재요청이 오면 무작정 PG 승인 요청을 다시 보내면 안 된다.

먼저 기존 `payment_attempt`를 찾는다.

상태가 `PENDING`이고 외부 거래 키가 있다면 PG 상태를 조회한다.

```text
PG 조회 결과 SUCCEEDED
  -> 내부 DB를 SUCCEEDED로 보정
  -> 성공 응답 반환

PG 조회 결과 FAILED
  -> 내부 DB를 FAILED로 보정
  -> 실패 응답 반환

PG 조회 결과 UNKNOWN 또는 PROCESSING
  -> 202 Accepted 또는 재시도 가능한 응답
```

사용자가 다시 요청하지 않는 경우도 있다.

그래서 reconciliation job이 필요하다.

```text
1. 오래된 PENDING payment_attempt 조회
2. PG에 merchant_order_id로 상태 조회
3. 내부 DB 상태 보정
4. 필요한 이벤트 outbox에 기록
```

webhook도 함께 사용할 수 있다.

단 webhook은 중복, 지연, 순서 역전이 가능하다. webhook handler도 event_id 또는 payment_attempt_id 기준으로 멱등해야 한다.

### 8. outbox로 이벤트 발행을 분리한다

주문 상태 변경과 이벤트 발행을 직접 이어 붙이지 않는다.

```java
order.markPaid();
eventPublisher.publish(new OrderPaidEvent(order.getId()));
```

이 방식은 DB commit과 publish 성공 사이에 불일치가 생긴다.

대신 같은 transaction 안에 outbox event를 저장한다.

```sql
BEGIN;

UPDATE orders
SET status = 'PAID'
WHERE order_no = :order_no
  AND status = 'PAYMENT_PENDING';

INSERT INTO outbox_events (
    event_id,
    aggregate_type,
    aggregate_id,
    event_type,
    payload,
    status,
    created_at
) VALUES (
    :event_id,
    'ORDER',
    :order_no,
    'OrderPaid',
    :payload,
    'READY',
    NOW()
);

COMMIT;
```

relay는 outbox를 읽어 발행한다.

```sql
SELECT *
FROM outbox_events
WHERE status = 'READY'
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

PostgreSQL 문서에 따르면 `SKIP LOCKED`는 잠긴 row를 기다리지 않고 건너뛴다. 작업 큐성 테이블에서는 여러 relay가 동시에 처리할 때 도움이 된다.

다만 엄격한 순서 보장이 필요한 이벤트에는 주의해야 한다. 잠긴 row를 건너뛰기 때문에 뒤 이벤트가 먼저 발행될 수 있다.

### 9. consumer는 inbox로 멱등하게 만든다

outbox를 써도 이벤트는 중복 발행될 수 있다.

consumer는 다음처럼 처리한다.

```sql
BEGIN;

INSERT INTO processed_messages (
    consumer_name,
    message_id,
    processed_at
) VALUES (
    :consumer_name,
    :message_id,
    NOW()
);

-- insert 성공한 경우에만 비즈니스 처리
UPDATE points
SET amount = amount + :point
WHERE user_id = :user_id;

COMMIT;
```

이미 처리한 message_id면 insert가 실패한다.

그 경우 메시지를 skip하고 ack한다.

중요한 점은 processed_messages insert와 비즈니스 변경을 같은 transaction에 넣는 것이다.

둘이 분리되면 "처리 기록은 남았는데 실제 처리는 실패"하거나, 반대로 "처리는 됐는데 기록은 없음" 상태가 생길 수 있다.

### 10. distributed lock은 충돌 완화로 쓴다

같은 `order_no`에 대한 처리 경쟁이 너무 잦고 외부 API 비용이 크다면 lock으로 동시 실행을 줄일 수 있다.

```text
1. idempotency record 조회
2. 이미 SUCCESS면 반환
3. lock:order:{orderNo} 획득
4. 다시 idempotency/order 상태 조회
5. 처리
6. token 검증 후 lock 해제
```

락을 잡은 뒤 반드시 다시 상태를 확인해야 한다.

락을 기다리는 동안 다른 요청이 이미 처리했을 수 있기 때문이다.

락 획득 실패 시 무작정 실패시키기보다 기존 idempotency record나 주문 상태를 조회해 결과를 반환하는 흐름이 좋다.

락은 중복 실행을 줄일 뿐이다.

뒤에는 여전히 unique constraint, 조건부 update, idempotency record가 있어야 한다.

### 11. retry와 timeout을 정리한다

retry는 재실행해도 안전한 실패에만 붙인다.

대상은 보통 다음이다.

- deadlock victim
- lock wait timeout 중 일부
- transient network error
- 5xx 중 멱등 보장되는 요청
- duplicate conflict 후 기존 결과 조회
- message publish retry

retry 간격은 즉시 반복보다 jitter가 있는 backoff가 낫다.

```text
1회차: 50~100ms
2회차: 100~200ms
3회차: 200~400ms
```

전체 timeout 예산 안에서만 수행해야 한다.

이미 사용자 요청 timeout이 임박했다면 재시도하지 않고 현재 상태를 저장한 뒤 조회 가능한 응답을 주는 편이 낫다.

외부 부작용이 있는 호출은 idempotency key 없이 retry하면 안 된다.

### 12. 프론트 버튼 비활성화는 보조 수단이다

버튼 중복 클릭을 막는 것은 좋다.

하지만 서버 정합성 보장의 근거가 될 수 없다.

중복 요청은 프론트 버튼과 무관하게 발생한다.

- 모바일 네트워크 재전송
- 브라우저 새로고침
- API Gateway retry
- 서버 timeout
- queue redelivery
- worker 재시작
- 배치 재실행
- 운영자 수동 재처리

프론트 제어는 사용자 경험을 위한 장치다.

정합성은 서버와 DB에서 보장해야 한다.

## 설계 예시

결제 API를 하나의 흐름으로 묶어보면 다음과 같다.

```text
client
  -> POST /payments
     Idempotency-Key: abc-123

server
  -> canonical request hash 생성
  -> idempotency_keys INSERT(PROCESSING)
     - conflict면 기존 record 확인
  -> payment_attempt INSERT(PENDING)
  -> order 상태를 PAYMENT_PENDING으로 조건부 update
  -> commit

server
  -> PG approve 호출
     - merchant_order_id 또는 payment_attempt_id 전달
     - PG idempotency key 전달

server
  -> PG 성공 시 짧은 transaction
     - payment_attempt SUCCEEDED
     - order PAID
     - outbox OrderPaid 저장
     - idempotency_keys SUCCESS + response 저장
  -> commit

relay
  -> outbox OrderPaid 발행

consumer
  -> processed_messages insert
  -> 중복이면 skip
  -> 신규면 배송/알림/정산 처리
```

이 구조의 핵심은 세 가지다.

첫째, 같은 요청이 여러 번 들어와도 idempotency key로 같은 결과를 반환한다.

둘째, 같은 데이터가 두 번 저장되지 않도록 DB unique constraint를 둔다.

셋째, DB 밖의 부작용은 outbox, webhook, reconciliation, consumer deduplication으로 수렴시킨다.

## 면접에서는 이렇게 답한다

질문은 이렇게 나올 수 있다.

> 주문 생성 API에 같은 요청이 동시에 두 번 들어와 결제가 중복 승인될 수 있습니다. 어떻게 막겠습니까?

1분 답변은 이렇게 말할 수 있다.

먼저 중복의 기준을 명확히 잡겠습니다.

같은 주문 의도인지 식별하기 위해 idempotency key를 받고, 서버에서는 key와 request_hash를 저장해 같은 key의 재시도는 기존 결과를 반환하게 합니다. 같은 key인데 request_hash가 다르면 같은 요청의 재시도가 아니므로 409 Conflict로 막겠습니다.

DB에는 주문 번호나 payment attempt id 기준으로 unique constraint를 둬서 애플리케이션 버그나 동시 요청이 있어도 중복 row가 저장되지 않게 합니다.

처리 흐름에서는 조회 후 생성처럼 race window가 있는 코드를 피하고, 상태 전이를 조건부 update로 처리하겠습니다. 예를 들어 `status = CREATED`일 때만 `PAYMENT_PENDING`으로 바꾸고, 영향받은 row 수가 0이면 이미 처리 중이거나 완료된 상태로 보고 현재 상태를 조회해 응답합니다.

외부 결제 API에는 PG가 제공하는 idempotency key나 merchant transaction id를 같이 전달하겠습니다. PG 성공 후 DB commit 전에 서버가 죽을 수 있으므로 `payment_attempt = PENDING`을 먼저 저장하고, 재요청이나 reconciliation job, webhook을 통해 외부 상태를 조회해 내부 상태를 보정합니다.

이벤트 발행은 DB commit과 직접 묶기 어렵기 때문에 outbox 패턴으로 주문 상태 변경과 발행할 이벤트 기록을 같은 transaction에 저장합니다. consumer는 event_id 기준으로 처리 이력을 저장해 중복 메시지를 멱등하게 처리합니다.

distributed lock은 같은 order_no에 대한 동시 실행을 줄이는 보조 수단으로 쓸 수 있지만, 최종 정합성은 DB 제약과 멱등 처리로 보장해야 합니다.

핵심 채점 포인트는 다음이다.

- 애플리케이션 `if` 체크만으로 race condition을 막을 수 없다는 점
- idempotency key와 unique constraint의 역할을 구분하는 점
- request_hash로 key 재사용 오류를 막는 점
- transaction boundary 밖의 외부 부작용을 별도로 다루는 점
- outbox와 consumer 멱등성을 함께 말하는 점
- distributed lock을 최종 방어선으로 보지 않는 점

꼬리 질문은 이렇게 이어질 수 있다.

### idempotency key가 같지만 request body가 다르면 어떻게 처리할 것인가?

거부해야 한다.

같은 idempotency key는 같은 의도의 같은 요청을 의미해야 한다. key는 같은데 body가 다르면 클라이언트 버그, 악의적 재사용, payload 변형 가능성이 있다.

최초 요청의 request_hash와 현재 request_hash를 비교하고, 다르면 기존 응답을 반환하지 않고 409 Conflict 또는 422 Unprocessable Entity로 처리한다.

### 외부 결제 API가 성공했는데 DB commit 전에 서버가 죽으면 어떻게 복구할 것인가?

외부 호출 전에 내부 DB에 `payment_attempt = PENDING`을 먼저 저장하고 commit한다.

외부 PG에는 `payment_attempt_id`나 `merchant_order_id`, idempotency key를 함께 전달한다.

서버가 PG 성공 후 내부 DB 반영 전에 죽으면 재요청, webhook, reconciliation job이 기존 `PENDING` 시도를 찾고 PG에 상태를 조회한다. 성공이면 내부 DB를 `SUCCEEDED`로 보정하고, 실패면 `FAILED`로 보정한다.

### distributed lock을 쓰더라도 unique constraint가 필요한 이유는 무엇인가?

distributed lock은 실행을 줄이는 장치다.

TTL 만료, 네트워크 지연, lock holder 장애, failover 같은 이유로 완전한 최종 방어선이 되기 어렵다.

unique constraint는 잘못된 결과가 DB에 저장되지 않게 막는 불변조건이다. 락이 실패해도 데이터가 깨지지 않게 하려면 DB 제약이 필요하다.

### outbox를 쓰면 exactly-once가 보장되는가?

아니다.

outbox는 DB 변경과 "발행할 이벤트의 기록"을 같은 transaction에 묶어 이벤트 유실을 줄인다. 하지만 relay가 publish 후 상태 변경 전에 죽으면 같은 이벤트를 다시 발행할 수 있다.

그래서 consumer는 event_id 또는 비즈니스 key 기준으로 멱등 처리해야 한다.

## 요약

같은 주문이 두 번 처리되는 문제는 코드가 틀려서만 생기지 않는다.

조회와 변경 사이의 race window, timeout, retry, 외부 부작용, 메시지 중복 전달이 겹치면 정상 코드도 중복 실행될 수 있다.

중복 방어의 최종선은 DB에 있어야 한다. `order_no`, `payment_attempt_id`, idempotency key처럼 유일해야 하는 기준에는 unique constraint를 두고, 충돌을 비즈니스 응답으로 해석해야 한다.

idempotency key는 재시도를 안전하게 만드는 API 계약이다. key만 저장하지 말고 request_hash, 처리 상태, 응답, TTL을 함께 설계해야 한다.

transaction은 DB 내부 변경을 보호하지만 외부 결제, 메시지 발행, 이메일 같은 부작용까지 자동으로 원자화하지 않는다. 외부 부작용은 멱등 API, 상태 머신, outbox, webhook, reconciliation으로 다뤄야 한다.

distributed lock은 동시 실행을 줄이는 데 유용하지만 정합성의 마지막 방어선이 아니다. 락 뒤에도 unique constraint, 조건부 update, idempotent consumer가 필요하다.

분석할 때는 중복 결과의 key, 요청 trace, retry rate, timeout budget, DB lock wait, duplicate conflict, outbox queue depth를 시간순으로 연결해야 한다.

"두 번 호출됐다"가 아니라 "어디까지 성공한 요청이 다시 실행됐는가"를 찾아야 한다.

가장 중요한 질문은 이것이다.

> 이 요청이 두 번 실행되어도 같은 결과로 수렴하는가?

이 질문에 답할 수 있을 때 동시성 처리는 단순히 락을 거는 문제가 아니라, 실패와 재시도를 포함한 전체 흐름의 설계가 된다.
