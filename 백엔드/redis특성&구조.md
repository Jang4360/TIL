# Redis는 왜 싱글 스레드인데 빠를까

Redis를 처음 보면 조금 이상하게 느껴진다.

서버는 보통 요청이 많아질수록 스레드를 늘리고, 커넥션을 나누고, 병렬 처리로 버틴다고 생각하기 쉽다. 그런데 Redis는 오랫동안 "싱글 스레드"라는 설명과 함께 소개되어 왔다. 그러면서도 캐시, 세션, 분산락, 랭킹, 카운터처럼 트래픽이 많이 몰리는 곳에서 가장 자주 등장한다.

그래서 궁금해진다.

> Redis는 메인 스레드가 하나인데, 어떻게 빠르게 동작할 수 있을까?

답은 단순히 "메모리에 있어서"가 아니다. 물론 메모리에 데이터를 둔다는 점은 중요하다. 하지만 Redis가 빠른 이유는 메모리, 이벤트 루프, I/O multiplexing, 단순한 자료구조, RESP 프로토콜, 파이프라이닝, 백그라운드 작업 분리 같은 설계가 한 방향으로 맞물려 있기 때문이다.

이 글에서는 Redis가 싱글 스레드임에도 빠른 이유를 구조와 동작 원리 중심으로 정리하고, Redis를 실무에서 사용할 때 어떤 트레이드오프를 같이 봐야 하는지까지 정리한다.

---

## Redis는 먼저 메모리 위에서 동작한다

Redis는 In-Memory 데이터 저장소다.

대부분의 요청은 디스크를 직접 읽지 않고 RAM에 올라와 있는 데이터를 조회한다. 디스크 I/O는 밀리초 단위 지연이 쉽게 발생하지만, 메모리 접근은 훨씬 짧은 시간 안에 끝난다. 캐시로 Redis를 사용하는 가장 큰 이유도 여기에 있다.

하지만 "메모리에 있으니까 빠르다"만으로는 부족하다. 메모리에 있어도 요청을 처리하는 구조가 복잡하거나, 커넥션마다 스레드를 만들거나, 락 경합이 많으면 레이턴시는 쉽게 흔들린다.

Redis는 여기서 한 가지 선택을 한다.

명령 실행 경로를 단순하게 유지한다.

클라이언트 요청을 처리하고, 자료구조를 읽고 쓰고, 응답을 만드는 핵심 경로는 기본적으로 하나의 메인 스레드에서 순차적으로 실행된다. 이 덕분에 Redis 내부 자료구조를 보호하기 위한 락이 거의 필요하지 않다.

락이 없다는 건 단순히 구현이 편하다는 뜻이 아니다.

- 락 획득 대기 시간이 없다.
- 락 경합으로 인한 지연 편차가 줄어든다.
- 같은 명령은 비슷한 시간 안에 끝날 가능성이 높다.
- 운영자가 레이턴시를 예측하기 쉽다.

Redis의 싱글 스레드 구조는 "CPU를 하나만 써서 느리다"가 아니라, "핵심 실행 경로를 하나로 제한해서 락 비용과 복잡도를 줄인다"에 가깝다.

---

## 커넥션은 많아도 스레드를 많이 만들지 않는다

싱글 스레드라고 해서 한 번에 클라이언트 하나만 연결할 수 있는 건 아니다.

Redis는 수많은 클라이언트 소켓을 I/O multiplexing으로 다룬다. Linux 환경에서는 대표적으로 `epoll` 같은 커널 기능을 활용한다.

흐름을 단순화하면 다음과 같다.

```text
client sockets -> epoll(kernel) -> Redis event loop -> single main thread
```

여기서 중요한 점은 Redis가 모든 클라이언트 소켓을 직접 계속 확인하지 않는다는 것이다. 커널이 여러 소켓의 상태를 감시하고 있다가, 읽거나 쓸 준비가 된 소켓만 Redis에 알려준다.

Redis 메인 스레드는 준비된 소켓만 빠르게 처리한다.

이 구조는 C10K 문제와 연결된다. C10K는 하나의 서버가 10,000개의 동시 커넥션을 어떻게 처리할 것인가에 대한 문제다. 커넥션 하나마다 스레드 하나를 붙이는 방식은 단순하지만, 커넥션 수가 커질수록 스레드 스택 메모리와 컨텍스트 스위칭 비용이 커진다.

Redis는 반대로 접근한다.

- 커넥션마다 스레드를 만들지 않는다.
- 소켓은 Non Blocking I/O로 다룬다.
- 준비된 소켓 이벤트만 이벤트 루프에서 처리한다.
- 명령 실행은 메인 스레드가 순차적으로 빠르게 끝낸다.

그래서 Redis는 메인 스레드가 하나여도 많은 클라이언트를 동시에 상대할 수 있다. "동시에 실행"하는 것이 아니라, "준비된 작업만 매우 짧게 처리해서 동시에 처리되는 것처럼 보이게" 만든다.

---

## Key-Value 구조는 단순해서 빠르다

Redis의 기본 모델은 Key-Value다.

클라이언트는 `GET user:1`, `SET session:abc ...`처럼 키를 기준으로 데이터를 읽고 쓴다. Redis 내부에서 key space는 해시 테이블 기반으로 관리된다. 그래서 일반적인 키 조회는 평균적으로 `O(1)`에 가깝다.

물론 해시 테이블에는 충돌이 발생할 수 있다. 서로 다른 key가 같은 bucket으로 매핑될 수 있기 때문이다. Redis는 이런 충돌을 체이닝 방식으로 해결한다. 같은 bucket 안에 여러 엔트리가 연결될 수 있고, Redis는 그 안에서 실제 key를 비교해 찾는다.

여기서 실무적으로 중요한 건 "Redis 명령이 항상 빠르다"가 아니라 "키를 찾는 기본 경로가 단순하다"는 점이다.

`GET`, `SET`, `INCR`처럼 작은 데이터를 다루는 단순 명령은 빠르다. 반면 하나의 key 안에 수십만 개의 필드나 멤버가 들어 있고, 그 전체를 한 번에 가져오는 명령은 느려질 수 있다.

Redis의 성능은 key-value 구조 덕분에 빠르지만, value 안에 너무 큰 자료구조를 넣는 순간 이야기가 달라진다.

## RESP는 파싱 비용을 줄인다

Redis는 클라이언트와 서버가 통신할 때 RESP(REdis Serialization Protocol)를 사용한다.

RESP의 특징 중 하나는 길이를 먼저 알려주는 형태의 메시지 구조다. 예를 들어 bulk string은 데이터 앞에 길이가 붙는다. 서버는 "이 데이터가 몇 바이트인지"를 먼저 알고 읽을 수 있다.

일반적인 구분자 기반 프로토콜을 생각해보면, 서버는 어디까지가 하나의 값인지 알기 위해 한 글자씩 스캔해야 한다. 데이터 크기를 읽으면서 파악해야 하고, 버퍼를 어느 정도 잡아야 할지도 애매해진다.

RESP는 반대로 동작한다.

- 길이를 먼저 읽는다.
- 필요한 버퍼 크기를 예측할 수 있다.
- 불필요한 구분자 탐색 비용을 줄인다.
- 파싱 루프가 단순해진다.

싱글 스레드에서 초당 많은 명령을 처리하려면 명령 하나를 파싱하는 시간도 작아야 한다. Redis는 명령 실행만 빠르게 만든 것이 아니라, 네트워크에서 들어온 요청을 해석하는 비용도 작게 유지한다.

이런 설계는 작은 차이처럼 보이지만, 요청 수가 커질수록 크게 체감된다.

---

## Pipeline은 네트워크 왕복을 줄인다

Redis 명령 하나의 실행 시간이 아무리 짧아도, 클라이언트와 서버 사이의 왕복 지연 시간(RTT)은 사라지지 않는다.

예를 들어 RTT가 1ms인 환경에서 명령 100개를 순서대로 보낸다고 해보자.

```text
command 1 -> response 1
command 2 -> response 2
...
command 100 -> response 100
```

각 명령이 아주 빨리 끝나도 왕복만 100번이면 이론상 최소 100ms가 걸린다.

Pipeline은 이 비용을 줄인다.

```text
command 1
command 2
...
command 100
-> responses
```

명령을 여러 개 모아서 한 번에 보내고, 응답도 나중에 모아서 읽는다. Redis 서버는 명령을 순차적으로 처리하지만, 클라이언트는 네트워크 왕복을 한 번 또는 훨씬 적은 횟수로 줄일 수 있다.

여기서 핵심은 Redis가 병렬로 명령을 실행한다는 뜻이 아니다. 서버 입장에서는 여전히 순차 처리다. 다만 클라이언트가 매번 응답을 기다리지 않기 때문에 네트워크 지연이 압축된다.

실무에서는 대량 캐시 적재, 여러 key 조회, 피처 데이터 로딩, 랭킹 업데이트처럼 작은 명령을 많이 보내는 구간에서 파이프라인 효과가 크다.

## Redis의 싱글 스레드는 "전부 싱글 스레드"가 아니다

Redis를 설명할 때 가장 많이 오해하는 부분이 있다.

Redis가 싱글 스레드라는 말은 "모든 일을 스레드 하나가 한다"는 뜻이 아니다.

정확히는 명령 실행의 핵심 경로가 싱글 스레드에 가깝다는 뜻이다. Redis는 느린 삭제나 디스크 관련 작업처럼 메인 스레드를 오래 잡아먹을 수 있는 일을 백그라운드로 분리해 왔다.

예를 들어 큰 key를 삭제할 때 `DEL`은 메모리 해제 비용 때문에 메인 스레드를 오래 붙잡을 수 있다. 그래서 Redis는 `UNLINK`를 제공한다. `UNLINK`는 key space에서 key를 먼저 떼어내고, 실제 메모리 회수는 백그라운드 스레드에서 처리한다.

이 차이는 운영에서 중요하다.

수백만 개 요소가 들어 있는 리스트나 해시를 삭제할 때 메인 스레드가 오래 멈추면, 다른 모든 요청이 기다린다. 반면 `UNLINK`나 lazy free 계열 설정을 사용하면 메인 스레드 블로킹을 줄일 수 있다.

정리하면 이렇다.

> Redis의 싱글 스레드는 명령 실행 경로를 단순하게 유지하기 위한 선택이고, 느린 보조 작업은 가능한 한 메인 스레드 밖으로 밀어낸다.

---

## 그래서 Redis가 빠른 이유

Redis가 빠른 이유를 한 문장으로 정리하면 이렇다.

> 메모리 위의 단순한 자료구조를, 이벤트 루프와 Non Blocking I/O로 받아서, 락 없는 단일 실행 경로에서 짧게 처리하기 때문이다.

조금 더 풀면 다음과 같다.

- 데이터가 RAM에 있어 디스크 읽기 지연이 없다.
- key 조회가 해시 테이블 기반이라 평균적으로 빠르다.
- 커넥션마다 스레드를 만들지 않아 메모리와 컨텍스트 스위칭 비용이 작다.
- `epoll` 같은 I/O multiplexing으로 준비된 소켓만 처리한다.
- RESP가 단순해 파싱 비용이 작다.
- Pipeline으로 RTT 비용을 줄일 수 있다.
- 큰 삭제와 디스크 작업 일부를 백그라운드로 분리한다.
- 명령 실행 경로가 싱글 스레드라 락 경합이 거의 없다.

Redis의 진짜 장점은 "무조건 빠름"이 아니다.

예측 가능한 빠름이다.

락이 없고, 실행 경로가 단순하고, 대부분의 단순 명령이 짧은 시간 안에 끝난다. 그래서 캐시처럼 레이턴시 편차에 민감한 영역에서 Redis가 자주 선택된다.

---

## Redis가 느려지는 패턴

Redis는 빠르지만, 싱글 스레드라는 구조 때문에 한 명령이 오래 걸리면 다른 요청도 같이 기다린다.

실무에서 자주 만나는 패턴은 다음과 같다.

| 상황 | 원인 | 증상 | 대응 |
| --- | --- | --- | --- |
| `KEYS *` 사용 | 전체 key space `O(N)` 스캔 | 서버 전체 블로킹 | `SCAN` 커서 방식으로 교체 |
| 대형 Hash/List | 단일 key에 수십만 필드 또는 요소 집중 | 명령 처리 지연 | key sharding, 자료구조 분리, 만료 정책 설계 |
| `SMEMBERS` 대형 Set | Set 전체를 한 번에 반환 | 응답 크기 증가, 지연 | `SSCAN` 사용 또는 구조 재설계 |
| Hot Key 집중 | 특정 key에 요청 폭주 | 싱글 스레드 병목, 네트워크 병목 | 로컬 캐시 계층, key 분산, replica read 검토 |
| `appendfsync always` | 매 쓰기마다 디스크 동기화 | 처리량 급락 | `everysec` 검토, 내구성 요구 재정의 |
| 메모리 부족 후 eviction | `maxmemory` 초과 | 레이턴시 스파이크, hit rate 하락 | eviction 정책 명시, 용량 계획, TTL 점검 |
| 큰 key 삭제 | 메모리 해제를 메인 스레드에서 수행 | 순간 블로킹 | `UNLINK`, lazy free 설정 검토 |
| 느린 Lua script | 스크립트가 오래 실행 | 모든 요청 대기 | 스크립트 짧게 유지, 입력 크기 제한 |

여기서 공통점은 하나다.

Redis를 느리게 만드는 건 "Redis라서"가 아니라, 하나의 명령이 메인 스레드를 오래 점유하는 상황이다.

그래서 Redis를 운영할 때는 평균 QPS보다 tail latency를 봐야 한다. `p99`, `p999`, slowlog, big key, hot key, `used_memory`, `evicted_keys`, `rejected_connections`, `lazyfree_pending_objects` 같은 지표를 같이 봐야 한다.

## Redis는 어디에 쓰일까

Redis를 떠올리면 보통 캐시와 분산락이 먼저 나온다.

실제로 이 둘은 Redis의 대표적인 사용처다. 하지만 Redis는 메모리 기반 key-value 저장소이면서 다양한 자료구조를 제공하기 때문에 더 많은 패턴에 쓰인다.

- 캐싱
- 분산락
- 세션 저장소
- Rate Limiting
- Idempotency Key 저장소
- 카운터와 통계
- 랭킹과 리더보드
- Pub/Sub
- Streams 기반 경량 이벤트 처리
- 큐 또는 지연 작업
- Bloom Filter, HyperLogLog 같은 확률적 자료구조

다만 Redis는 "빠른 저장소"이지, 모든 문제의 최종 저장소는 아니다. 빠른 대신 메모리 비용, 장애 시 정합성, TTL 설계, eviction, 복제 지연, 영속성 옵션 같은 트레이드오프가 따라온다.

아래부터는 실무에서 많이 쓰는 방식과 트레이드오프를 하나씩 정리한다.

---

## 1. 캐싱

캐시는 응답 데이터를 재사용하기 위해 저장하는 방식이다.

DB에서 매번 읽거나, 외부 API를 매번 호출하거나, 비용이 큰 계산을 매번 수행하면 응답 시간이 길어지고 원본 시스템 부하가 커진다. 이때 결과를 Redis에 저장해두고 다음 요청에서 재사용한다.

가장 흔한 방식은 Cache-Aside다.

```text
1. 애플리케이션이 Redis에서 key 조회
2. cache hit이면 바로 응답
3. cache miss이면 DB 조회
4. DB 결과를 Redis에 TTL과 함께 저장
5. 응답 반환
```

이 방식은 단순하고 도입이 쉽다. 하지만 트레이드오프가 분명하다.

### 트레이드오프: 데이터가 오래될 수 있다

캐시는 원본 데이터의 복사본이다. 원본 DB가 바뀌었는데 Redis에 남아 있는 값이 갱신되지 않으면 사용자는 오래된 데이터를 볼 수 있다.

해결 방식은 데이터 성격에 따라 달라진다.

- 강한 최신성이 필요하면 쓰기 시 캐시 무효화(`DEL`)를 같이 수행한다.
- 조금 오래된 값이 허용되면 TTL을 짧게 둔다.
- 캐시 key에 버전을 붙여 배포나 스키마 변경 시 한 번에 갈아탄다.
- 원본 변경 이벤트를 발행하고 소비자가 캐시를 갱신한다.

실무에서는 "무조건 최신"보다 "얼마나 오래된 값까지 허용할 수 있는가"를 먼저 정해야 한다. 캐시 TTL은 기술 값이 아니라 서비스 정책에 가깝다.

### 트레이드오프: 캐시 스탬피드가 발생할 수 있다

캐시 스탬피드는 인기 key가 만료되는 순간 많은 요청이 동시에 DB로 몰리는 현상이다.

예를 들어 메인 화면 상품 목록 캐시가 만료됐다고 해보자. 캐시가 있을 때는 모든 요청이 Redis에서 끝난다. 그런데 만료 직후 요청 1,000개가 동시에 들어오면 1,000개 요청이 모두 DB를 조회할 수 있다.

Redis를 붙였는데 장애는 DB에서 나는 상황이 생긴다.

실무 해결책은 여러 개를 같이 쓴다.

### 해결책 1: TTL jitter

모든 key에 같은 TTL을 주면 같은 시점에 대량 만료가 발생한다. TTL에 랜덤 값을 섞으면 만료 시점이 분산된다.

```text
base TTL = 300초
actual TTL = 300초 + random(-30초, +30초)
```

간단하지만 효과가 크다. 특히 배치로 한 번에 적재되는 캐시에 유용하다.

### 해결책 2: Single-flight lock

캐시 miss가 발생했을 때 모든 요청이 DB를 조회하지 않게, 대표 요청 하나만 원본을 조회하게 만든다.

```text
1. 캐시 miss
2. lock:cache:user:1 획득 시도
3. 성공한 요청만 DB 조회 후 캐시 재생성
4. 실패한 요청은 짧게 대기하거나 stale 데이터 반환
```

이때 락은 Redis의 `SET key value NX PX ttl` 같은 원자 명령으로 잡을 수 있다. 단, 이 락도 TTL과 token 검증을 갖춰야 한다. 락을 잘못 구현하면 캐시 스탬피드를 막으려다 중복 실행이나 잘못된 락 해제를 만들 수 있다.

### 해결책 3: Stale-While-Revalidate

캐시 값을 물리적으로 바로 지우지 않고, 논리적 만료 시간을 함께 저장한다.

```json
{
  "data": "...",
  "freshUntil": "2026-06-14T10:00:00+09:00"
}
```

요청이 들어왔을 때 `freshUntil`이 지났다면 한 요청만 백그라운드 갱신을 수행하고, 나머지 요청은 잠깐 오래된 값을 그대로 반환한다.

이 방식은 대시보드, 상품 목록, 추천 영역처럼 약간의 stale을 허용할 수 있는 곳에 잘 맞는다. 대신 결제 승인, 재고 차감, 계좌 잔액처럼 최신성이 중요한 데이터에는 조심해야 한다.

### 해결책 4: 캐시 워밍

사용자가 몰리기 전에 주요 key를 미리 채워둔다.

배포 직후, 이벤트 시작 전, 매일 자정 집계 직후처럼 캐시 miss가 몰릴 시점을 알고 있다면 캐시를 미리 적재한다. 다만 워밍 대상이 너무 많으면 Redis 메모리를 낭비하고, 실제로 쓰이지 않는 데이터를 밀어 넣을 수 있다.

### 해결책 5: 로컬 캐시 계층

Hot Key가 Redis 자체를 압박할 정도로 자주 조회된다면 애플리케이션 프로세스 내부에 짧은 TTL 로컬 캐시를 둘 수 있다.

```text
local cache -> Redis -> DB
```

이 방식은 Redis 요청 자체를 줄인다. 하지만 서버마다 로컬 캐시가 따로 존재하므로 최신성은 더 약해진다. 짧은 TTL, 변경 이벤트 기반 무효화, Caffeine 같은 검증된 로컬 캐시 라이브러리 사용을 함께 고려해야 한다.

## 2. 분산락

분산락은 여러 서버가 동시에 같은 작업을 실행하지 못하게 조율하는 방식이다.

캐시는 응답 데이터를 재사용하기 위해 저장한다. 반면 분산락은 "이 요청이 처리 중이다"라는 상태를 공유하기 위해 저장한다.

예를 들어 같은 사용자가 같은 회차의 로또 참여 요청을 여러 번 보냈다고 해보자. 서버가 여러 대라면 요청 A는 서버 1로, 요청 B는 서버 2로 들어갈 수 있다. 애플리케이션 내부의 `synchronized`나 mutex만으로는 막을 수 없다.

이때 Redis에 lock key를 저장한다.

```text
SET lock:lotto:{userId}:{roundId} {token} NX PX 3000
```

- `NX`: key가 없을 때만 생성한다.
- `PX 3000`: 3초 뒤 자동 만료한다.
- `{token}`: 락 소유자를 구분하기 위한 고유 값이다.

Redis는 이 명령을 원자적으로 실행한다. 동시에 같은 요청이 들어와도 하나만 key 생성에 성공한다.

### TTL은 반드시 필요하다

락에 TTL이 없으면 서버가 작업 중 죽었을 때 락이 영원히 남을 수 있다. 그러면 이후 정상 요청도 계속 막힌다.

하지만 TTL은 짧아도 문제고 길어도 문제다.

- TTL이 너무 짧으면 작업 중 락이 풀려 중복 실행이 발생할 수 있다.
- TTL이 너무 길면 실패 후 정상 재시도가 오래 막힐 수 있다.

실무에서는 작업 시간의 `p99`보다 길게 잡고, 외부 API 지연이나 GC pause 같은 변수를 반영한다. 작업 시간이 흔들리는 영역이라면 락 연장(renewal)도 고려할 수 있다. 단, renewal은 구현 복잡도를 높이고 장애 상황에서 락이 오래 유지될 수 있으므로 반드시 상한 시간을 둬야 한다.

### `DEL key`로 락을 해제하면 위험하다

락 해제 시 단순히 `DEL lock:key`를 호출하면 안 된다.

다음 상황을 생각해보자.

```text
1. 요청 A가 lock 획득, TTL 3초
2. 작업이 5초 걸림
3. 3초 뒤 A의 lock 만료
4. 요청 B가 같은 lock 획득
5. 요청 A가 작업 완료 후 DEL lock 실행
6. B의 lock이 삭제됨
```

이러면 요청 C가 다시 들어와 같은 작업을 실행할 수 있다. A가 자기 락이 아니라 B의 락을 삭제한 것이다.

그래서 value에 token을 저장해야 한다. 해제할 때는 Redis 안에서 "현재 value가 내가 발급한 token과 같은지" 비교하고, 같을 때만 삭제해야 한다.

Redis 8.4 이상에서는 조건부 삭제를 위한 `DELEX key IFEQ token`을 사용할 수 있고, 그 이전 버전이나 일반적인 클라이언트 환경에서는 Lua script로 처리한다.

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

비교와 삭제가 Redis 안에서 한 번에 실행되어야 한다. 애플리케이션에서 `GET` 후 `DEL`을 따로 호출하면 그 사이에 락 소유자가 바뀔 수 있다.

### Redis 분산락만 믿으면 안 된다

Redis 락을 썼는데도 DB에 중복 데이터가 생길 수 있다.

대표 원인은 다음과 같다.

- TTL이 실제 작업 시간보다 짧다.
- Redis 장애나 failover가 발생했다.
- 네트워크 지연으로 락 획득 여부 판단이 흔들렸다.
- 락 획득 후 DB 저장 직전에 애플리케이션이 재시도됐다.

그래서 Redis 락은 중복 실행 가능성을 낮추는 장치로 보고, 최종 방어선은 DB에 둬야 한다.

로또 참여라면 DB에 다음 unique constraint가 있어야 한다.

```text
UNIQUE(user_id, round_id)
```

이 제약이 있으면 Redis 락이 실패해도 최종 중복 저장은 막을 수 있다.

### Idempotency Key도 같이 봐야 한다

Idempotency Key는 같은 요청이 여러 번 들어와도 결과를 한 번 처리한 것처럼 보장하기 위한 키다.

분산락이 "동시에 처리하지 못하게 막는 장치"라면, idempotency key는 "이미 처리한 요청의 결과를 재사용하는 장치"에 가깝다.

결제, 주문, 쿠폰 발급처럼 클라이언트 재시도나 네트워크 타임아웃이 자주 발생하는 곳에서는 둘을 함께 쓰는 경우가 많다.

```text
idempotency:{clientRequestId} -> 처리 결과 또는 처리 상태
```

요청이 처음이면 처리하고 결과를 저장한다. 같은 key로 다시 들어오면 새로 처리하지 않고 기존 결과를 반환한다.

여기서도 TTL 정책이 필요하다. 너무 짧으면 재시도 요청을 못 막고, 너무 길면 저장 공간이 커진다. 보통 비즈니스 재시도 가능 시간, 결제사 재시도 정책, 고객센터 대응 기간을 기준으로 잡는다.

### 분산락의 실무 체크리스트

- `SET key token NX PX ttl`처럼 획득과 만료를 원자적으로 처리한다.
- token은 요청마다 유니크해야 한다.
- 해제는 token 비교 후 삭제를 원자적으로 처리한다.
- TTL은 작업 시간 `p99`보다 길게 잡는다.
- 작업 시간이 길어질 수 있으면 renewal과 최대 보유 시간을 같이 둔다.
- 실패 시 무한 재시도하지 말고 backoff와 timeout을 둔다.
- DB unique constraint 또는 idempotency key를 최종 방어선으로 둔다.
- Redis 장애 시 정책을 정한다. 실패 닫힘(fail closed)인지, 실패 열림(fail open)인지 서비스별로 다르다.

분산락은 편하지만, 정합성의 마지막 책임자가 되면 안 된다.

## 3. 세션 저장소

Redis는 세션 저장소로도 자주 쓰인다.

서버가 여러 대로 늘어나면 특정 서버의 메모리에 세션을 저장하는 방식은 불편해진다. 사용자가 로그인한 서버와 다음 요청을 받은 서버가 다르면 세션을 찾을 수 없기 때문이다. 이 문제를 해결하려고 sticky session을 쓰면 로드밸런싱과 서버 증설이 복잡해진다.

세션을 Redis에 저장하면 모든 애플리케이션 서버가 같은 세션 저장소를 바라볼 수 있다.

```text
session:{sessionId} -> userId, roles, expiresAt
```

장점은 명확하다.

- 서버를 무상태에 가깝게 만들 수 있다.
- 로그아웃이나 강제 만료를 서버에서 통제할 수 있다.
- TTL로 세션 만료를 자연스럽게 관리할 수 있다.

트레이드오프도 있다.

- Redis 장애가 로그인 장애로 이어질 수 있다.
- 모든 요청이 Redis를 조회하면 Redis가 인증 경로의 병목이 된다.
- 세션 데이터가 커지면 네트워크 비용과 메모리 비용이 증가한다.

실무에서는 세션에는 최소한의 정보만 넣고, Redis Cluster 또는 replication 구성을 통해 가용성을 확보한다. 인증이 모든 요청에 걸리는 경우에는 connection pool, timeout, fallback 정책도 명확히 둬야 한다.

## 4. Rate Limiting

Rate Limiting은 특정 사용자, IP, API key가 일정 시간 동안 보낼 수 있는 요청 수를 제한하는 방식이다.

Redis는 `INCR`와 `EXPIRE`만으로도 간단한 fixed window limiter를 만들 수 있다.

```text
INCR rate:{userId}:202606141030
EXPIRE rate:{userId}:202606141030 60
```

하지만 단순 fixed window는 경계 시점에 요청이 몰릴 수 있다. 예를 들어 10:30:59에 100번, 10:31:00에 100번 요청하면 실제 1초 사이에 200번을 허용할 수 있다.

더 정교한 방식이 필요하면 sorted set으로 sliding window를 구현하거나, token bucket 알고리즘을 Lua script로 원자적으로 처리한다.

트레이드오프는 정확도와 비용이다.

- fixed window는 단순하지만 경계 문제가 있다.
- sliding window는 정확하지만 저장 데이터와 연산 비용이 커진다.
- token bucket은 버스트를 자연스럽게 허용하지만 구현이 조금 더 복잡하다.

실무에서는 API 성격에 따라 다르게 둔다. 로그인 시도나 결제 요청처럼 민감한 API는 더 엄격하게, 검색 자동완성처럼 어느 정도 버스트가 허용되는 API는 token bucket이 잘 맞는다.

## 5. 카운터와 통계

Redis의 `INCR`, `INCRBY`, `HINCRBY`는 원자적 카운터를 만들기 좋다.

조회수, 좋아요 수, 실시간 접속자 수, 이벤트 참여 수처럼 빠르게 증가하는 값을 DB에 매번 쓰면 DB write 부하가 커진다. Redis에 먼저 적재하고 일정 주기로 DB에 반영하면 쓰기 부하를 줄일 수 있다.

하지만 이 방식은 유실 가능성과 정합성 트레이드오프가 있다.

- Redis 장애 시 아직 DB에 반영되지 않은 카운트가 사라질 수 있다.
- 배치 반영 중 중복 반영이 발생할 수 있다.
- 실시간 값과 DB 값이 다를 수 있다.

해결책은 요구 수준에 따라 달라진다.

- 유실되면 안 되는 값은 DB를 원장으로 두고 Redis는 조회 최적화로만 사용한다.
- 누적 카운트는 주기적으로 snapshot을 남긴다.
- DB 반영 작업은 idempotent하게 설계한다.
- 정확도가 덜 중요한 지표는 HyperLogLog 같은 확률적 자료구조를 검토한다.

조회수처럼 약간의 오차가 허용되는 값과, 포인트 잔액처럼 오차가 허용되지 않는 값은 같은 방식으로 다루면 안 된다.

---

## 6. 랭킹과 리더보드

Redis sorted set은 랭킹을 만들기 좋다.

```text
ZADD leaderboard 1200 user:1
ZREVRANGE leaderboard 0 9 WITHSCORES
ZRANK leaderboard user:1
```

각 member는 score를 가지고, Redis는 score 기준으로 정렬된 상태를 유지한다. 게임 랭킹, 인기 게시글, 실시간 점수판, Top N 상품 목록에 자주 쓰인다.

트레이드오프는 메모리와 정합성이다.

- 모든 유저를 sorted set에 넣으면 메모리 사용량이 커진다.
- score 산정 기준이 바뀌면 재계산 비용이 크다.
- DB 원장과 Redis 랭킹이 어긋날 수 있다.

실무에서는 랭킹 범위를 제한하거나, 기간별 key를 나눈다.

```text
leaderboard:daily:20260614
leaderboard:weekly:2026-W24
leaderboard:season:2026-summer
```

또한 Redis에는 랭킹 계산에 필요한 최소 데이터만 두고, 상세 프로필은 DB나 별도 캐시에서 조회하는 편이 좋다.

---

## 7. Pub/Sub과 Streams

Redis Pub/Sub은 메시지를 구독자에게 즉시 전달하는 데 사용할 수 있다.

구조가 단순하고 빠르지만, 구독자가 잠시 내려가 있으면 메시지를 놓칠 수 있다. 메시지를 저장하지 않기 때문이다. 그래서 Pub/Sub은 "놓쳐도 되는 실시간 알림"에 적합하다.

예를 들면 다음과 같다.

- 관리자 화면 실시간 갱신
- 내부 이벤트 브로드캐스트
- 채팅 presence 신호
- 캐시 무효화 이벤트 전파

반대로 메시지를 놓치면 안 된다면 Redis Streams를 볼 수 있다.

Streams는 append-only log에 가깝고 consumer group을 지원한다. 소비자가 처리한 위치를 추적할 수 있어 Pub/Sub보다 안정적인 이벤트 처리에 적합하다.

다만 Redis Streams도 Kafka 같은 전용 로그 플랫폼과 같은 선택지는 아니다.

- 장기 보관에는 메모리 비용이 크다.
- 대규모 재처리, 파티셔닝, 보관 정책은 Kafka가 더 적합할 수 있다.
- Redis 장애와 persistence 설정에 따라 메시지 내구성이 달라진다.

실무에서는 짧은 보관 기간의 내부 이벤트, 경량 작업 큐, 실시간 처리에는 Streams가 잘 맞고, 장기 이벤트 로그나 대규모 데이터 파이프라인은 Kafka 같은 시스템을 검토한다.

---

## 8. 큐와 지연 작업

Redis list를 사용하면 간단한 큐를 만들 수 있다.

```text
LPUSH queue:email job
BRPOP queue:email 5
```

작업을 넣고 worker가 꺼내 처리하는 구조다. 구현은 간단하지만, 실패 처리와 재시도까지 들어가면 생각보다 복잡해진다.

큐에서 중요한 질문은 "작업자가 꺼낸 뒤 죽으면 어떻게 할 것인가"다.

단순 `BRPOP`은 작업자가 메시지를 가져간 뒤 죽으면 메시지를 잃을 수 있다. 이를 보완하려면 processing queue를 따로 두거나, Streams의 pending entries를 활용하는 편이 좋다.

지연 작업은 sorted set으로 구현할 수 있다.

```text
ZADD delayed:jobs {executeAtTimestamp} {jobId}
```

worker가 현재 시간보다 score가 작은 job을 가져와 실행한다. 이 방식은 간단한 예약 작업에는 유용하지만, 정확한 실행 보장, 재시도, 중복 방지, dead letter queue까지 필요하면 전용 큐 시스템을 고려해야 한다.

---

## 9. 확률적 자료구조

Redis는 Bloom Filter, HyperLogLog, Count-Min Sketch 같은 확률적 자료구조도 제공한다.

이 자료구조들은 정확도를 일부 포기하고 메모리를 크게 줄이는 방식이다.

예를 들어 HyperLogLog는 고유 사용자 수 같은 cardinality 추정에 쓸 수 있다. 모든 사용자 ID를 Set에 저장하면 메모리가 많이 들지만, HyperLogLog는 훨씬 작은 공간으로 근사값을 제공한다.

Bloom Filter는 "이 값이 존재하지 않는지"를 빠르게 판단할 때 유용하다. 단, false positive가 있을 수 있다. 존재한다고 했는데 실제로는 없을 수 있다는 뜻이다. 반대로 존재하지 않는다고 판단한 값은 보통 존재하지 않는 것으로 볼 수 있다.

트레이드오프는 명확하다.

- 메모리는 줄어든다.
- 정확도는 낮아진다.
- 한 번 잘못 설계한 error rate는 운영 중 바꾸기 어렵다.

그래서 확률적 자료구조는 돈, 재고, 권한처럼 정확해야 하는 데이터가 아니라 분석, 추천, 사전 필터링, 중복 가능성 낮추기 같은 곳에 적합하다.

---

## Redis를 실무에 넣을 때 먼저 정해야 하는 것

Redis를 도입할 때는 "어떤 명령을 쓸까"보다 먼저 정해야 할 것들이 있다.

### 1. Redis가 원장인가, 캐시인가

가장 중요하다.

Redis가 사라졌을 때 복구 가능한 데이터라면 캐시다. 이 경우 eviction, TTL, 재생성 전략을 중심으로 설계하면 된다.

반대로 Redis에만 있고 사라지면 안 되는 데이터라면 원장에 가깝다. 이 경우 AOF/RDB persistence, replication, backup, failover, 데이터 복구 절차까지 설계해야 한다. 그래도 Redis를 RDBMS처럼 강한 정합성 저장소로 쓰는 것은 조심해야 한다.

### 2. TTL은 서비스 정책이다

TTL은 단순 성능 파라미터가 아니다.

- 사용자가 얼마나 오래된 값을 봐도 되는가
- 중복 요청을 얼마나 오래 막아야 하는가
- 재시도는 언제까지 같은 결과를 받아야 하는가
- 메모리 비용은 어디까지 감당 가능한가

이 질문의 답이 TTL이다.

### 3. 큰 key를 만들지 않는다

Redis에서 위험한 건 key 개수가 많은 것보다, 하나의 key가 너무 커지는 경우다.

큰 hash, 큰 list, 큰 set은 특정 명령에서 메인 스레드를 오래 점유할 수 있다. key sharding, 기간별 분리, 페이지 단위 저장, `SCAN` 계열 명령 사용을 처음부터 고려해야 한다.

### 4. 장애 시 동작을 정한다

Redis가 느리거나 장애가 났을 때 서비스를 어떻게 할지 정해야 한다.

- 캐시 장애면 DB로 우회할 것인가
- DB 보호를 위해 일부 요청을 실패시킬 것인가
- 분산락 획득 실패 시 요청을 막을 것인가
- 세션 조회 실패 시 로그아웃 처리할 것인가

이 정책이 없으면 장애 시 애플리케이션이 Redis를 계속 기다리다가 전체 장애로 번질 수 있다.

### 5. 관측 지표를 먼저 붙인다

Redis는 빠른 만큼 문제가 생겼을 때 전파도 빠르다.

최소한 다음 지표는 봐야 한다.

- `used_memory`, `used_memory_peak`
- `mem_fragmentation_ratio`
- `evicted_keys`
- `expired_keys`
- `keyspace_hits`, `keyspace_misses`
- `instantaneous_ops_per_sec`
- `connected_clients`
- `blocked_clients`
- `slowlog`
- `latency doctor`
- big key, hot key
- `lazyfree_pending_objects`

캐시 hit rate만 보면 부족하다. Redis가 빠르게 응답하고 있는지, tail latency가 튀는지, eviction이 발생하는지 같이 봐야 한다.

---

## 정리

Redis가 싱글 스레드인데 빠른 이유는 한 가지가 아니다.

메모리에 데이터를 두고, key-value 구조로 빠르게 찾고, I/O multiplexing으로 많은 커넥션을 감시하고, RESP로 파싱 비용을 줄이고, Pipeline으로 네트워크 왕복을 압축한다. 그리고 핵심 명령 실행 경로를 싱글 스레드로 유지해 락 경합을 없앤다.

그래서 Redis는 빠르다.

하지만 Redis가 빠르다는 말은 어떤 명령을 어떻게 써도 괜찮다는 뜻이 아니다. `KEYS`, 큰 자료구조 전체 조회, hot key, 큰 key 삭제, `fsync always`, 메모리 부족 후 eviction 같은 패턴은 싱글 스레드 구조의 약점을 그대로 드러낸다.

Redis를 잘 쓰는 방법은 빠른 기능을 많이 아는 것이 아니라, Redis가 빠른 경로에서 벗어나지 않게 모델링하는 것이다.

캐시라면 스탬피드를 막고, 분산락이라면 TTL과 token, DB unique constraint를 함께 둔다. 세션, rate limit, 카운터, 리더보드, Streams, 확률적 자료구조도 마찬가지다. 각각은 편리하지만 항상 트레이드오프가 있다.

Redis는 문제를 없애주는 도구가 아니라, 문제의 위치를 바꾸는 도구에 가깝다.

DB 부하를 Redis로 옮기고, 서버 간 상태 공유를 Redis로 옮기고, 네트워크 왕복과 원본 조회 비용을 Redis로 줄인다. 그래서 Redis를 도입할 때는 항상 물어봐야 한다.

> 이 데이터를 Redis에 두면 무엇이 빨라지고, 대신 어떤 실패 모드를 새로 갖게 될까?

이 질문에 답할 수 있을 때 Redis는 단순한 캐시 서버가 아니라, 서비스 레이턴시와 운영 안정성을 함께 설계하는 도구가 된다.
